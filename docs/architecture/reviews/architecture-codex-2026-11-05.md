## 1. 판단

**기본 구조는 유지하고, 처리 규칙과 검증 조건을 보완하는 편이 좋다.** 모듈형 모놀리스, PostgreSQL, 건물 안에서 끝나는 호출 경로, `family` 단일 공유 경로, 원장 불변, 직원용 AI와 회원 답 틀의 구분은 서로 맞는다. 이번 검토를 근거로 마이크로서비스·Kubernetes·별도 벡터 DB를 앞당길 이유는 찾지 못했다. [가설]

## 2. 우선 보완 제안

### R1. `16.4.1 이상`만으로 보안 기준을 닫지 않는다

- **위치:** [설계안 3절](../senior-housing-architecture-design.md), 6.7절. `arch-system/candidate.json:447`, `stack/make.py:200` 등 도식 원본에도 같은 버전이 있다.
- **문제·근거:** 문서가 인용한 RCE 수정 이후에도 2026-11-03 공식 캐시 보안 공지가 있다. 중첩 `use cache`와 root parameter의 특정 조합 문제는 16.4.2 수정으로 표시된다. 별도 binary 인자 캐시 문제는 영향 버전이 16.0.0~16.4.2이고 공지의 수정 버전 칸은 `None`이다. 두 공지를 혼동해 “16.4.2면 모두 해결”이라고 쓸 수 없다. [사실] [중첩 캐시 공지](https://github.com/vercel/next.js/security/advisories/GHSA-vc7v-qv4w-wrv8), [binary 인자 공지](https://github.com/vercel/next.js/security/advisories/GHSA-rhh4-g77r-r9qj), 조회 2026-11-05.
- **영향:** 실제 위험은 해당 기능 사용 여부에 달려 있다. 사용자·보호자별 응답을 잘못 공유 캐시하면 DB의 권한 검사를 거쳤더라도 다른 응답을 돌려줄 수 있다. 현재 프로토타입에는 Next.js 서버가 없으므로 해당 취약점 적용 여부를 판정한 것은 아니다. [추정]
- **최소 보완:** 승인된 하한 버전의 재검토를 제안한다. 설계에는 “도입 시 공식 보안 공지를 확인한 지원 패치를 정확한 버전으로 고정”하는 절차를 추가한다. 초기 기본값은 건강 소식·청구·권한 응답의 공유 캐시 제외다. 공개 정적 자료만 별도 캐시 대상으로 둔다. [가설]
- **2개 운영 조건:** Valkey 설치 외에 캐시 핸들러·무효화 전파, 동일 빌드, 배포 버전 구분을 명시한다. Server Actions를 사용하면 빌드 간 암호화 키 관리도 정한다. 이 조건들은 Next.js 자체 호스팅 문서의 다중 인스턴스 고려사항이다. [사실] [공식 자체 호스팅 문서](https://nextjs.org/docs/app/guides/self-hosting), 조회 2026-11-05.
- **확인 시나리오:** 보호자 A가 조회한 뒤 B가 같은 주소를 조회해도 A의 내용을 받지 않는다. 철회 직후 어느 화면 인스턴스로 요청해도 거부된다. 구·신 버전이 함께 도는 배포 중에도 같은 결과다. [가설]

### R2. 공유 허락 철회와 원본 삭제를 분리한다

- **위치:** [설계안 6.4절](../senior-housing-architecture-design.md), 6.8절 398행, 복구 342행. 대조: `evenstay/docs/family/tech-design.md` 3-1·3-2절.
- **문제·근거:** 설계는 보호자 공유·건강정보 처리·모델 투입을 다른 동의 목적으로 정의하면서, 보호자 허락 철회도 원본과 인덱스까지의 “삭제 전파”에 함께 넣는다. 반면 `family`의 `Consent`는 특정 보호자 × 항목의 열람 허락이다. [사실]
- **영향:** 한 보호자의 열람 철회가 직원과 다른 보호자에게 필요한 원본 삭제로 해석될 여지가 있다. 또한 복원 후 철회를 다시 적용한다는 규칙은 있으나 재적용 완료 전에 서비스를 열 수 있는지 명시하지 않았다. [추정]
- **최소 보완:** 아래 목적별 효과표를 추가한다. 실제 보존·파기 근거는 법률 검토로 확정하고, 공유 철회를 원본 파기로 직접 연결하지 않는다. 복구 시 별도 철회 기록의 재적용과 검증이 끝날 때까지 보호자 조회와 관련 발송을 닫는다. [가설]

| 변경 | 즉시 적용할 효과 | 원본·파생물 처리 제안 |
|---|---|---|
| 특정 보호자 공유 철회 | 그 보호자의 조회·예정 알림 차단, 관련 캐시 무효화 | 원본은 소유 모듈의 보존 근거로 판단 |
| 모델 투입 동의 철회 | 새 투입·대기 작업 차단 | AI 파생물과 진행 중 작업의 처리 범위를 정책으로 결정 |
| 원본 처리 근거 소멸·보존 기간 만료 | 해당 처리 중지 | 보존 의무 여부를 확인한 뒤 원본·파생물별 파기 |

- **확인 시나리오:** A에게만 건강 소식을 그만 보여 주면 A는 즉시 거부되고, 허락이 유지된 B와 권한 있는 직원의 자료는 남는다. 철회 이전 시점으로 복원해도 재개 전에 A의 거부가 회복된다. [가설]

### R3. RLS 문맥에 `operator_id`를 명시한다

- **위치:** [설계안 6.5절](../senior-housing-architecture-design.md). 대조: `evenstay/docs/core/tech-design.md:61`, ADR-1.
- **문제·근거:** 격리 경계는 운영사라고 선언했지만 구체적인 세션 변수 설명에는 허용 `site_id` 배열만 있다. 코어에는 `operator_id`가 모든 행에 있고 `site_id`는 사업장 행에만 있다. 운영사 범위 행은 사업장 목록만으로 처리 규칙이 설명되지 않는다. [사실]
- **최소 보완:** 서버가 만드는 문맥을 `operator_id`, `allowed_site_ids`, 주체 ID로 적는다. 모든 행은 운영사 일치를 먼저 확인하고 사업장 행에는 사업장 포함 조건도 적용한다. 문맥 누락은 거부한다. 정책 여러 개를 쓸 경우 운영사 제한이 다른 허용 정책의 OR 결합으로 풀리지 않도록 한다. [가설] PostgreSQL은 기본 허용 정책을 OR로, 제한 정책을 AND로 결합한다. [사실] [공식 RLS 문서](https://www.postgresql.org/docs/18/ddl-rowsecurity.html), 조회 2026-11-05.
- **확인 시나리오:** 운영사 없는 문맥, 다른 운영사, 사업장 없는 운영사 행, 풀에서 이전 요청 문맥을 재사용하는 경우를 API·작업자 양쪽에서 시험한다. 시스템의 사업장 열거에도 운영사 범위를 적용한다. [가설]
- **판단 한계:** SQL 구현이 없으므로 실제 격리 실패를 확인한 것은 아니다. 이미 정한 이중 방어를 구체화하는 제안이다.

### R4. 오래된 호출을 종료된 호출로 간주하지 않는다

- **위치:** [설계안 6.1절](../senior-housing-architecture-design.md).
- **문제·근거:** 기준 시간보다 오래된 신호는 기록만 하고 알림을 내지 않는다. 그러나 호출 상태의 정본은 건물 안 설비다. 발생 시각만으로 현장에서 확인하거나 종료했는지는 알 수 없다. [사실·추정]
- **최소 보완:** 늦은 신호를 “종료·확인 증거 있음 / 진행 중 / 상태 미확인”으로 나눈다. 기록만 하는 것은 종료·확인이 증명된 경우로 한정한다. 진행 중과 미확인은 현재 상태 조회 또는 현장 확인 목록으로 보내며 기존 호출을 새 호출처럼 무조건 재발송하지 않는다. 공급자가 종료 상태를 주지 못하면 그 한계를 명시한다. [가설]
- **식별자:** 시각만 이용한 대체 중복 키는 별도 검증한다. 영속 어댑터 식별자와 이벤트 순번을 기본으로 두고, 순번을 초기화할 수 있다면 세대 식별자를 함께 둔다. [가설]
- **확인 시나리오:** 긴 단절 뒤 미해결 호출, 단절 중 종료한 호출, 해제 신호가 먼저 도착한 경우, 같은 시각의 다른 호출을 구분한다. 건물 안 호출 경로는 계속 자립한다. [가설]

### R5. 사업장별 반복 작업을 실패 단위로 나눈다

- **위치:** [설계안 6.11절](../senior-housing-architecture-design.md), 4.2절 154행. 대조: 코어 `tech-design.md` 확인할 것 35.
- **문제·근거:** 반복 작업 하나가 사업장을 돌도록 정했지만, 한 사업장이 실패한 뒤 나머지를 계속하는지와 재시작 지점은 닫히지 않았다. 이 부분은 코어에도 미결정으로 남아 있다. [사실]
- **영향:** 한 사업장의 오류가 다른 사업장의 청구나 대리권 만료 처리를 지연시키거나, 전체 재시작으로 이미 끝난 작업이 반복될 수 있다. [추정]
- **최소 보완:** 단일 반복 작업은 유지하되 실행 결과와 재시도 단위를 `(운영사, 사업장, 작업 종류, 대상 기간)`으로 기록한다. 한 사업장 실패는 기록하고 다음 사업장을 처리하며 실패한 단위만 재시도한다. 거대한 전체 트랜잭션을 만들지 않는다. [가설]
- **작업자 분리 조건:** 이미 정한 `safety` 전용 타이머 스레드·풀은 유지한다. 일반 JobRunr 작업은 프로세스만 나눠도 업무별 소비가 분리된다고 쓰지 않는다. 같은 작업 저장소를 읽는다면 별도 저장소나 지원되는 큐 라우팅 같은 실제 할당 경계를 정해야 한다. [가설] [JobRunr FAQ](https://www.jobrunr.io/en/documentation/faq/), [동적 큐 문서](https://www.jobrunr.io/en/documentation/pro/dynamic-queues/), 조회 2026-11-05.
- **확인 시나리오:** 첫 사업장은 성공, 둘째는 실패, 셋째는 성공하게 한 뒤 재시작한다. 둘째만 재처리되고 다른 두 곳의 효과는 한 번이어야 한다. [가설]

## 3. 함께 보완할 항목

### R6. 자동이체의 미결정을 M2 완료 조건에 연결한다

- **위치:** 설계안 6.2절, [9절 11번](../senior-housing-architecture-design.md), 4.2절 M2 완료 기준. 코어 3-5·3-6절과 확인할 것 32.
- **근거:** 결과 미확인 배치를 재전송하지 않기, 청구서 잠금, 늦은 성공 결과의 예외 목록 처리는 이미 보완됐다. 이를 다시 빠진 기능으로 지적하지 않는다. 다만 결과 대기 중 수동 수납·승계의 최종 정책과 예외 목록 역할은 미정이고, M2 완료 기준에는 이 미결정을 닫는 항목이 직접 연결되지 않았다. [사실]
- **제안:** CMS 기능을 켜는 사업장의 운영 전환 조건에 해당 결정과 상태 조합 시험을 넣는다. `PENDING_BANK_RESULT + 수동 수납/건별 결제`, `대기 중 승계`, `종료 상태 뒤 늦은 성공`, `승계 뒤 되돌림`을 확인한다. 아직 결정을 못 했다면 해당 기능을 켜지 않는 조건을 둔다. 기존 기본안을 확정한 것처럼 쓰지 않는다. [가설]

### R7. 이벤트 ID 멱등 외에 순서와 소비자별 완료를 정의한다

- **위치:** 설계안 5절 6번, 6.7절 시험 표, [6.11절](../senior-housing-architecture-design.md). 코어 `OutboxEvent` 102행, 이벤트 계약 8-3절.
- **근거:** 중복 제거와 순서 역전 시험은 있지만, 순서가 뒤집혔을 때의 공통 기대 동작은 없다. `OutboxEvent.published_at` 하나와 모듈별 완료 표만으로는 소비자 A 성공·B 실패 후 재시도 범위도 명료하지 않다. [사실]
- **제안:** 상태를 적용하는 이벤트에는 집계 버전 또는 출처 revision을 사용하고, 지난 버전은 상태에 재적용하지 않는다. 단순 알림 이벤트는 정본 API 재조회 방식도 가능하다. 처리 완료 키는 `(consumer_id, event_id)`로 명시하고 소비자별 재시도·최종 실패 기록을 구분한다. 새 큐 도입은 필요하지 않다. [가설] AWS도 아웃박스에서 중복과 전달 순서를 별도 고려사항으로 다룬다. [사실] [AWS 아웃박스 지침](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html), 조회 2026-11-05.
- **확인 시나리오:** 같은 이벤트의 두 번째 전달, 버전 2 뒤 버전 1 도착, A 완료 후 B 처리 중 종료, B만 실패해 재시도하는 경우의 기대 결과를 적는다. [가설]

### R8. RDS 엔진 지원과 실제 견적 조합을 구분한다

- **위치:** [설계안 3절](../senior-housing-architecture-design.md), 7절 비용 표, 9절 4번.
- **근거:** AWS의 서울 PostgreSQL 18 지원표 중 확인한 것은 Multi-AZ **DB 클러스터**다. 비용 표는 `db.t4g.medium`의 Single-AZ와 Multi-AZ **DB 인스턴스**를 전제로 한다. 클래스 지원표에는 이 클래스의 PostgreSQL 18이 열거되지 않아 그 견적 조합은 별도 확인이 필요하다. 문서에 없다는 이유로 불가능하다고 단정하지 않는다. [사실·미확인] [지역별 클러스터 지원](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.RDS_Fea_Regions_DB-eng.Feature.MultiAZDBClusters.html), [클래스 지원표](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.DBInstanceClass.Support.html), 조회 2026-11-05.
- **제안:** `describe-db-engine-versions` 외에 아래 주문 옵션 조회로 지역·엔진 세부 버전·클래스·스토리지·Multi-AZ 가능 조합을 확인한다. 확인된 조합으로 비용을 다시 계산한다. 승인된 금액을 이 노트에서 변경하지 않는다. [가설] [AWS CLI 공식 문서](https://docs.aws.amazon.com/cli/latest/reference/rds/describe-orderable-db-instance-options.html), 조회 2026-11-05.

```bash
aws rds describe-orderable-db-instance-options \
  --region ap-northeast-2 \
  --engine postgres \
  --db-instance-class db.t4g.medium \
  --query 'OrderableDBInstanceOptions[].{Version:EngineVersion,Storage:StorageType,MultiAZ:MultiAZCapable}'
```

이 명령은 이번 검토에서 실행하지 않았다. 사용자의 AWS 계정을 이용한 주문 가능 조합과 실제 견적은 미확인이다. [미확인]

### R9. 오프라인 스냅샷도 별도 데이터 사본으로 관리한다

- **위치:** [설계안 6.1절](../senior-housing-architecture-design.md), 6.8절 분류·보존.
- **근거:** 스냅샷에 연락처·알레르기·비상 연락처·진행 중 요청을 담지만, 저장 장소·열람자·생성 시각·만료·회수 조건은 연결되지 않았다. 알레르기는 민감정보 최소 수집 원칙에 따라 필요성과 별도 수집 근거부터 확인해야 한다. [사실·추정]
- **제안:** 필수 항목만 정하고, 암호화한 현장 보관 장소와 허용 직원, 오프라인 열람 기록, 최대 사용 기간, 복구 후 교체·파기를 한 표로 둔다. 최신성과 권한 회수를 온라인처럼 보장하지 못하는 점도 표시한다. 프런트 PC에 무기한 CSV를 남기는 방식은 피한다. [가설]
- **확인 시나리오:** 오래된 사본, 직원 퇴사·권한 회수 중 단절, 현장 단말 분실, 복구 후 사본 회수와 정정 입력을 점검한다. 수치와 제품은 미정으로 둔다. [가설]

### R10. 현재 기준표와 옛 제안을 구분한다

- **위치:** [evenstay 개관 7절](../../overview/project.md), `evenstay/CLAUDE.md` 기술 방향, 설계안 6.11절, `strings/architecture.json`.
- **근거:** 개관 표에는 Modulith 이벤트 기록, 2단계 AI 서비스, 3단계 Kubernetes가 남아 있다. 바로 아래 주석이 최신 설계와의 차이를 설명하지만 표 자체만 읽으면 다른 결론을 낸다. 루트 기술 방향에는 “MVP는 Next.js, 나머지 미정”이 남아 있고 개관이 그 미반영을 인정한다. 최신 설계와 웹 문장은 Modulith 이벤트 기록 미사용, 문서 AI 3단계, Kubernetes 5단계 조건부다. [사실]
- **제안:** 개관의 현재 기준표를 승인된 최신 설계 기준으로 한 번 정리하고 옛 표는 히스토리로 구분한다. 0~5단계와 M0~M5만 현재 설명에 사용한다. 아웃박스도 “각 소유 모듈 스키마에 저장, `platform` 구현 공유”라는 코어 원문을 유지해 “코어 아웃박스 하나”로 오해되지 않게 한다. [가설]
- **반영 경로:** 사용자 지시 뒤 설계 원본 → `strings/architecture.json`·도식 원본 → 빌드 → 문장표 갱신 순서를 따른다. 생성 HTML·PNG를 직접 고치지 않는다. 이번 검토는 반영 지시나 승인 요청을 대신하지 않는다.

## 7. 반영 순서와 남긴 범위

1. R1의 새 보안 공지와 R10의 현재 기준표를 먼저 재검토한다.
2. R2·R3의 동의·운영사 경계를 문장과 결정표로 닫는다.
3. R4·R5·R7의 장애·순서·재시도 기대 결과를 시나리오로 적는다.
4. R6·R8·R9를 M0/M2의 결정·완료 조건에 연결한다.
5. 사용자가 반영을 맡기면 원본과 웹 원본을 정해진 순서로 맞춘다. 허브 요청은 그때 사용자 지시를 인용해 작성한다.

이번에 새로 쓴 것은 이 검토 노트와 프로젝트 스킬 설치·출처 기록뿐이다. 승인된 설계, `shared/`, evenstay 문서·문장·도식·생성물은 수정하지 않았다. MVP 구현, 운영 환경 변경, 공개 저장소 배포도 하지 않았다. [사실]
