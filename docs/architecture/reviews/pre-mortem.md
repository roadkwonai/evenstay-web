## Tigers (실제 위험)

| # | 위험 | 등급 | 근거 |

| T1 | 작업자·이벤트 리스너에서 RLS 범위가 빠진다. 대리인 만료 일일 배치나 비서 보관 정리가 0건을 처리하고 오류 없이 끝나거나, 급하게 BYPASSRLS로 우회한다 | 출시 차단 | 코어 문서에 세션 변수 설정 방식이 없다 |
| T2 | 작업자를 하나만 띄워 호출벨 넘김 타이머가 멈춘다. 웹훅 수신도 API와 같은 프로세스라 배포 중 끊긴다. `SKIP LOCKED`, 2개 동시 실행 테스트, 생존 지표는 이미 설계에 있고, 상시 2개 운영과 무중단 배포가 비어 있다 | 출시 차단 | ADR-S2, 안심 11절, 안심 확인할 것 8번 |

| T5 | 폴링 아웃박스가 밀려 알림 지연이 커진다 | 출시 후 30일 | 코어 11절 모니터링에 아웃박스 지연 지표가 있다 |
| T6 | Spring Boot 마이너를 해마다 올려야 하는데 소규모 팀이 미룬다 | 추적 | 4.0 종료 2026-12-31은 2차 자료 |

## Paper Tigers (과한 걱정)

- **모놀리스라 확장이 안 된다**: 약 400실 규모 사업장 몇 곳은 부하가 작다 [추정]. 조사한 사례 중 이 규모에서 분리가 필요했다는 근거는 없었다.
- **Kafka가 없어서 이벤트를 잃는다**: 아웃박스가 같은 트랜잭션에 저장한다. 소비자 멱등 처리는 이미 ADR-2 규칙이다.
- **언어가 둘이라 감당이 안 된다**: 화면 계층은 얇고 API 계약으로 나뉜다. 다만 혼자 구현할 때는 진짜 비용이다.
- **회원이 앱 푸시를 못 받는다**: 설계에 앱 푸시가 없다. 알림은 문자·알림톡과 직원 경로다(코어 9절). iOS 웹 푸시 제약은 앱을 넣을 때만 문제가 된다.
- **JVM 메모리 비용**: 작업 크기를 키워도 월 수십 달러 차이다.

## 출시 차단 위험의 조치

담당과 기한은 실서비스 일정이 없어 [미정]이다. 포트폴리오 범위에서는 설계 문서 반영까지만 한다.

| 위험 | 조치 | 담당 | 기한 |
|---|---|---|---|
| T1 | 시스템 작업용 범위 설정을 작업 실행기 한 곳에 둔다. "범위 없으면 실패" 테스트를 넣는다 | Tech Lead | 코어 ADR 추가 시 |
| T2 | 작업자 상시 2개 운영과 무중단 배포를 정한다. 수신이 끊기는 시간을 재서 안 4 전환 신호로 쓴다 | Tech Lead | 안심 ADR 보완 시 |
| T4 | 일반 조회 접속기록 범위와 보관 기간을 정한다. 법무 검토를 요청한다 | Tech Lead, 법무 | 실서비스 전 |

T3은 출시 차단이 아니지만 코어 9절을 고칠 때 일괄 출금 의뢰·결과 수신을 어댑터에 함께 넣는다.
