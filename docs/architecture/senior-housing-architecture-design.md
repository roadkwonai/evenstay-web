## 1. 결론

1. **시작은 기준안(A안)으로 둔다.** Next.js 화면, Spring Boot 4.1 + Modulith 업무 코어, PostgreSQL 18, AWS 서울이다. 2026-11-04에 사용자가 고른 "팀과 채용" 기준을 따른 것이다. GPT 문서가 JVM과 AWS를 우선한 것은 "경험이 깊으면", "기반이 있으면"이라는 조건이 붙은 판단이고, 그 조건은 확인되지 않았다. 회사 표준을 알면 그것을 따른다. [가설]
2. **B안(TypeScript 단일 언어)과 C안(Vercel + Supabase 파일럿)은 조건이 맞을 때 고르는 대안이다.** 세 안은 모듈 경계, PostgreSQL 스키마, 아웃박스 구조가 같다. 그래서 안을 바꿔도 스키마, 데이터, 화면은 남는다. 다만 코어 언어가 바뀌면 코어와 모듈 코드, 테스트는 다시 쓴다(3절 이동 표). [가설]
3. **어느 안이든 확장 단계는 같다.** 0단계 프로토타입에서 시작해 1단계 핵심 업무 구축, 2단계 운영 전환, 3단계 문서 AI, 4단계 승인 기반 에이전트, 5단계 플랫폼으로 확장한다. 완료 기준을 채우지 못하면 다음 단계로 진행하지 않고, 도입 기준이 나타나지 않은 구성요소는 더하지 않는다. 진행 순서는 10절 로드맵에 있다. [가설]
4. **실제 입주자 데이터를 받는 조건이 이 설계에서 가장 무거운 약속이다.** 기술 조건만이 아니라 동의와 대리 권한, 접속기록, 위탁과 국외 이전 대장, 장애 대체 절차, 법률 검토를 모두 채워야 한다(4.2절 2단계, 6.8절, 10.5절). [가설]
5. **GPT 문서에서 가장 쓸모 있는 부분은 기술 순위가 아니라 실패 조건이다.** 재시도 곱셈, DB 연결 한도, 읽기 복제본 제외 조회, 파티션 유일성 함정, 문서 삭제 전파, 승인 재검증을 이 설계에 넣었다. [가설]
6. **GPT 문서에서 약한 곳은 건물 층과 한국 결제다.** 일반 연동으로만 다룬 부분을 호출 설비 자립, 벤더 서명 웹훅 부재, CMS 비동기 상태기계, 소유주 범위로 채웠다. 모두 조사 문서에서 가져왔다. [가설]
7. **AI 사용 범위는 GPT 문서보다 좁게 둔다.** 회원에게 보이는 답은 틀에 채워 만들고(ADR-G1), 금전 실행은 에이전트 도구로 만들지 않는다. 에이전트는 직원용 초안과 제안까지다. [가설]

| AI 접근 | AI 기능부터 공통 모델 접근 계층 | 공급자가 하나인 동안 AI 게이트웨이 없음 | 1단계부터 어댑터, 제품 게이트웨이는 신호가 확인될 때 | 둘이 충돌하지 않는다. 어댑터가 공통 접근 계층이다 |

### 2.3 그대로 쓰지 않는 것

- **순위 숫자.** GPT 문서가 스스로 실측이 아니라고 밝혔다. 이 설계도 순위를 측정값처럼 쓰지 않는다. [사실]
- **월 예산 범위.** GCP $100~300, AWS $150~400은 GPT 문서가 "견적이나 검증된 최소 비용이 아니다"라고 적은 가설이다. 7절에서 전제가 다름을 밝힌다. [사실]
- **환불 실행 도구 `execute_approved_refund`.** 2.1절 표와 같은 까닭으로 넣지 않는다. [가설]
- **용어.** Unit, Site, Customer, Worker, Agent는 이 저장소의 말(호실, 사업장, 입주자, 인물, 작업자, 에이전트)로 옮겼다. 대응표는 `evenstay/docs/glossary.md`의 "아키텍처 용어"에 있다. [사실]


## 3. 구성안 세 가지

세 안은 "무엇을 먼저 고정하느냐"가 다르다. A안은 팀과 채용, B안은 언어 하나, C안은 검증 속도다.

| 항목 | A안(기준안) | B안 TypeScript 단일 언어 | C안 빠른 파일럿 |
|---|---|---|---|
| 화면 | Next.js 16, 도입 시 보안 공지를 확인한 지원 패치 고정 | Next.js 16, 도입 시 보안 공지를 확인한 지원 패치 고정 | Next.js 16, 도입 시 보안 공지를 확인한 지원 패치 고정 (Vercel) |
| 업무 코어 | Java 25, Spring Boot 4.1, Modulith 2.1 | NestJS 또는 Fastify | 프레임워크 없는 TypeScript 패키지 + 별도 작업자 |
| 실행 환경 | ECS(화면, API, 작업자) | ECS Fargate 또는 Cloud Run | Vercel + 컨테이너 작업자 |
| DB | RDS PostgreSQL 18 | RDS 또는 Cloud SQL | Supabase PostgreSQL(서울) |
| 비동기 | 모듈별 아웃박스 + JobRunr | 아웃박스 + SQS 또는 Cloud Tasks | 아웃박스 + 외부 작업자 |
| AI | 어댑터 → Bedrock 서울 | 어댑터 → Bedrock 또는 승인된 모델 API | 어댑터 → 승인된 모델 API |
| 적합한 경우 | 코어를 오래 맡을 팀이 JVM이고, 트랜잭션 경계를 프레임워크로 강제하고 싶을 때 | 팀이 TypeScript이고 화면과 계약 타입을 함께 쓰고 싶을 때 | 실제 데이터 없이 인증과 화면을 며칠 안에 사람에게 보여야 할 때 |
| 약점 | 언어가 1단계에 둘, 3단계부터 Python까지 셋이다. 초기 부담이 가장 크다 | 모듈 경계 검사 도구를 직접 골라야 한다. 3단계에 Python을 더하면 언어가 둘이다 | 복구와 작업자를 따로 더해야 하고, 고정 송신 IP가 유료 기능이다 |
| 실제 입주자 데이터 | 2단계 완료 기준을 채운 뒤 | 2단계 완료 기준을 채운 뒤 | A안이나 B안으로 옮긴 뒤를 기본으로 둔다 |

- Next.js는 16.0.0~16.4.0의 원격 코드 실행 취약점 외에 2026-11-03 캐시 관련 보안 공지도 나왔다. 중첩 캐시 문제의 수정 버전은 16.4.2이고, 별도 바이너리 인자 캐시 공지는 조회 당시 수정 버전이 표시되지 않았다. 도입할 때 각 공지와 지원 상태를 다시 확인하고 검증한 정확한 패치 버전을 고정한다. [사실·가설]
- C안의 코어를 Next.js 서버 코드 안에 쓰면 "Next.js는 `app/`·`ui/`에만"이라는 `evenstay/CLAUDE.md` 규칙과 어긋난다. 그래서 프레임워크 없는 패키지로 둔다. [가설]
- AWS는 서울의 PostgreSQL 18 Multi-AZ DB 클러스터 지원을 명시한다. 7절 견적의 `db.t4g.medium` Single-AZ·Multi-AZ DB 인스턴스 조합은 별도다. M0에서 `describe-orderable-db-instance-options`로 서울 리전의 엔진 세부 버전, 클래스, 스토리지와 Multi-AZ 가능 여부를 함께 확인하고 비용을 다시 계산한다. 실제 주문 가능 조합은 [미확인]이다.

**평가 기준**은 GPT 문서 1.3절에서 가져오고 안전 경로와 데이터 위치를 더했다. GPT 문서의 "실제 성능"은 측정값이 없어 뺐다. 숫자 점수를 매기지 않고 상대 판단만 적는다. [가설]

| 기준 | A안 | B안 | C안 |
|---|---|---|---|
| 모듈 경계를 강제하는 수단 | 강함(Modulith 검사) | 보통(도구를 직접 고름) | 보통 |
| 업무 정확성·복구 | 같음(같은 스키마와 아웃박스) | 같음 | 약함(2단계 요건을 옮겨야 채움) |
| 개발·운영 총비용 | 팀이 JVM이면 보통, 아니면 약함 | 팀이 TypeScript이면 강함 | 초기 강함, 이전 뒤 약함 |
| 첫 화면까지 속도 | 약함 | 보통 | 강함 |
| 부분 교체·확장 | 강함 | 강함 | 보통 |
| AI 통제 | 같음 | 같음 | 같음 |
| 호출 경로 분리 | 같음 | 같음 | 같음 |
| 서울 안 데이터 처리 | Opus 5·Sonnet 5일 때 가능 | AWS이면 같음, GCP이면 Gemini 2.5 Flash 하나 | 경로별 확인 필요 |

제품 기준과 별개로, 지원 직무가 Tech Lead·Backend라서 포트폴리오 설명에는 A안이 쓰기 쉽다. 공고에 기술 스택이 없으므로 "공고가 요구한다"로 쓰지 않는다. [가설]

**선택 기준.** 위에서부터 차례로 묻고 처음 맞는 곳에서 멈춘다. [가설]

1. 회사에 정해진 클라우드, 언어, 네트워크 표준이 있으면 그것을 따른다.
2. 실제 입주자 데이터 없이 화면 검증이 먼저이면 C안으로 시작하고, 2단계 전에 A안이나 B안으로 옮긴다.
3. 코어를 맡을 사람이 JVM이면 A안이다.
4. 코어를 맡을 사람이 TypeScript이면 B안이다. 서울 안 AI 처리가 조건이면 AWS로 둔다.
5. 어디에도 해당하지 않으면 A안으로 둔다. 사용자가 고른 기준이고, 포트폴리오로 설명하기 쉽기 때문이다.

**안을 옮기는 방법.** 언어가 같은지에 따라 비용이 크게 다르다. JobRunr와 Modulith 테이블은 A안 전용이고, RLS 정책은 세션 변수 방식이 달라지면 다시 쓴다. [가설]

| 이동 | 유지 | 고쳐서 옮김 | 다시 작성 |
|---|---|---|---|
| C안 → B안 | 스키마와 데이터, 화면, TypeScript 코어 패키지 | 인증 연결, RLS 변수 주입, 작업자 배포 | 실행 환경, IaC |
| C안 → A안 | 스키마와 데이터, 화면 | 인증 연결, RLS 변수 주입 | 코어와 모듈 코드, 테스트, 실행 환경. M1을 사실상 다시 한다 |
| A안 ↔ B안 | 스키마와 데이터, 화면, OpenAPI 계약 | 인증 연결 | 코어와 모듈 코드, 테스트, 작업 실행 테이블 |

## 4. 확장 단계

### 4.1 단계별 구성

| 단계 | 이름 | 단계별 제안 대응 | GPT 문서 대응 | 목적 |
|---|---|---|---|---|
| 0 | 프로토타입 | 없음 | 없음 | 지금 있는 결과물. 서버 없이 화면과 흐름을 보인다 |
| 1 | 핵심 업무 구축 | 기존 1단계 | 0 범위·환경 확정, 1 업무 MVP | 계약, 청구, 권한, 원장을 컨테이너 3개와 DB 하나로. 가상 데이터만 쓴다 |
| 2 | 운영 전환 | 기존 2단계 앞부분 | 1의 운영 조건 | 실제 입주자 데이터를 받을 수 있는 복구, 격리, 법적 준비 |
| 3 | 문서 AI | 기존 2단계 AI 부분 | 2 첫 AI 기능 | 직원용 문서 추출, 근거 검색, 평가와 비용 추적 |
| 4 | 승인 기반 에이전트 | 기존 3단계 일부 | 3 지속 실행 Agent | 긴 승인 흐름을 재개할 수 있게 한다 |
| 5 | 플랫폼 확장 | 기존 3단계 나머지 | 4 운영 확대, 5 플랫폼 확대 | 측정된 병목만 분리한다 |

2단계와 3단계는 병행할 수 있다. 다만 3단계를 가상 문서로 완료했다면 성공 1건당 비용은 가상 값이고, 실제 문서를 모델에 넣는 일은 2단계 완료 뒤에 한다. [가설]

### 4.2 단계별 구성 (A안 기준)

**0단계. 프로토타입 (지금)** [사실]
- HTML·JS 클릭형, 상태는 브라우저 localStorage, 서버와 DB 없음.
- 화면과 흐름, 시연 41단계를 이 형태로 먼저 검증했다. 모듈 경계의 DB 규칙은 서버가 없어 검증하지 못했다.

**1단계. 핵심 업무 구축** [가설]
- 추가 구성: Next.js 1개, Spring Boot 이미지로 API와 작업자, RDS PostgreSQL 18 Single-AZ, S3, Secrets Manager, CloudWatch.
- 실행: 화면과 API는 ECS Express Mode 후보, 작업자는 일반 ECS다. 공식 기능임은 확인했고, 작업자에 쓸 수 없다는 문장은 못 찾았다. 일반 ECS는 용도 설명에서 나온 추정이다(대조 16번).
- 네트워크: DB와 작업자는 프라이빗 서브넷, ALB만 공개한다. 프라이빗 서브넷의 태스크가 이미지를 받고 로그를 보내려면 NAT 또는 VPC 엔드포인트가 필요하다(대조 F1). 현장 어댑터는 아웃바운드 TLS만 쓴다.
- PostgreSQL이 맡는 일: 모듈별 스키마, RLS, 아웃박스, JobRunr 저장소. 역할 구분은 6.11절에 있다.
- 처음부터 두는 테이블: 주체 유형, 동의·대리, 보존 정책, 접속기록(6.8절). 민감 컬럼은 암복호 포트 뒤에 둔다.
- 외부 연동: 어댑터만 두고 목업. 데모 AI는 녹화 응답이 기본이고(ADR-G6), Bedrock 실호출은 가상 데이터로 테스트할 때만 켠다.
- 완료 기준:
  - 가상 데이터만 쓴다.
  - 다른 사업장 ID를 직접 요청해도 막힌다. 정책 테스트 세 가지(다른 사업장 행이 안 보인다, 변수가 없으면 0행이다, `WITH CHECK`가 쓰기를 막는다)가 API와 작업자 경로 모두 통과한다.
  - 운영사 문맥 누락·다른 운영사·사업장 없는 행과 연결 풀 재사용을 API와 작업자에서 시험한다. 운영 역할이 테이블 소유자나 BYPASSRLS가 아님을 CI가 확인한다.
  - 같은 결제 이벤트가 여러 번 와도 수납은 한 번 반영된다. 원장은 추가만 된다.
  - 복원 절차를 한 번 돌려 봤다.
- 고정비: 약 $261(계산값, 7절).

**2단계. 운영 전환** [가설]
- 추가 구성: Multi-AZ, 화면, API, 작업자 2개씩, 무중단 배포, Valkey 공유 캐시, OpenTofu, 계정 분리, OpenTelemetry, 외부 상태 점검, 봉투 암호화(KMS), 접속기록 점검, 비밀 순환.
- 실제 어댑터: 도입하기로 한 CMS, PG, ERP 배치, 알림톡, 출입 조회, 전자서명, 본인확인. CMS의 미결정 조건은 아래 완료 기준에서 확인한다. 허용목록에 등록할 고정 송신 IP는 NAT로 만든다.
- 안심 경로 격리: 넘김 타이머는 JobRunr 공용 작업과 분리된 스레드와 DB 연결 풀로 돌린다. 월 청구가 넘김을 늦추는지 측정하고, 한도를 넘으면 전담 작업자로 나눈다(8절). JobRunr 우선순위 큐와 동적 큐는 Pro 기능이다(대조 F2). 프로세스만 나누고 같은 작업 저장소를 읽으면 업무별 소비가 분리되는 것은 아니므로 저장소나 지원되는 큐 라우팅 등 할당 경계를 확인한다. [추정]
- 시작 전: 법률 검토 묶음(10.5절). C안이면 A안이나 B안으로 옮기는 일을 끝낸다.
- 완료 기준(실제 입주자 데이터 투입 조건):
  - M0에서 정한 RPO·RTO를 복원 훈련으로 확인했다. 복원 뒤 동의 철회와 삭제를 다시 적용했다.
  - CMS를 켜는 사업장은 결과 대기 중 수동 수납·승계의 코어 확인할 것 32를 결정하고 상태 조합 시험을 마쳤다. 결정하지 못했다면 해당 사업장의 CMS는 끈다.
  - 외부 API 시간 초과를 실패로 단정하지 않고 결과 조회와 대사로 넘긴다.
  - 작업자나 어댑터의 하트비트가 끊기면 앱 밖 경로로 알림이 가고, 접수자가 확인 응답한다.
  - 개별 알림이 전달되지 않으면 다음 수단으로 넘어간다.
  - 월 청구를 돌리는 동안에도 넘김 지연이 사업장 설정 한도 안에 있다.
  - 접속기록 점검을 한 번 실제로 돌렸고, 침해 범위 산출을 테스트했다.
  - 위탁·이전 대장, 처리방침, 동의 근거가 법률 검토를 거쳤다.
  - 직원 대체 절차 훈련을 한 번 했고, 인수인계 절차가 있다.
- 고정비: 약 $546(계산값, 7절).

**3단계. 문서 AI** [가설]
- 추가 구성: `documents` 모듈, FastAPI + Pydantic v2 + PydanticAI AI 서비스(업무 DB 접근 없음), Taskiq, pgvector + 전문 검색 + `pg_bigm`, 문서 파이프라인, 평가 세트, 비용 계측.
- 경계: 코어와 모듈이 `authorize()` 뒤 허용 필드만 AI 서비스에 넘긴다. AI 서비스가 업무 API를 직접 부르지 않는다. 파싱과 임베딩 결과는 `documents` API로 돌려주고, 벡터 저장과 검색은 `documents`가 맡는다(6.11절).
- 첫 기능 순서: ① 계약서·운영 문서 구조화 추출과 검토 보조 ② 규정·계약 조항 근거 검색(직원용) ③ 허용된 업무 API를 쓰는 운영 질의 ④ 직원이 검토할 초안(주간 리포트, 직원용 답변). 회원 답을 생성하는 일은 여기 없다.
- 시작 전: AI 기능 등록부, 고지 문구, 고영향 해당성 점검(6.3절). Python 패키지는 해시로 고정한다.
- 완료 기준: 근거 문서와 쪽 번호를 제시한다. 폐기된 규정이 나오지 않는다. 권한 밖 문서가 모델에 들어가지 않는다. 성공 1건당 비용을 안다.
- 고정비: 약 $567(계산값, 7절). 필요가 확인되지 않으면 Python 서비스를 뺀다.

**4단계. 승인 기반 에이전트** [가설]
- 추가 구성: `assistant` 스키마에 에이전트 실행 기록과 승인 테이블. 기본은 DB 상태기계다. 조사 노트도 흐름이 단순하면 상태기계로 충분하다고 봤다. LangGraph(Python)나 Spring AI 실행기는 8절 기준을 채울 때만 더한다. Spring AI는 승인 화면과 영속화를 주지 않는다. 필요하면 LiteLLM을 쓰되 버전과 해시를 고정한다(6.3절). 외부 MCP는 8절 기준을 채울 때 읽기부터 연다.
- 시작 전: 대상 업무 명령이 있어야 한다. 계약 변경 명령은 코어의 다음 버전 범위라서 이 명령이 먼저 준비돼야 한다.
- 대상 예: 계약 변경 요청 분석 → 최신 계약 조회 → 코어가 영향 계산(모델이 금액을 계산하지 않는다) → 제안 → 담당자 승인 → 직원이 승인 ID를 붙여 업무 명령 실행 → `assistant`가 같은 트랜잭션에서 재검증하고 코어 명령 실행. 금전을 움직이는 마지막 단계는 사람의 업무 명령이다.
- 완료 기준: 작업자가 재시작돼도 같은 제안과 승인 요청이 두 번 만들어지지 않는다. 승인 뒤 권한이나 계약 버전이 바뀌면 실행이 거절되고 다시 묻는다. 승인 없이 같은 명령을 낼 수 없다. 문서 안의 지시문이 도구 권한을 바꾸지 못한다.
- 고정비: [미정].

**5단계. 플랫폼 확장** [가설]
- 측정된 병목을 기준으로 고른다. 읽기 복제본, 파티션, 검색 분리(OpenSearch Nori), 분석 저장소, dlt + Dagster, 부하가 다른 모듈 분리, 기관 연계, EKS Auto Mode, Langfuse 자체 호스팅.
- GraphDB, 샤딩, 자체 GPU는 8절의 도입 기준을 채울 때만 검토한다. 나타나지 않으면 5단계에도 넣지 않는다.
- 고정비: [미정].

## 5. 처음부터 지킬 규칙

다음 단계로 확장할 때 다시 작성하지 않으려는 규칙이다. 안이 달라도 같다. [가설]

1. 서비스별 이미지 하나, 설정은 환경변수, 상태는 DB와 객체 저장소에 둔다. 헬스체크와 SIGTERM 종료를 지원한다.
2. 큐, 모델, 검색, 알림, 결제, ERP, 수신은 인터페이스 뒤에 둔다.
3. 모듈 경계는 첫날부터 CI로 검사한다.
4. AI 서비스는 업무 DB에 접근하지 않는다. 코어와 모듈이 `authorize()` 뒤 허용 필드만 넘긴다.
5. 금액은 원 단위 정수, 발행 항목은 불변으로 시작한다. 되돌림은 조정 전표로 한다.
6. 쓰기 요청은 `Idempotency-Key`를 받고, 소비자는 이벤트 ID로 멱등 처리한다. 전달은 적어도 한 번으로 설계한다.
7. 사업장 범위는 요청 값이 아니라 서버가 정한다. 사람 요청은 세션, 시스템 작업은 `runAs`, 에이전트는 저장된 위임 권한으로 정한다. 에이전트가 넘긴 `site_id`도 믿지 않는다.
8. 긴 대기는 트랜잭션과 잠금을 붙잡지 않는다.
9. 외부 호출의 시간 초과는 "알 수 없음"이다. 실패로 적지 않고 대사로 넘긴다.
10. 캐시와 모델 출력은 원장이 되지 않는다.
11. 모델 호출 코드를 흩어 놓지 않는다. 어댑터 하나를 거친다.
12. 호출 경로는 이 시스템 없이 동작해야 한다. 이 시스템은 2차 알림과 기록이다.
13. 입주자와 보호자가 쓰는 기능에는 앱 밖 경로(전화, 문자, 직원 대행, 보호자 대행)가 있다. 대행은 대행자, 근거, 접수 채널을 기록하고 같은 `authorize()`와 접속기록을 지난다.
14. 주민등록번호는 수집하지 않는다. 민감 컬럼은 처음부터 암복호 포트 뒤에 둔다. 2단계에 봉투 암호화를 켜도 컬럼 형태와 검색 방식이 바뀌지 않게 하려는 것이다.
15. 카드번호와 인증정보를 받지 않는다. 저장은 PG 토큰과 마스킹한 표시 값까지이고, 로그, 추적, 아웃박스, AI 입력에는 카드와 계좌 번호를 넣지 않는다. CI에서 패턴을 검사한다.
16. 이 시스템은 수납 기록과 대사까지만 한다. 정산금을 대신 받아 나눠 주지 않는다.
17. 법정 요건과 입법예고 중인 요건은 코드가 아니라 정책 버전과 설정으로 둔다.
18. 발생 시각과 입력 시각을 따로 저장한다. 장애 뒤 재입력과 늦게 온 신호를 구분하기 위해서다.
19. 의존성은 잠금 파일로, 이미지는 digest로 고정한다. 정적 클라우드 키를 두지 않고 GitHub OIDC를 쓴다.
20. 스키마 변경은 추가, 이중 쓰기, 제거 순서로 나눈다. 무중단 배포 때 옛 버전과 새 버전이 함께 돌기 때문이다.

## 6. 흐름별 설계

### 6.1 호출과 안심 신호

호출 접수와 표시는 건물 안 설비에서 끝난다는 구조를 권고안으로 둔다. 클라우드는 사본을 받아 2차 알림과 기록을 맡는다. 국내 설비의 실제 구조는 벤더 문의 전이다. 근거와 한계는 조사 문서 6.5절, 10절에 있다. [추정]

- L0 입주자 방 → L1 건물 안 호출 경로(자립) → L2 현장 어댑터(정규화, 서명, 단절 시 버퍼) → L3 수집(원본 먼저 보관, 중복 확인) → L4 코어 PMS → L5 외부 시스템.
- 국내 벤더의 서명 웹훅은 확인되지 않는다. 어댑터가 서명한다. 벤더 연동은 계약과 맞춤 개발 가능성으로 표시한다. [추정]
- 5분 미응답 시 다음 당번을 호출하는 기준은 사업장 설정값이고 법정 요건으로 확인되지 않았다. 열어 본 법령 본문(미러)에서 찾지 못했다는 뜻이다. [추정]
- 개인 이동 위치가 들어가는 신호(웨어러블, GPS)는 이 설계에 없다. 넣게 되면 위치정보법 검토부터 한다. [가설]

**멈춤 감시.** 멈춘 구성요소는 스스로 멈췄다고 알리지 못한다. 그래서 작업자와 어댑터가 하트비트를 보내고, 앱 밖 점검이 시간을 세어 끊기면 경보를 낸다. URL 점검만으로는 API가 살아 있고 작업자만 멈춘 상태를 못 본다. 수신은 메신저와 문자·전화 두 갈래로 둔다. 건물 인터넷이 끊기면 어댑터 하트비트도 끊기므로 같은 경보로 알 수 있고, 건물 안에는 어댑터의 단절 표시등을 둔다. 주기, 제공자, 받는 사람은 [미정]이고 Opsgenie는 2027-04-05에 종료된다(조사 문서 8절). [가설]

**알림 전달.** 생성 → 발송 요청 → 전달 확인 → 사람 확인 → 확인이 없으면 다음 수단 → 다음 당번 순서로 상태를 둔다. 채널 순서(앱 알림, 알림톡, 문자, 음성 전화, 현장 단말)는 사업장 설정이다. 알림톡과 문자의 발송 성공은 읽음이 아니다. 같은 알림이 여러 채널로 나가므로 알림 멱등 키와 확인 뒤 취소를 둔다. 건강 소식의 보호자 채널은 `family` 동의를 지난 것만 쓴다. [가설]

**늦게 온 신호.** 단절 뒤 쌓인 신호는 건물 안 설비의 현재 상태와 대조해 종료·확인 증거가 있는 호출, 진행 중인 호출, 상태 미확인으로 나눈다. 종료·확인이 증명된 경우에만 기록으로 남기고 넘김을 생략한다. 진행 중과 미확인은 현장 상태를 확인하고, 미확인은 직원 확인 목록에 둔다. 시간만으로 종료를 판정하거나 모두 새 호출로 다시 보내지 않는다. 벤더가 현재 상태와 안정적인 이벤트 번호를 제공하는지는 [미확인]이다. 이벤트 번호가 없는 경우의 식별과 중복 방지 방식은 벤더 규격을 확인해 정한다. [가설]

**단절 시 대체 절차.** L2 이상이 멈춰도 L1은 계속 동작해야 한다. 직원은 ① 기존에 수집한 연락처, 비상 연락처, 진행 중 요청 중 필요한 항목만 담은 읽기 전용 스냅샷을 쓰고 ② 복구 뒤 재입력할 때 발생 시각과 입력 시각을 나눠 적고 ③ 장애 구간을 기록에 표시한다. 사본의 생성 시각·만료·허용 열람자·오프라인 열람 기록·암호화 보관·복구 후 회수와 파기를 정한다. 단절 중에는 최신성과 권한 회수를 온라인처럼 보장하지 못한다. 보관 위치, 유효 기간과 전환 시간은 [미정]이다. [가설]

### 6.2 청구와 결제

- 월 청구는 코어 트랜잭션이고, 발행이 확정 시점이다. 발행 뒤 정정은 조정 전표로만 한다. [가설]
- 자동이체는 요청과 결과가 분리된다. 코어 `tech-design.md` 3-5절의 객체별 상태를 그대로 따른다. [가설]
  - 출금 동의 `DirectDebitMandate`: REQUESTED → REGISTERED → REVOKED, 등록 거절은 REJECTED. 매달 흐름의 전제다.
  - 출금 의뢰 배치 `DirectDebitBatch`: DRAFT → SENT → RESULT_RECEIVED → CLOSED, 전체 거절은 REJECTED, 결과를 알 수 없으면 RESULT_UNKNOWN.
  - 예상 수납 `ExpectedPayment`: EXPECTED → PENDING_BANK_RESULT → CONFIRMED 또는 FAILED. 그 밖에 EXPIRED, CANCELLED, REVERSED가 있다.
- Payment는 CONFIRMED가 될 때 한 건만 쓴다. 이후 3자 대사로 넘어간다. REVERSED는 음수 Payment를 더한다. [가설]
- 결과가 오지 않으면 PENDING_BANK_RESULT를 자동으로 닫지 않는다. 조회로 다시 읽고, 그 줄의 출금이 없음을 제공자에게 확인한 뒤에만 사람이 닫는다. 돈이 이미 나갔을 수 있어 같은 건을 다시 보내지 않는다. 배치 전송이 시간 초과이면 실패로 적지 않고 배치를 RESULT_UNKNOWN으로 둔다. `fetchResults`로 다시 읽어 결과가 있으면 RESULT_RECEIVED로 옮기고, 접수되지 않았다는 것은 사람이 제공자에게 확인해 REJECTED로 확정한다. 이 배치는 시스템도 사람도 다시 보내지 않는다(코어 3-5). [가설] 응답 시간 초과 값, 결과 기한, 재확인 주기와 횟수는 [미정]이다.
- FAILED는 자동으로 다시 출금하지 않는다. 사람이 확인한 뒤 새 예상 수납을 만든다. [가설]
- CMS 출금 동의 증빙(서면, 녹취, ARS)은 운영사가 보관할 책임이 있어(조사 문서 6.2절) 동의 기록과 보존 정책에 연결한다. [가설]
- 금액과 성격에 따라 수납 수단을 고른다. CMS 건당 한도가 월 한도의 10% 이내라 보증금은 CMS로 받지 않는다. 출금은 은행 영업일에만 되므로 공휴일 달력을 데이터로 둔다(코어 3-5, 조사 문서 6.2절). [추정]
- 웹훅 검증과 멱등 키는 제공자마다 다르다. 토스는 이벤트별 서명 유무가 [미확인]이고, 상태 변경 웹훅에 `eventId`가 없다. `transactionKey` + `orderId` 멱등 키는 [가설]이다. [사실]
- ERP는 `LedgerExportBatch` 포트 하나로 두고 전달 방식은 어댑터로 바꾼다. 그룹 ERP 사양은 [미확인]이다.
- 규칙이 분명한 처리에 AI를 넣지 않는다. 수납 반영은 일반 프로그램이다. 자동으로 상태가 바뀌는 일(요금 변경, 출금 실패)은 입력과 규칙 버전을 남겨 설명할 수 있게 하고 사람 확인 지점을 둔다. [가설]

#### 계약 → 월 청구 → 수납: 가상 사례

[가설] 아래는 기존 코어 설계를 한 흐름으로 요약한 가상 사례다. 사업장 A의 경리 또는 본사 담당자가 호실과 입주자, 계약 당사자를 확인해 계약을 등록하고 해당 사업장의 요금표 버전을 연결한다. 사업장 B도 같은 구조를 쓰지만 요금표와 청구 일정은 사업장별로 관리한다. 실제 사업장 정책이나 금액을 확인한 사례는 아니다. 공통 구조와 버전별 규칙을 나누면 사업장 차이를 담으면서 과거 청구 근거를 추적할 수 있다.

| 단계 | 담당과 데이터 | 판단과 결과 |
|---|---|---|
| 계약 | 권한 있는 직원이 사업장·호실·입주자·계약 당사자와 요금표 버전을 확인한다 | 본인 또는 유효한 계약 대리권을 가진 사람이 서명한다. 승계·퇴거 접수와 정산은 사람이 확인한다 |
| 월 청구 | 경리가 계약과 해당 기간의 요금·이용 근거로 초안을 확인한다 | 계약에 연결된 요금표 버전과 기준일의 청구 일정 버전을 사용한다. 발행하면 금액과 납부 기한이 고정된다 |
| 수납 반영 | 납부 결과를 확인하고 경리가 불일치를 살핀다 | 예상 수납은 작업 기록이고 실제 수납 원장은 확정된 Payment다. 중복 결과는 제공자별 식별과 상태 확인으로 한 번만 반영한다 |

**판단의 연결.** [가설] 같은 가상 계약을 따라가며 세 경계를 구분한다. 계약을 체결할 때 해당 사업장의 요금표 버전을 연결해 과거 청구 근거를 추적하고, 입주 처리로 ACTIVE가 된 뒤 청구 기간을 기준으로 대상을 고른다. 월 청구 실행은 초안(DRAFT)을 만들고 경리가 검토해 발행(ISSUED)하면 금액과 납부 기한을 고정한다. 자동이체를 이용할 경우 등록된 동의를 확인하고 예상 수납을 결과 대기(PENDING_BANK_RESULT)로 둔다. 제공자의 성공 결과로 CONFIRMED가 되면 Payment를 한 번 기록하고 은행 입금은 사후에 3자 대사한다. 따라서 요청이나 결과 대기는 수납 사실이 아니다. 출금 배치의 RESULT_UNKNOWN은 예상 수납의 상태와 다른 배치 상태다(코어 3-2·3-5·9절).

**구현 시 확인할 조건.** [가설] 계약·월 조합 중복 생성 거부, 발행 전 재계산과 발행 후 정정의 차이, 사업장 범위와 보호자 동의·대리권별 허용·거부, 동일 결과 반복 수신, 결과 미확인 뒤 늦은 성공과 대사 불일치를 가상 데이터로 검증한다. 이는 향후 구현의 검증 조건이며 실행하거나 통과한 시험이 아니다. 제공자의 식별·조회·서명 규격은 별도 확인한다.

**관계.** 사업장에는 동과 호실, 요금표 버전이 있다. 계약은 한 호실과 요금표 버전을 가리키고, 입주자는 계약 당사자 행으로 계약에 연결된다. 계약과 청구 기간 조합마다 청구서는 최대 한 건이고 청구서에는 여러 청구 항목과 수납 기록이 연결된다. 계약 당사자가 여러 명일 수 있으므로 입주자와 계약을 단순한 일대일 관계로 표현하지 않는다(코어 2-2·2-3). [가설]

**열람과 행동.** 본사와 사업장 경리는 허용된 사업장 범위에서 발행·조정·수납 업무를 한다. 사업장 직원은 맡은 권한에 따라 청구 근거를 조회하고, 입주자는 본인의 청구서를 본다. 보호자에게 보여 주는 범위는 `family` 동의에 따르며, 보호자 관계 자체가 대리권은 아니다. 대리 조회와 납부에는 각각 유효한 대리 범위를 따로 확인한다. 서버가 운영사·사업장·행동·동의와 대리권을 검사하고 거부와 필요한 변경 이력을 남긴다(코어 6절). [가설]

**예외.** 발행 전 초안은 다시 계산할 수 있다. 발행 뒤에는 원래 항목을 지우거나 청구서를 취소하는 대신 다음 초안에 원래 항목을 가리키는 조정 전표를 더한다. 승계·퇴거 접수와 정산 시에는 기존 기록과 연결을 남기고 사람이 확인한다. 같은 결제 결과가 다시 와도 현재 상태를 확인해 수납을 중복 기록하지 않는다. 출금 배치 전송이 시간 초과되면 실패로 단정하거나 재전송하지 않고 결과 미확인으로 두어 제공자 조회와 대사, 사람 확인으로 처리한다. 제공자별 식별·서명 규격은 [미확인], 재확인 간격과 결과 대기 중 수동 수납·승계 정책은 [미정]이다(코어 3·9절, 확인할 것 32). [가설]

**범위.** 현재는 가상 데이터의 문서와 클릭형 프로토타입이다. 향후 1단계는 계약·청구·권한·원장과 비동기 수납 모델을 가상 데이터로 검증하는 설계안이고, 실제 운영 전 2단계에서는 외부 연동·대사, 법률 검토, 개인정보 보호와 복구·대체 절차를 갖추는 조건을 둔다. 첫 출시 범위나 일정이 확정된 것은 아니다(4.2절, 10절). [가설]

| 종류 | 하는 일 | Evenstay 위치 | 도입 |
|---|---|---|---|
| HTTP 진입 | 인증 연계, 요청 제한, 라우팅 | ALB, API 앞 | 1단계 |
| 모델 접근 | 공급자, 키, 비용, 폴백, 기록 | 모델 어댑터 → 필요 시 LiteLLM | 어댑터는 1단계, 제품은 공급자가 둘이 될 때 |
| 도구 접근 | 도구 발견과 호출 정책 | 내부 도구 등록부(ADR-G2) → 필요 시 MCP | 등록부는 `assistant` 도입 때, 외부 MCP는 읽기부터 |

게이트웨이를 설치해도 객체별 권한은 생기지 않는다. 권한은 `authorize()`가 정한다. [가설] LiteLLM은 2026-03 PyPI 악성 릴리스 사고가 있었고 CISA 악용 취약점 목록에 3건이 올라 있다(대조 F5). [사실] 쓰게 되면 버전과 해시를 고정하고 망을 격리한다. [가설]

**질문 경로.** 숫자와 상태는 원장에서, 조항은 문서에서 답한다. [가설]

| 질문 | 경로 | 까닭 | 단계 |
|---|---|---|---|
| 이번 달 청구 금액, 수납 상태 | 업무 API | 현재 원장 값이 필요하다 | 3 |
| 기간에 빈 호실 | 업무 API | 기간과 동시성 규칙이 필요하다 | 3 |
| 계약서 해지 조항 | 문서 검색(직원) | 원문과 조항 근거가 필요하다 | 3 |
| 운영 규정의 절차 | 버전과 권한을 적용한 검색 | 유효한 규정이어야 한다 | 3 |
| 계약서의 날짜, 보증금 추출 | 구조화 출력 + 사람 확인 | 검색 인덱스 없이도 된다 | 3 |
| 회원의 날짜와 청구 질문 | 의도 분류 + 도구 + 답 틀 | ADR-G1 | `assistant` 도입 뒤 |
| 건강, 금전, 계약 판단 | 직원에게 넘김 | 사람이 판단한다 | 항상 |

회원 발화를 실제 모델에 보내는 시점은 `assistant`를 도입하고 2단계 완료 기준과 3단계 시작 전 점검을 채운 뒤다. 그 전에는 녹화 응답이다. [가설]

**고지와 해당성 점검.** AI 기본법은 2026-01-22에 시행됐다. 생성형 또는 고영향 AI를 쓰는 서비스는 이용자에게 알려야 하고, 사람이 최종 결정하면 고영향에서 제외한다는 설명이 있다. 과태료는 최소 1년 계도기간을 둔다(gaps L-8). [사실] 이 서비스의 해당 여부는 법률 검토 전이다. 그래서 AI 기능 등록부(기능, 대상 이용자, 입력 데이터 분류, 최종 결정자, 고지 문구 버전)와 해당성 점검표를 둔다. 회원 대면 AI는 첫 응답과 전화 첫 안내에 고지하고, 노출 시각과 문구 버전을 저장한다. 모델이나 프롬프트를 바꾸면 점검표를 다시 본다. [가설]

**사람 대신 조회하는 권한.** 하루를 넘기는 실행에는 세션이 없다. 그렇다고 `SYSTEM:<모듈키>`로 조회하면 요청자 권한을 넘어선다. 그래서 위임 권한을 둔다. 요청자, 범위, 만료를 서버가 저장하고, 호출할 때마다 요청자의 현재 권한을 다시 평가한다. 회수되면 다음 호출부터 막힌다. [가설]

**에이전트 실행 기록.** 브라우저 연결은 출력 전달 수단이고 실행 상태가 아니다. 4단계에 아래 컬럼을 둔다. 필드 이름은 [가설]이다.

| 컬럼 | 쓰임 |
|---|---|
| `run_id` | 실행 식별자. 접근 권한이 아니다 |
| `requester_id`, `operator_id`, `site_scope`, `delegation_id` | 요청 주체, 서버가 정한 범위, 위임 권한 |
| `status` | 대기, 실행, 승인 대기, 완료, 실패, 취소 |
| `workflow_version`, `prompt_version`, `model_id` | 재현과 원인 분석 |
| `input_ref`, `document_version` | 쓴 자료와 근거 |
| `approval_payload_hash`, `target_version` | 승인 대상과 변경 충돌 확인 |
| `step_attempt`, `idempotency_key` | 재실행과 중복 효과 통제 |
| `cost`, `usage`, `deadline` | 비용과 시간 한도 |
| `event_cursor` | 화면 재연결 |

**승인.** 승인 범위는 "이 에이전트의 모든 행동"이 아니라 특정 명령과 입력값이다. 담당자의 승인은 기록만 하고, 실행은 승인 ID가 있어야 한다. `assistant`의 명령이 승인 ID를 받아, 한 트랜잭션 안에서 요청자의 현재 권한, 대상의 최신 버전, 승인한 금액, 행위, 대상을 다시 확인하고 `target_version` 조건부 갱신으로 승인을 사용 처리한 뒤 코어 명령까지 실행한다. 코어는 승인 내용을 모르고 불투명한 참조만 받아 기록한다. 비서의 확인 토큰(ADR-G3)과 같은 방식이다. 그래서 승인 뒤 버전이 바뀌면 실행이 거절되고, 승인 없이 같은 명령을 낼 수 없다. [가설]

**체크포인트는 중복을 막아 주지 않는다.** 재개할 때 노드가 처음부터 다시 실행된다(대조 12번). [사실] 외부 효과 앞에 지속 저장한 멱등 키, DB 유일성 제약, 외부 제공자의 멱등 기능을 둔다. 응답을 못 받았으면 조회와 대사로 넘긴다. [가설]

**재시도 한도.** 작업자, 에이전트, 게이트웨이가 3번씩 시도하면 하위 호출이 최대 27번이다. 재시도 권한은 한 층에만 둔다(6.11절). 다른 층은 재시도하지 않거나 한 번으로 둔다. 총 시간, 총 토큰, 총 시도 수 한도는 실행 기록에 둔다. [가설]

**도구는 좁게 만든다.** 조회 도구와 제안 도구까지 둔다. 범용 SQL, 임의 URL, 넓은 관리자 토큰은 주지 않는다. 입출력 스키마는 형식만 검사한다. [가설]

**입력 마스킹과 폴백.** Guardrails PII 필터에는 주민등록번호 유형이 없고 도구 인자와 결과를 보지 않으므로(조사 문서 6.7절) 마스킹은 앱 계층이 먼저 한다. 평가를 통과한 경로만 자동 폴백으로 둔다. 서울 안 처리로 제한한 데이터를 장애를 이유로 global 경로에 보내지 않는다. 모델 ID 접두사(`global.`)를 코드와 IAM 정책에서 막는다. 서울 안 경로가 멈추면 폴백 없이 직원이 수동으로 처리한다. [가설]

### 6.4 문서 파이프라인

원본, 문서 ID, 버전 → 파싱, 필요하면 OCR → 구조와 쪽을 보존한 청크 → 임베딩·인덱스 → 검증·활성 버전 전환 → 권한을 적용한 검색. [가설]

- 시작은 S3 + 작업 상태 테이블 + 큐 + 작업자다. Dagster는 원천이 셋을 넘거나 백필이 운영 문제가 될 때 검토한다.
- 재처리는 새 버전을 만들어 검증한 뒤 활성 버전을 바꾼다. 일부 청크만 활성화되지 않게 한다.
- 보호자 공유 허락 철회는 해당 보호자의 조회와 예정 발송을 차단하고 관련 캐시를 무효화한다. 한 보호자의 철회만으로 직원이나 다른 보호자에게 필요한 원본을 삭제하지 않는다. 모델 투입 동의 철회는 새 투입과 대기 작업을 막고 파생물 처리는 별도 정책으로 정한다. 원본 처리 근거 소멸이나 보존 기간 만료에 따른 파기는 법적 보존 의무를 확인하고 원본, 인덱스, 파생 요약, 아웃박스 본문, 작업 인자와 체크포인트에 정책별로 전파해 저장소별 완료를 추적한다.
- 파서, 청커, 임베딩 모델 버전을 컬럼으로 둔다.
- 올린 파일은 악성코드 검사를 지난 뒤 파싱한다. 파싱한 문서는 신뢰하지 않는 입력이다. 권한 밖 자료를 모델에 넣고 출력에서 가리는 방식은 쓰지 않는다.
- 원장 값과 수납 기록은 임베딩하지 않는다. 계약서 본문은 검색해야 하므로 넣되, 이름과 계좌 같은 개인정보는 청크에서 가리고 금액은 원문 쪽 번호로 찾아 사람이 확인한다.

### 6.5 데이터베이스

**확장 순서.** 스키마, 쿼리, 인덱스 → 트랜잭션 → 연결과 동시성 → 수직 확장 → 읽기 분산 → 부하 분리 → 파티셔닝 → 샤딩. 사업장 수나 행 수의 고정 기준은 두지 않는다. [가설]

**사업장 범위.** 격리 경계는 운영사이고 사업장은 범위 축이다. 서버가 주체와 역할에서 `operator_id`, 허용 `site_id` 배열, 주체 ID를 정해 트랜잭션 안 세션 문맥에 넣는다. 모든 행은 운영사 일치를 확인하고 사업장에 속한 행은 사업장 포함 조건도 확인한다. 운영사 문맥이 없으면 거부한다. 시스템 작업도 운영사 범위에서 사업장을 열거하고 사업장마다 `runAs`로 처리한다. 연결 풀 재사용 때 이전 문맥이 남지 않게 한다. 아웃박스에 `site_id`와 `actor_id`를 저장해 재처리 때도 같은 범위를 쓴다. 사업장을 넘는 집계는 읽기 전용 역할과 뷰로 한다. 모듈별 DB 역할은 역할별 연결과 `SET ROLE` 중에서 M1에 정한다(코어 확인할 것 35, 조사 문서 5절). [가설]

**소유주 범위.** 소유주는 읽기와 집계 이용자이고 데이터 생산자가 아니다. 입주자 개인정보가 아니라 집계와 명세서만 준다. 소유주는 정보주체가 아니어서 집계 제공이 개인정보 제공에 해당하는지는 법률 검토 사항이다. `site_ownership`은 기간 겹침을 막고, 소유가 바뀌면 명세서는 그 시점의 소유 관계로 계산한다. 설치자(소유)와 위탁운영자는 따로 둔다(코어 `ManagementContract`). [가설]

**DB 연결 한도.** 합계 = (API 최대 개수 + 배포 겹침) × API 풀 + (작업자 최대 개수 + 배포 겹침) × 작업자 풀 + JobRunr, 폴러, 배치, 마이그레이션 여유. 모듈별 DB 역할을 연결로 나누면 역할 수만큼 곱해진다. 자동 확장 상한은 이 합계와 모델, ERP 한도에서 정한다. 지금 단계에는 풀러가 없고 앱 풀만 쓴다. RDS Proxy나 PgBouncer를 도입하면 RLS 변수 주입이 고정(pinning)을 일으키는지 그때 실측한다. [가설]

**읽기 복제본에 보내지 않는 조회.** [가설]
- 결제 직후 잔액과 중복 수납 판단
- 계약 확정과 호실 배정
- 권한 회수 확인
- 승인 대상이 그대로인지 확인
- 보호자 허락 철회 확인(그만 보여 주기는 바로 반영돼야 한다)
- 안심 알림의 넘김 판단

**파티션 함정.** 파티션 테이블의 유일성 제약에는 파티션 키가 들어가야 한다. 날짜로 나눈 표에서 `event_id` 단독 유일성을 선언할 수 없고, 날짜를 넣으면 날짜가 다른 같은 이벤트를 막지 못한다. [사실] `SignalEvent`, 아웃박스, 변경 이력을 나눌 때는 별도 중복 방지 테이블을 먼저 정한다. [가설]

**복구.** HA, 읽기 복제본, PITR, 복원 훈련은 푸는 문제가 다르다. Multi-AZ가 곧 읽기 분산은 아니고, PITR이 외부 시스템까지 같은 시점으로 되돌려 주지는 않는다. 복원 뒤에는 결제와 ERP를 대사하고, 복원 시점 이후의 동의 철회와 삭제를 목적과 보존 정책에 맞게 다시 적용한다. 철회와 삭제 이벤트는 복원 범위 밖의 별도 기록으로 남기고, 재적용과 검증이 끝날 때까지 관련 보호자 조회와 발송을 열지 않는다. [가설]

**리전 장애.** 서울 밖 한국 리전은 찾지 못했다(조사 문서 8절). 그래서 리전 전체 장애를 막지 못한다. 이때 이 시스템은 멈출 수 있고, 호출은 건물 안에서 계속되며, 직원은 대체 절차로 운영한다. 서울 밖 백업은 국외 보관이 될 수 있어 법률 검토 전에는 두지 않는다. 복원 훈련은 별도 계정의 백업 볼트에서 한다. [가설]

### 6.6 데이터 위치

DB를 서울에 뒀다고 전 경로가 서울인 것은 아니다. 아래 경로마다 위치를 따로 확인한다. 법적 허용 여부와 기술 지원은 다른 문제이고, 법적 결론은 이 문서에서 내리지 않는다. [사실]

| 경로 | A안 기본 | 확인할 것 |
|---|---|---|
| 업무 DB, 객체 저장소 | 서울 | 백업 복사 지역. 서울 밖이면 국외 보관 검토 |
| 모델 추론 | Bedrock 서울, Sonnet 5 | Opus 5·Sonnet 5는 리전 안 처리가 된다. Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5·5.1은 서울에서 global 추론만 된다(대조 10b, F3 재확인, 조회 2026-11-05). 최신 세대를 쓰면 처리 위치가 서울 밖이 될 수 있다 |
| 가드레일 | 미사용 기본 | 한국어는 Standard 등급만 되고 Standard는 교차 리전 처리다(대조 F3). 서울 안 처리가 조건이면 쓰지 않는다 |
| 임베딩 | 3단계에 결정 | 서울 안 처리는 Titan Text Embeddings V2다. Cohere Embed v4는 서울에서 global만 된다(대조 F3) |
| 재순위화 | 쓰지 않는 것이 기본 | Bedrock 재순위화 모델은 서울에 없다(대조 F3). 쓰면 처리 위치가 서울 밖이다 |
| OCR | 3단계에 결정 | 공급자의 처리 위치 |
| 로그, 추적 | 서울 | 프롬프트 원문은 마스킹, 샘플링, 보존 기간을 정한다 |
| 알림, 결제, 전자서명 | 2단계에 결정 | 수탁자로 대장에 올린다 |
| 외부 관측 도구 | 5단계 | SaaS 지역과 자체 호스팅 운영 부담 |

**위탁·이전 대장.** 수탁자, 업무, 항목, 처리 위치, 이전 근거, 재위탁 여부를 코드가 읽는 설정 파일로 둔다. 처리방침 게시 문안을 여기서 만들고, 대장에 없는 경로로 나가는 배포를 막는다. `global.` 차단과 같은 위치에 둔다. 국외 이전 요건은 개인정보위 안내를 따른다(gaps L-4). [가설]

### 6.7 캐시, 관측, 평가, 테스트

**캐시.** Valkey는 Next.js를 2개 이상 띄우거나 Taskiq를 쓸 때 더한다. 회원·보호자·청구·권한 응답은 공유 캐시에서 제외하는 것이 기본이다. 캐시를 쓰는 자료에는 사업장, 권한 버전, 데이터 버전을 반영하고, 결제와 계약 확정 전에는 원장으로 다시 확인한다. 다중 화면 인스턴스는 동일 빌드, 배포 버전 구분, 캐시 핸들러와 무효화 전파를 정한다. Server Actions를 쓴다면 인스턴스 간 암호화 키도 관리한다. 전체 장애나 빈 캐시에서 DB를 지키는 동작을 테스트한다. 체크포인트와 승인 기록은 캐시에 두지 않는다. Valkey는 강한 일관성을 주지 않는다(대조 14번). [가설]

**관측.** 구조화 로그, 지표, 추적을 쓰고 업무 요청과 비동기 실행을 하나의 추적으로 잇는다. AI는 `run_id`, 모델, 프롬프트 버전, 근거 문서, 도구 결과, 토큰, 비용, 승인 결과를 남긴다. 큐는 길이보다 가장 오래된 작업의 대기 시간을 본다. [가설]

**평가.** 답변 정확성, 근거, 최신성, 권한, 도구 선택, 실행 정확성, 복구, 비용을 축으로 둔다. 금액, 권한, 중복 수납은 채점 모델이 아니라 코드와 실제 데이터로 검증한다. 모델과 프롬프트를 바꾸면 평가 뒤 일부에 먼저 적용한다. [가설]

**테스트.** 단계마다 돌릴 테스트를 정한다. [가설]

| 단계 | 테스트 |
|---|---|
| 1 | 운영사·사업장 격리와 연결 풀 문맥 누수(API와 작업자), 이벤트 중복·순서 역전·소비자별 재시도·시간 초과, 사업장별 작업 실패 격리, 카드 번호 패턴 검사, 복원 |
| 2 | 알림 전달 실패와 늦은 신호 상태 대조, 월 청구 중 넘김 지연, 하트비트 끊김, 침해 범위 산출, 복원 뒤 철회 재적용, 대체 절차 훈련. CMS 사용 시 결과 대기와 수동 수납·건별 결제·승계, 늦은 성공과 승계 뒤 되돌림 조합 |
| 3 | 평가 세트 회귀, 권한 밖 문서 차단, 폐기 규정 차단 |
| 4 | 재시작, 중복, 승인 뒤 권한 변경, 문서 안 지시문 |

### 6.8 개인정보, 동의, 대리 권한

단계별로 흩어진 요구를 여기 모은다. 원문 요약은 `arch-multisite-rbac-privacy.md`이고, 법령 근거는 `arch-review-gaps-2026-11-05.md`의 L 항목이다. 모두 법률 검토가 필요하다. [가설]

**주체 유형과 인증.** 표의 방식은 후보이고 제품은 M2까지 정한다. M1에는 유형 구분만 있으면 된다. [가설]

| 주체 | 로그인 | 강한 인증 | 앱 밖 경로 |
|---|---|---|---|
| 입주자 | 소셜 또는 전화번호 인증 | 금전·동의 변경 때 재인증 | 전화, 프런트, 직원 대행 |
| 보호자 | 소셜 또는 전화번호 인증 | 건강 소식 첫 열람 | 전화, 문자 |
| 대리인, 후견인, 신원인수인 | 보호자와 같음 | 권한 근거 문서 확인 | 직원 대행 |
| 직원 | 사내 SSO | 외부 접속 때 필수 | 해당 없음 |
| 소유주 이용자 | 전용 계정 | 필수 | 해당 없음 |
| 파트너, 시스템, 에이전트 | 토큰, `SYSTEM:<모듈키>`, 위임 권한 | 범위와 만료 필수 | 해당 없음 |

**데이터 분류와 암호화.** M0 산출물이다. 컬럼마다 분류(일반, 민감, 고유식별, 금융, 신호 원본), 암호화 여부, 보존 기간, 모델 투입 가능 여부를 적는다. 건강, 돌봄, 호출, 재실, 출입 신호는 개인정보이고 건강정보로 해석되면 민감정보다. 민감 컬럼은 동의 근거가 비면 저장되지 않게 한다. 암호화 컨텍스트에는 개인정보를 넣지 않는다. [가설]

**동의.** 목적(정보성, 광고성, 보호자 공유, 건강정보 처리, 모델 투입), 범위, 방식(서면, 전자, 구두와 직원 입회), 증빙, 유효기간, 철회 이력을 기록한다. 목적별 철회 효과와 원본 보존·파기는 6.4절에 따르고 철회 확인은 6.5절의 원본 조회로 한다. 건강 소식이 보호자에게 가는 경로는 `family` 하나이고 `authorize()` 정책으로 강제한다. [가설]

**대리와 긴급 열람.** 위임장 대리인, 후견인, 신원인수인은 보호자와 다른 역할로 둔다. 대리 서명은 서명 방식 합의, 서명자 식별, 대리 근거 문서, 문서 해시를 남긴다. 효력은 근거를 못 찾았다. [미확인] 긴급 열람은 사유, 승인자, 만료, 사후 통지를 둔다. 상시 관리자 권한은 두지 않는다. [가설]

**접속기록.** 대상은 직원만이 아니라 보호자, 소유주 이용자, 파트너 토큰, 시스템 주체, 에이전트 실행까지다. 고시가 "접속한 자(정보주체 제외)"로 넓어졌다는 해설이 있기 때문이다(gaps L-1). 보관은 2년을 하한으로, 점검 주기는 설정값으로 두고 기본은 월 1회다. 어느 해석에서도 안전한 쪽이다. 내보내기에는 사유와 건수를 남기고, 대량 조회 이상 탐지 규칙을 둔다. 기록에는 평문 개인정보를 넣지 않고, 파기 의무와 Object Lock 보존이 충돌하지 않게 한다. 현행 고시 본문은 읽지 못했다. [미확인]

**보존과 파기.** 분류, 근거, 기간, 파기 방식을 담은 보존 정책 테이블과 파기 배치를 둔다. 법정 장부(운영일지, 입소자 관리카드, 총계정원장, 보증금 장부)는 분리 저장한다. 키 폐기를 복원 불가 파기로 볼 수 있는지는 법률 검토 사항이라 키 폐기와 원본 삭제를 모두 지원한다. 사업장 단위 반출과 파기도 가능해야 한다. [가설]

### 6.10 장애와 사고 대응

- **등급.** 안전 경로(2차 알림 누락) > 청구·수납 > 그 밖. 시간 수치는 정하지 않는다. [가설]
- **접수.** 접수자와 대체자를 정하고, 앱 밖 두 갈래로 받는다. 사업장 공지 문안과 사후 검토 한 장을 둔다. 온콜 도구는 [미정]이다. [가설]
- **침해 사고.** 유출이 의심되면 어느 사업장, 입주자, 항목이 영향을 받는지 접속기록과 데이터 분류로 산출하고, 통지 명단, 문안, 이력을 만든다. 통지 기한은 시행령 원문 확인 전이다. [미확인]
- **교대 인계.** 야간과 교대 때 "확인되지 않은 알림 목록과 대체 절차 상태"를 넘기는 화면과 절차를 둔다. 한국 교대 관행은 근거가 없다. [미확인]
- **비밀과 키.** 종류별로 소유자, 순환 주기, 유출 시 폐기 절차를 표로 둔다. 어댑터 서명 키, 웹훅 비밀, 파트너 토큰이 대상이다. 블라인드 인덱스 키를 바꾸면 재색인이 필요해 키 ID를 컬럼으로 둔다. [가설]
- **비용 경보.** 2단계에 계정별 월 예산 경보, 3단계에 모델 호출 비용 상한을 둔다. [가설]

### 6.11 비동기 처리와 소유 모듈

**역할 구분.** 저장, 전달, 재시도를 하는 장치가 겹치면 재시도가 곱해진다. 역할을 하나씩만 준다. 단계별 제안의 "Modulith 이벤트 기록"은 쓰지 않는 쪽으로 바꿨다. [가설]

| 일 | 담당 | 재시도 권한 | 비고 |
|---|---|---|---|
| 모듈 사이 이벤트, 외부 전달 | 소유 모듈별 아웃박스 + 공통 디스패처 | 아웃박스 `attempts` 한 곳 | 각 모듈 스키마에 상태 변경과 같은 트랜잭션으로 쓰고 `platform` 구현을 공유한다. 어댑터는 재시도하지 않는다 |
| 지연·반복 작업(월 청구, 일일 배치) | JobRunr | JobRunr 재시도 | 무료판의 트랜잭션 참여는 확인 못 했다. 업무 상태에 묶이는 작업은 아웃박스 이벤트로 등록한다 |
| 소비자 멱등 | 모듈별 처리 완료 테이블 | 해당 없음 | 이벤트 ID로 확인 |
| 넘김 타이머 | `safety` 전용 스레드와 연결 풀 | 코어 재시도와 분리 | 8절 기준을 넘으면 전담 작업자 |
| Modulith | 모듈 경계 검사와 문서화 | 해당 없음 | 이벤트 기록은 쓰지 않는다 |

JobRunr 무료판은 반복 작업이 100개까지이고, 9.0은 하위 호환이 깨지는 메이저 변경이 있었다(대조 F2). [사실] 그래서 사업장별 반복 작업을 만들지 않고, 작업 하나가 사업장을 돌며 `runAs`로 처리한다. 한 사업장의 실패는 기록하고 나머지는 계속하며 실패한 사업장만 재시도한다. 업무 명령은 사업장과 기간에 맞는 멱등 키를 쓴다. 상태 스냅샷 이벤트는 해당 출처 revision을 비교하고 정본 조회가 필요한 이벤트는 소유 모듈 API를 다시 읽는다. 소비자 하나의 실패를 다른 소비자의 완료와 구분해 재시도한다. [가설]

**소유 모듈.** 코어는 어떤 모듈도 모른다는 ADR-2를 지킨다. [가설]

| 구성요소 | 소유 | 저장 | 비고 |
|---|---|---|---|

| 마일스톤 | 시작 조건 | 작업 순서 | 완료 기준 | 되돌리기 조건 | 결정 사항 |

| 운영과 관측 | CI/CD, 로그 | OpenTelemetry, IaC, 장애 대응 | 비용 계측 | 실행 추적 | Langfuse, EKS |
| 현장 전환 | 없음 | 대체 절차 훈련, 사업장 1곳 전환 | 없음 | 없음 | 사업장 확대 |

### 10.3 모듈 도입 순서

코어는 어떤 모듈도 모르므로 순서를 바꿔도 코어를 다시 작성하지 않는다. 이 순서는 의존 관계와 시연 흐름에서 도출한 제안이다. 실제 데이터는 어느 모듈이든 M2 완료 뒤에 받는다. [가설]

| 순서 | 모듈 | 마일스톤 | 까닭 |
|---|---|---|---|
| 1 | `family` | M1 끝 | 보호자 관계에 동의를 더한다. 건강 소식을 전달하는 경로가 먼저 있어야 한다 |
| 2 | `safety` | M2 | 수신 어댑터, 규칙, 당번, 2차 알림. 호출 경로와 분리해 도입한다 |
| 3 | `requests` | M2 뒤 | 유료 요청이 코어 청구로 연결되는 첫 지점이다 |
| 4 | `community` | M2 뒤 | 다른 모듈에 주는 영향이 가장 적다. `requests`와 함께 진행할 수 있다 |
| 5 | `transitions` | M2 뒤 | 사람의 결정 흐름이 길어 앞선 모듈이 자리 잡은 뒤 도입한다 |
| 6 | `assistant` | M3 평가 세트 뒤 | 코어와 모듈의 조회 API가 있어야 답할 수 있다. 도구 등록부도 이때 만든다 |
| 7 | `documents` | M3 | 3단계에 새로 둔다 |

### 10.4 구성안 변경 시점

안을 바꾸는 비용은 M1을 지날수록 커진다. 코어 코드가 쌓이기 전인 M0이 비용이 가장 낮고, C안은 M2 전에 A안이나 B안으로 옮긴다. M2 뒤에 안을 바꾸려면 실제 데이터 이전과 복구 절차까지 다시 테스트해야 한다. [가설]

### 10.6 현장 전환

기존 장부를 쓰는 사업장으로 옮길 때의 순서다. 인력 수와 기간은 정하지 않는다. [가설]

1. 개시 데이터: 입주자, 계약, 보증금 개시 잔액(조정 전표 형식), 기존 서면 동의의 증빙 연결, 보증보험 상태를 적재한다.
2. 범위: 한 사업장부터 시작해 사업장 단위로 넓힌다. 건물 설비와 어댑터가 사업장마다 다르다. 사업장별로 기능을 켠다.
3. 안심: 읽기 전용 사본 → 직원 화면 → 2차 알림 켜기 순서로 간다. 호출은 건물 안에서 자립하므로 되돌리기 쉽다. 켜기 전에 대체 절차 훈련을 끝낸다.
4. 청구: 월 마감 경계에서 전환하고, 한 번의 마감을 두 방식으로 돌려 대사한다.
5. 사람: 야간과 교대 인계, 입주자와 보호자 대면 안내, 앱 밖 경로 안내를 전환 조건에 넣는다.
