# Red-Team: Evenstay 포트폴리오 전략 ([지원 회사] Tech Lead / Senior Backend 지원)

작성: 2026-11-03 · 허브 · 방법: `strategy-red-team` 스킬(Skill 도구 호출) · 상태: 초안
함께 볼 것: `PreMortem-evenstay-mvp-expanded-2026-11-03.md`

**한 줄 계획**: 시니어 레지던스 운영을 코어(계약·청구) + 모듈 5개 모듈형 모놀리스로 설계하고, 사람이 판단하고 시스템은 사실만 보이게 만든 MVP와 소개 사이트로 Tech Lead 역량을 증명한다.

## Top Kill-Assumptions (ranked: 영향 × 틀릴 가능성 × 확인 비용의 낮음)

### 1. "기획 문서와 화면의 폭이 Tech Lead 역량을 보여 준다"
- **Steelman**: 공고는 "비개발 요구사항의 기술화"를 요구하고, 리서치 → PRD → 아키텍처 흐름 자체를 증명 수단으로 적었다(`shared/target-companies.md` 기술 역량 표 마지막 줄) [사실]. 6개 모듈의 경계·이벤트·권한 설계는 PMS 0→1에 필요한 판단을 보여 준다.
- **Fails if**: 면접관이 "돌아가는 코드, 테스트, CI, 관측"으로 백엔드 깊이를 재는데, 면접 날 보여 줄 것이 문서와 HTML 목업뿐이다. 공고 표에는 Cloud·CI/CD·모니터링, 연동의 멱등성·재시도가 따로 있다 [사실]. 지금 코드는 0줄이고, Must 화면 66개가 구현 시간을 화면 만들기로 끌어간다 [사실: `mvp-screens.md` 6-1].
- **Evidence to get this week**: 코어 한 줄기(계약 → 마감 → 청구 → 아웃박스 → 소비자 1개)를 실제로 만드는 데 며칠이 걸리는지 잰다.
- **Kill criterion**: 그 한 줄기가 테스트·CI 포함 4일을 넘으면, 화면 수가 아니라 "깊은 줄기 2~3개 + 나머지는 목업"으로 데모 전략을 바꾼다.
- **Cheapest test**: `sprint-plan`으로 첫 주를 코어 줄기 하나에 배정하고 1주차 끝에 실제 진척을 본다.

### 2. "시니어·보호자 기능이 회사의 핵심 문제다"
- **Steelman**: 회사 사업목적에 라이프케어(건강관리, 문화·여가)가 있고, 시니어 효용과 운영 효율을 함께 보이라고 정리했다(`target-companies.md` 내 MVP와 연결할 지점) [사실].
- **Fails if**: 회사의 돈은 **소유주(펀드)를 대신한 위탁 운영 수수료**에서 나오고, 운영 KPI가 곧 영업 자료인데(`target-companies.md` 사업 모델, 추정 과제 2) [사실·추정], 포트폴리오에서 소유주 월 리포트는 로드맵에만 있고(`docs/core/roadmap.md` 40행 I-25) 운영 수수료 계산은 어디에도 없다 [사실: 문서 검색 0건]. 면접관이 "우리 고객은 소유주인데?"라고 물으면 답이 약하다.
- **Evidence to get this week**: 공고·기사(S2·S6)에서 소유주 리포팅·정산 언급을 다시 읽고, 코어 CORE-09 소유주 현황이 그 질문에 얼마나 답하는지 본다.
- **Kill criterion**: 소유주 관점 화면이 데모 22단계 중 1단계(코어 5)뿐이면 부족하다고 본다.
- **Cheapest test**: 운영 현황 대시보드 카드를 소유주 월 리포트(입주율, 청구·수납 합계, 안전 신호 처리 시간, 생활 요청 처리)로 한 장 더 묶을 수 있는지 코어 기획에 물어본다. 새 데이터 없이 같은 조회로 된다면 비용이 거의 없다 [추정].

### 3. "안전·건강 보완이 시니어 하우징다움을 높인다"
- **Steelman**: 사용자가 직접 짚은 빈 곳이고, 호출벨 응답·안부 확인은 시니어 하우징의 기본 기대다(`service-coverage-review.md` S21) [사실].
- **Fails if**: 회사가 겨냥하는 대상은 **건강한 액티브 시니어**이고 의료·간병 중심 요양시설과 차별화한다(`target-companies.md` 첫 프로젝트) [사실]. 소개 사이트와 데모가 출동·병원 동행·안부 방문을 앞에 세우면 "요양시설처럼 보인다"는 인상을 줄 수 있다.
- **Evidence to get this week**: 소개 사이트 계획에서 안전·건강 섹션과 생활·여가·식사 섹션의 비중, 히어로 메시지를 센다.
- **Kill criterion**: 메인 랜딩 첫 세 섹션 중 둘 이상이 안전·건강이면 순서를 바꾼다.
- **Cheapest test**: 랜딩 기획 세션에 섹션 순서와 메시지 비중만 다시 보게 한다(문서 수정 30분 안팎 [추정]).

### 4. "가상 시설 소개 사이트가 포트폴리오 가치를 더한다"
- **Steelman**: 브랜드·화면·문구를 한 줄로 보여 주는 첫인상이고, 사용자가 원한다.
- **Fails if**: 지원 직무는 백엔드 리드이고 회사는 4명 규모 초기 조직이다 [사실]. 에셋 68개 생성과 40화면 안팎의 사이트가 앱 데모보다 먼저 시간과 비용을 쓰면 1번 위험을 키운다. 또 가상 센터장·직원·시설이 실제처럼 보이면 신뢰를 잃는다.
- **Evidence to get this week**: 사이트가 증명하려는 것을 한 문장으로 정한다(예: "제품이 운영 현장과 회원 경험을 어떻게 잇는지").
- **Kill criterion**: 그 문장을 앱 데모가 이미 증명한다면 사이트는 메인 1장 + 소개·시설·식사 3장으로 줄이고 에셋을 키 이미지 세트 + 15장 안팎으로 줄인다.
- **Cheapest test**: 키 이미지 세트(약 10장)만 먼저 만들고 메인 1장 프로토타입으로 반응을 본 뒤 나머지를 정한다(이미 계획된 순서와 같다).

## What's Well-Reasoned
- **사람이 판단하고 시스템은 사실만**: 의료·응급·금전·단계 판단을 사람에게 두고, 판단 단어를 화면에서 막고, 진단·치료를 기능으로 만들지 않은 결정은 법·윤리·책임 경계가 분명하다. 면접에서 강점이다.
- **모듈 경계 규칙**: 다른 모듈 데이터 사본 금지, 아웃박스·멱등, 단일 `authorize()`. 오늘 B·D가 부재 데이터를 저장하지 않기로 한 결정도 이 규칙을 지켰다. 공고의 연동·RBAC·감사 요구와 바로 이어진다.
- **멀티 사이트·소유주 격리**: 코어 데모 5단계(소유주 격리)는 공고의 Multi-site 요구에 직접 답한다.
- **사실 태그와 [미정] 드러내기**: 지어낸 수치가 없다는 점은 면접에서 신뢰를 준다.

## What I Couldn't Assess
- 면접 형식(코드 리뷰, 라이브 데모, 설계 토론 중 무엇인지)과 일정. 상시채용이라 마감은 없다 [사실].
- 회사가 실제로 먼저 적용할 자산(임대주택 등)이 무엇인지 [미확인].
- AI 생성 이미지·영상의 품질과 실제 생성 비용.

## 이번 주에 할 일 (요약)
1. `sprint-plan`으로 첫 주를 코어 줄기 하나(계약 → 청구 → 아웃박스)에 배정하고 실제 속도를 잰다.
2. 운영 현황 대시보드 카드를 소유주 월 리포트로 묶을 수 있는지 코어 기획에 확인한다.
3. 소개 사이트 메인 섹션 순서를 액티브 시니어 생활 먼저, 안전은 뒤로 다시 본다.
4. 소개 사이트는 키 이미지 세트와 메인 1장부터 만들고 나머지 규모는 그 뒤에 정한다.
