## 1. 한 줄 정의
**시니어 회원이 말 한마디나 큰 버튼 하나로 하루 일정, 시설 요청, 케어 소식, 돈 문제를 처리하고, 판단이 필요한 일은 사람(직원, 보호자, 전문가)에게 이어 주는 AI 비서.**

코어 + 모듈 구조에서 G는 **새 데이터를 만드는 모듈이 아니라, 다른 모듈을 하나의 창구로 묶는 앞단**이다. 에이전트는 각 모듈이 공개한 API를 도구로 호출한다. 공고의 "AI Agent 연동"(S2, S3)을 가장 직접 보여주는 모듈이다.

```
 시니어 회원 앱(큰 글씨) · 음성/전화 · 보호자 앱
                │
        G. AI 생활 비서 (대화 → 의도 → 도구 호출 → 확인 → 실행/인계)
                │  모든 호출은 회원 본인 권한 또는 대리권(I-30) 안에서만
   ┌───────────┬───────────┬───────────┬───────────┬──────────────┐
 일정·요청      돈(청구)     케어 소식    보호자 연결    자산 이해(선택)
 A·요청 큐     A 청구 원장   B 이상 신호   D 동의 포털    본인이 연결한
 시설 예약     I-29 명세 설명 C 단계 전환   I-31 금전 경계  증권 계좌(조회 전용)
```

## 2. 가치 제안 (`value-proposition` 6단계)
- **Who**: 앱 사용이 어려운 70~80대 입주 회원(U1)과 그 보호자(U3), 그리고 요청을 받는 현장 직원(U4).
- **Why**: 일정(병원, 복약, 프로그램, 가족 행사), 시설 요청, 청구, 케어 소식이 서로 다른 곳에 있다.
  - 디지털 적응이 어렵다는 응답이 67.2%다(P-037. D3, D5).
  - 진료·복약 정보가 흩어져 있다(P-024, P-027).
  - 보호자는 여러 곳에서 따로 확인한다(P-023).
- **What before**: 프런트에 전화하거나 직접 찾아간다. 자녀에게 묻거나 종이 달력에 쓴다. AI 안부전화(케어콜 등)는 안부 확인만 하고 시설 업무와 연결되지 않는다(E7, E15).
- **How**
  - 회원이 말하거나 버튼을 누르면 에이전트가 의도를 파악한다.
  - PMS 모듈 API(일정, 요청 큐, 청구 명세, 케어 이벤트, 보호자 동의)를 호출한다.
  - **실행 전에 확인을 받는다**(무엇을 언제 할지 다시 말해 줌).
  - 결정이 필요한 일(건강 판단, 금전 대행, 계약 변경)은 직원이나 보호자에게 넘긴다.
  - 모든 대화와 도구 호출을 감사 로그로 남긴다.
- **What after**: 회원은 창구 하나로 하루를 챙긴다. 직원은 반복 전화 대신 정리된 요청을 받는다. 보호자는 동의 범위 안에서 같은 정보를 본다.
- **Alternatives**: 프런트 직원, 자녀, AI 안부전화·돌봄 스피커(시설 업무 비연동), 범용 AI 비서(시설 데이터·권한 없음). 그리고 **비소비(그냥 참고 넘김)**.
- **가치 제안 문장**: *말 한마디로 오늘 일정과 시설 요청, 청구와 케어 소식을 챙기고, 판단이 필요한 일은 믿을 수 있는 사람에게 이어 주는 비서.*

## 3. 비서가 하는 일과 하지 않는 일
| 영역 | 하는 일 | 하지 않는 일 (사람에게 인계) | 연결 모듈 |
|---|---|---|---|
| 일정 | 병원·복약·프로그램·셔틀·가족 방문 일정 조회와 알림, 일정 등록 | 진료 판단, 복약 변경 | A(시설 일정), 외부 일정은 회원 입력 |
| 시설 요청 | 청소·수리·식사 변경·동행 요청 접수, 진행 상황 안내 | 요청 우선순위 판단(직원) | 요청 큐(I-05), 시설 예약 |
| 돈(청구) | 이번 달 청구를 쉬운 말로 설명, 항목 근거 보여주기, 이의 제기 접수 | 금액 조정 결정(경리), 이체 대행 | A 청구 원장, I-29 |
| 케어 소식 | 내 단계와 다음 단계 조건 설명, 이상 신호 처리 결과 안내 | 응급 판단, 단계 판정 | B, C |
| 보호자 | 동의한 보호자에게 요약 전달, 보호자 질문에 동의 범위 안에서 답 | 동의 범위 밖 정보 제공 | D, I-30 대리권 |
| 금융 안전 | 의심 연락을 받았을 때 직원·보호자 확인 요청 연결 | 금융 판단, 송금 | I-28, I-31 |

## 4. 사용자가 구상한 AI 자산관리 비서를 어디까지 넣을 수 있나
원래 구상은 범용 서비스다. 수입·지출과 목표로 소비 습관과 저축 계획을 점검하고, 경제·투자 상식을 눈높이에 맞게 설명한다. 증권사 API로 계좌 잔고, 보유 종목, 거래 내역, 시세를 연결하고, 목표·위험 허용 범위·거래 한도 안에서 자동매매까지 간다. 계좌 조회와 분석부터 만들고 자동투자는 모의투자로 검증한다.

### 확인한 사실
- Namuh PLUG는 2026-08-10에 출시됐다. 고객이 직접 개발한 프로그램을 연결해 시세, 잔고, 주문을 처리한다(F26).
- 공식 SDK는 모의투자 서버(`moapi.nhplug.com`)를 제공하고, 주문은 모의투자에서 먼저 검증하라고 안내한다. 인증은 계좌 소유자의 앱키·앱시크릿이다(F27).
- 본인 계좌·본인 자금·본인 규칙의 자동매매는 개인 매매 자동화이고, 타인 자금 운용은 투자일임 영역이라는 해설이 있다(F28. 블로그 해설이라 법적 해석은 아님).
- 투자 판단 자문은 등록이 필요하고(F17), 금융회사 정보를 모아 본인에게 보여주는 업은 마이데이터 허가가 필요하다(F16).

### 단계별 판정
| 단계 | 내용 | 일반인용 개인 프로젝트 | 시니어하우징 포트폴리오(G에 넣기) |
|---|---|---|---|
| L1 | 본인 계좌 조회·자산 현황을 쉬운 말로 설명 (조회 전용) | 가능 | **넣는다(I-38)**. 회원이 본인 앱키로 직접 연결하는 선택 기능이고, 운영사 서버는 앱키를 보관하지 않는 구조로 설계한다 [판단]. 여러 회원의 금융 정보를 운영사가 모아 보여주면 마이데이터 허가 문제가 생길 수 있어 [미확인] 법률 검토 전제 |
| L2 | 소비 습관·저축 계획 점검 (본인 입력 수입·지출, 목표) | 가능 | 보류(I-39, 2.70점). 입주 회원은 시설 청구가 지출의 큰 부분이라 A 청구 설명(I-29)으로 대신한다 |
| L2' | 이례 거래 숙려·보호자 확인 (조회 데이터로 큰 거래·낯선 패턴을 표시하고 동의한 보호자에게 알림) | 해당 없음 | 후보(I-41, 3.35점). 사기 피해(P-039)와 인지 저하(P-044, P-049)를 겨냥한 **보호 기능**. 주문을 막지는 못하고 알림만 한다 |
| L3 | 목표·위험 범위·거래 한도 안에서 투자 계획 실행과 자동매매 | 증권사가 개인 본인 계좌용 API와 모의투자를 공식 제공한다(F27, K30). 실거래 전 모의투자 검증 필수 | **넣지 않는다(I-40 탈락)**. 사업자가 고객에게 제공하려면 투자일임·자문 등록이 요건이고(K25), 사업자 제공 사례는 등록 업자 로보어드바이저뿐이다(K22). 평가 기준 통과 조건과 운영사 금전 관여 경계(P-048)에도 걸린다 |

리서치 후 점수: I-38(L1) 3.30 → 3.05, I-41(L2') 3.35 유지, I-39(L2) 2.70 보류, I-40(L3) 탈락. 상세는 `../outputs/scorecard.md` "축 9·10 반영 재평가".

**정리**: 원래 구상(L1~L3, 모의투자 자동매매)은 **사용자의 별도 개인·해커톤 프로젝트**로 진행하는 것이 맞다. 본인 계좌·본인 키로 LLM을 연결하는 방식은 증권사가 공식 지원한다(토스 K30, NH F26). 다만 토스가 이미 일반 고객에게 대화형 주문을 열어서 일반인용 프로젝트의 차별성은 낮아졌다. 차별화하려면 **사용자가 정한 목표·한도·확인 단계를 서버에서 강제하는 가드레일**(P-061)과 모의투자 검증 기록에 집중하는 편이 낫다 [판단]. 시니어 포트폴리오에는 L1(조회·설명)과 L2'(보호 알림)만 G의 선택 기능으로 넣는다. 두 프로젝트는 같은 기술 기반(증권 API 어댑터, LLM 설명 계층, 가드레일)을 공유할 수 있다. 면접에서는 "같은 기술을 시니어에게는 실행이 아니라 **이해와 보호**로 적용했다"는 판단 자체가 설득 포인트가 된다 [판단].

## 5. 설계 원칙 (백엔드로 보여줄 것)
1. **도구 호출만 허용**: 에이전트는 모듈 API를 정해진 도구로만 호출한다. 도구마다 필요한 권한(회원 본인, 대리인, 보호자 동의 범위)을 정책 테이블로 검사한다(D, I-30 재사용).
2. **쓰기 전 확인**: 일정 등록, 요청 접수, 이의 제기처럼 상태를 바꾸는 도구는 회원에게 확인을 받은 뒤에만 실행한다. 확인 토큰이 없으면 서버가 거부한다.
3. **인계 지점 명시**: 건강, 금전, 계약 의도는 분류기로 잡아 사람에게 넘기고, 넘긴 이유를 기록한다.
4. **채널 독립**: 앱, 음성, 전화(I-11), 보호자 앱이 같은 대화 세션과 요청 큐로 모인다.
5. **금융 비밀 분리**: 증권 앱키는 회원 기기나 별도 보관소에 두고, 운영사 데이터베이스와 로그에 남기지 않는다. 조회 결과는 대화에 필요한 만큼만 쓰고 저장하지 않는다 [판단].
6. **평가 가능한 로그**: 의도 분류, 도구 호출, 인계, 회원 확인을 모두 남겨 정확도와 인계율을 측정한다. 효과 수치를 주장하지 않고 측정 가능한 구조로 대신한다.

## 7. 데모 시나리오 (5분)
1. 회원이 "오늘 뭐 있어?"라고 말한다. 비서가 병원 예약, 복약 시간, 오후 프로그램을 읽어 준다(일정).
2. 회원이 "화장실 전등이 나갔어"라고 말한다. 비서가 확인을 받아 요청을 접수하면 직원 큐에 티켓이 생긴다(요청).
3. 회원이 "이번 달 왜 이렇게 많이 나왔어?"라고 묻는다. 비서가 결식 감면과 난방비 항목을 근거와 함께 설명하고, 이의 제기를 접수한다(청구).
4. 회원이 "은행이라는데 돈을 옮기래"라고 말한다. 비서가 판단하지 않고, 직원과 동의한 보호자에게 확인 요청을 보낸다(금융 안전).
5. (선택) 모의투자 계좌를 연결한 회원이 "내 주식 어때?"라고 묻는다. 비서는 잔고와 등락을 쉬운 말로 설명한다. "이거 팔까?"라는 질문에는 추천하지 않고 전문가 상담 연결을 안내한다(자산 이해).
6. 보호자 화면에서 동의 범위 안의 요약만 보인다(D).
