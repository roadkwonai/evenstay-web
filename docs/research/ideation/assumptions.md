# 핵심 가정 (숏리스트 후보)

상태: 초안 · 작성: 2026-11-02 · 방법: `identify-assumptions-new` 스킬의 8개 위험 범주(가치, 사용성, 사업성, 실현성, 윤리, 시장 진입, 전략, 팀) · 변경: 2026-11-03 한국어 문장·용어 검수(korean-skills)
신뢰도는 상(근거 있음) / 중(간접 근거) / 하(추정뿐)로 매겼다. 포트폴리오 MVP라서 "시장 진입"은 **면접 설득**(면접관을 설득하는 것)으로, "팀"은 **혼자 구축**(혼자 2~4주에 만드는 것)으로 해석했다.
★ 표시는 후보별로 가장 위험한 가정이다(신뢰도가 낮은데 틀리면 MVP 의미가 사라지는 것).

## A. 계약·청구 코어
| 범주 | 가정 | 신뢰도 | 확인 방법 |
|---|---|---|---|
| 가치 | 운영사는 소유주별 정산·리포트가 필요하다 | 중 (S4, S6, B14) | 해외 임대 PMS owner statement 문서 조사 |
| 사용성 | 경리 직원이 계약 상태와 청구 조정을 이해하고 쓸 수 있다 | 하 | 데모 화면을 현장 직원 1명에게 보여주기 |
| 사업성 | 자체 구축 비용이 기성 SW 도입보다 낫다 | 중 (회사가 이미 결정. S2) | 해당 없음 (회사 결정) |
| 실현성 | ★ 시니어하우징 청구 규칙(의무식 감면, 보증금·월비 교환, 선납, 몰취)을 공개 자료만으로 모델링할 수 있다 | 중 (A6, A11, A12, A16) | 시설 2~3곳 요금표로 규칙을 정리하고 예외를 목록화 |
| 윤리 | 금융 데이터의 정합성 오류가 입주자 피해로 이어지지 않게 한다 | 중 | 원장 불변성, 조정 전표, 테스트 |
| 면접 설득 | 면접관이 "PMS 코어 설계"를 핵심 역량 증거로 본다 | 상 (공고 S2) | 공고 주요업무와 1:1 대응표 |
| 전략 | 시니어하우징과 임대를 같은 코어로 묶을 수 있다 | 중 (S2, B8) | 임대 계약 시나리오 1개를 같은 모델에 올려 보기 |
| 혼자 구축 | 원장과 상태 전이를 2~3주 안에 테스트와 함께 만든다 | 중 | 범위를 식비·생활비·감면 3개 규칙으로 제한 |

## B. 이상 신호 통합 허브
| 범주 | 가정 | 신뢰도 | 확인 방법 |
|---|---|---|---|
| 가치 | ★ 현장에서 이상 신호가 여러 경로로 흩어져 놓치는 일이 실제로 있다 | 하 (현장 근거 없음. E7·E15 등은 서비스 존재 근거) | 시설 종사자 인터뷰 1~2명 |
| 사용성 | 야간 직원이 알림 홍수 없이 중요한 신호만 받는다 | 하 | 규칙·중복 제거 시뮬레이션으로 알림 수 비교 |
| 사업성 | 운영사가 기기 비용과 연동 비용을 감당한다 | 하 | 범위 밖 (MVP는 연동 구조만) |
| 실현성 | 기기 이벤트를 웹훅과 시뮬레이터로 충분히 재현할 수 있다 | 상 | 목업 어댑터 구현 |
| 윤리 | ★ 시스템이 판단을 대신하지 않고, 오탐·미탐 때 책임이 사람에게 명확하다 | 중 | 사람 확인 단계와 감사 로그를 필수로 설계 |
| 면접 설득 | 이벤트 처리(멱등성, 재시도, 순서)가 백엔드 역량으로 읽힌다 | 상 (공고 IoT·출입통제 연동) | 데모에서 같은 이벤트를 중복 전송해 보여주기 |
| 전략 | 출입통제·설비 알림으로 임대주택에도 쓸 수 있다 | 중 | 임대 시나리오 1개 |
| 혼자 구축 | 규칙 엔진은 단순 조건 규칙으로 충분하다 | 상 | 규칙 5개 이내로 제한 |

## C. 케어 단계 전환 관리
| 범주 | 가정 | 신뢰도 | 확인 방법 |
|---|---|---|---|
| 가치 | 입주자·보호자는 단계 전환 규칙을 미리 알고 싶어 한다 | 중 (A15, D1) | 시니어·보호자 인터뷰 3명 |
| 사용성 | 시니어가 자기 단계와 다음 단계를 화면에서 이해한다 | 하 | 종이 프로토타입을 부모님께 보여주기 |
| 사업성 | 운영사는 전환 규칙을 공개하는 것을 꺼리지 않는다 | 하 | 면접 질문으로 확인 |
| 실현성 | 단계 정의를 사이트별 설정으로 일반화할 수 있다 | 중 (A15 노블 단계 전환 사례) | 시설 2곳 사례를 같은 모델로 표현 |
| 윤리 | ★ 단계 판정이 입주자에게 불리한 낙인이나 퇴거 근거로 오용되지 않는다 | 하 | 판정 근거 공개, 이의 제기, 사람의 최종 결정을 설계에 넣기 |
| 면접 설득 | 2026-10 개정안을 반영한 점이 도메인 이해로 읽힌다 | 상 (A3 원문 대조) | 개정안 조항과 기능 대응표 |
| 전략 | ★ 개정안이 원안대로 확정된다 | 중 (입법예고 중, 2026-11-23 종료) | 입법예고 종료 후 확정 여부 확인 |
| 혼자 구축 | A의 계약·요금 연동 없이도 단독 데모가 가능하다 | 중 | A를 먼저 만들면 연동, 아니면 요금 변경을 이벤트로만 남긴다 |

## D. 동의 기반 보호자 포털
| 범주 | 가정 | 신뢰도 | 확인 방법 |
|---|---|---|---|
| 가치 | ★ 보호자는 여러 곳에서 따로 확인하는 데 불편을 느끼고 한곳에서 보기를 원한다 | 하 (한국 정량 자료 없음) | 보호자 인터뷰 3~5명 |
| 사용성 | 시니어가 항목별 동의를 이해하고 설정한다 (또는 직원이 대신 설정한다) | 하 | 동의 화면을 부모님께 보여주기 |
| 사업성 | 보호자 응대 시간이 줄어 운영사에 이득이다 | 하 | 범위 밖 [추정] |
| 실현성 | 관계 + 동의 + RBAC을 하나의 정책 모델로 표현할 수 있다 | 상 | 정책 테이블과 테스트 |
| 윤리 | ★ 동의 철회가 즉시 반영되고, 입주자 의사에 반해 정보가 보이지 않는다 | 중 | 철회 시나리오 테스트, 감사 로그 |
| 면접 설득 | RBAC과 개인정보 설계가 공고 요구로 읽힌다 | 상 (S2) | 공고 대응표 |
| 전략 | 다른 MVP(B, C)의 결과를 보호자에게 보여주는 공통 출구가 된다 | 중 | B·C 이벤트를 포털에 노출 |
| 혼자 구축 | 자동 요약 리포트는 직원 검수를 거치는 단순 생성으로 충분하다 | 중 | LLM 요약 + 검수 단계 |

## E. 입주 상담 CRM + AI 문의 에이전트 (예비)
| 범주 | 가정 | 신뢰도 | 확인 방법 |
|---|---|---|---|
| 가치 | 입주 문의가 반복적이고 상담 직원 시간을 많이 쓴다 | 하 | 상담 직원 인터뷰 또는 시설 FAQ 분석 |
| 사용성 | 시니어·보호자가 에이전트 응답을 믿고 쓴다 | 하 | 데모 대화를 보호자에게 보여주기 |
| 사업성 | 대기자 관리가 입주율에 영향을 준다 | 중 (A7, A16 대기 2년) | 해당 없음 |
| 실현성 | 에이전트가 PMS API를 도구로 호출해 정확히 답한다 | 상 | 도구 호출 + 평가 세트 |
| 윤리 | ★ 에이전트가 비용이나 자격을 두고 틀린 약속을 하지 않는다 | 중 | 답할 수 없는 질문은 사람에게 넘기기, 근거 표시 |
| 면접 설득 | 공고의 AI Agent 연동 요구를 보여준다 | 상 (S2, S3) | 공고 대응표 |
| 전략 | 흔한 CRM과 구분된다 | 하 | 시니어 고유 단계(심사, 건강 조건)를 강조 |
| 혼자 구축 | CRM과 에이전트를 2~3주에 만든다 | 중 | CRM은 최소 파이프라인만 |
