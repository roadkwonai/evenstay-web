# Evenstay 화면 필요성·이용자별 검토

상태: 초안 (검토 의견. 정의서는 고치지 않았다. 사용자 확인 전)
날짜: 2026-11-04
대상: `design/mvp-screens.md` 1~3절 목록, 5절 통합 흐름(41단계), 6절 흐름 표시, 6-1절 화면 수
방법: `prioritization-frameworks`(Kano, MoSCoW), `stakeholder-map`(권력×관심 격자, 이용자별 표). 스킬 본문은 직접 읽고 틀만 적용했다. 각 모듈 `prd.md`는 머리말과 이용자 항목만 훑었다(전체 정독 아님).

기준: (1) 5절 흐름에 나옴 (2) 사용자가 오늘 직접 요청 (3) 백엔드 설계가 보임(상태 전이, 모듈 경계, 이벤트, 권한, 감사) (4) 이용자 핵심 일. 사용자 요청 기능은 지우지 않고 가벼운 형태(탭, 패널, 상태, 카드, 서랍)로 줄이는 안만 냈다.

## 0. 먼저 알아 둘 것

- **숫자 세는 단위.** 아래 "제안"은 **페이지 단위 화면**이다. 탭, 서랍(Sheet), 대화창(Dialog), 상태는 0으로 세지만 아트보드 컷은 여전히 필요하다. 그래서 작업량은 숫자만큼 줄지 않는다 [추정: 컷 20~30장 남음].
- **현재 118은 하한이다.** 한 행이 여러 화면을 숨긴다: TRN-09(하위 화면 5개, 3-5절), REQ-03(종류별 입력, 한 화면 한 칸), FAM-14(초대·수락 2화면), CORE-05(작성·승계 창), CORE-07(탭 3개). 합치면 실제 아트보드는 118보다 많다 [추정].
- **정의서끼리 어긋난 곳.** 7절 결정 4는 SAF-05, AST-10, TRN-07을 "Must(누가 언제 무엇을 했는지)"로 정했는데 6절은 AST-10, TRN-07을 "없음"으로 표시했다. 탭으로 합치면 기능은 유지되고 이 충돌도 풀린다.
- **화면 행이 없는 목록 항목.** 1-1절 COM-07 목록 5번 "급할 때 연락할 분"은 3절에 행이 없다(CORE-08 옆 칸으로만 나옴, 4-7절 CORE-08 행). 만들지, 칸으로 둘지 정해야 한다.

## 3. 따로 두는 화면과 이유

- **데모 흐름의 뼈대(상태 전이·권한이 보임):** CORE-01(운영 현황, 요청), CORE-02(소유주 격리), CORE-04·05(계약·승계), CORE-06·07(식사 마감 → 청구), CORE-13(장기 부재, 요청), CORE-14(월 리포트, 요청), SAF-01·02(알림 목록, 처리), SAF-06(기기 신호 입력), FAM-01(허락), FAM-02·03(건강 소식은 법적으로 따로 동의라 합치지 않음), FAM-06a~f, FAM-09~11, TRN-02~05(제안자 ≠ 결정자 규칙은 TRN-05가 별도 이용자(책임자)의 받은편지함이라 분리), REQ-01·03·05·07·12, CMN-03·11·14·17·20.
- **입주자 앱 확인 단계:** 시니어 앱은 "한 화면 한 칸"(DESIGN.md) 규칙이라 REQ-03, REQ-05, CMN-08은 각각 따로 둔다. 위 합치기는 확인 단계를 "같은 화면의 상태 컷"으로 옮기는 것이지 한 번에 여러 입력을 받는 것이 아니다.
- **서로 다른 이용자의 같은 자료:** CMN-08(회원) / CMN-19(직원)은 앱이 달라 분리 유지. 시설 예약은 직원 일정표(겹침 검사)와 회원 예약 흐름이 다르다(3-7절 설명).
- **감사 보기:** FAM-04(회원이 본 열람 기록), FAM-11(본사 열람 기록)은 이용자와 권한이 다르다. AST-11은 거부 줄이 모듈 경계 설계를 보여 주는 화면이라 유지.
- **요청 기능이 화면 하나인 것:** SAF-16(사고·학대 보고: 저장 후 덧붙이기만 되는 기록, 감사 설계), SAF-17(재실 명단: 사람마다 확인), CORE-09, CORE-15(탭이나 카드로 합치기 전에는 단독).
- 회원 안심 알림 SAF-09(B의 유일한 회원 화면), 대리인 화면 FAM-13도 단독 유지(해당 이용자의 유일한 화면).

## 4. 빼기(Won't) 후보

사용자 요청도 아니고 5절 흐름에도 없는 화면만. 기능이 모듈 설계에 있으면 "문서에만 남김".

| 화면 | 이유 | 대안 |
|---|---|---|
| FAM-14 초대·수락 | 6절 없음, P1. 보호자 연결은 5절 7단계 FAM-09(프런트 대신 입력)가 이미 보여 줌 | 문서에만 남김 |
| AST-07 지난 대화 | 6절 없음, P1. 시니어가 다시 열어 보는 일이 드뭅니다 [추정]. 보관 정책은 AST-10/11 탭에 보임 | 합치기 21 대신 이것도 빼도 됨 |
| CORE-12 퇴거 정산 | 6절 없음, P1. 보증금 보호(요청)는 CORE-04 부록에서 이미 다룸 | 합치기 7의 탭도 시간이 없으면 생략 |
| FAM-17, FAM-20 | 6절 없음. 범위 넓힘 직후 안내인데 5절에서 안 나옴(3절 FAM-20 설명: 11/18 장면은 안내가 나오지 않음) | 합치기 17 대신 생략 가능 |

위 4건 외 6절 "없음" 23개는 요청 기능이거나 설계 보이는 화면이라 Won't로 두지 않고 합치기로만 처리했다.

## 5. Kano + MoSCoW (행마다)

Kano는 "포트폴리오 데모" 맥락이다. 예: SAF-16·17은 현실에서는 기본 기대(법적 의무)지만 데모에서는 감탄(Attractive)으로 분류했다. 별칭 행(AST-01, SAF-07, TRN-10)은 가리키는 화면을 따른다. 기준: Must = 흐름에 나옴 + (백엔드 설계가 보이거나 핵심 일). Should = 흐름에 나오는 보조 화면, 요청한 부록. Could = 부록이나 없음 중 틀 보여 주기. Won't = 4절.

| 모듈 | Kano: 기본(M) / 성능(P) / 감탄(A) / 무관(I) | MoSCoW |
|---|---|---|
