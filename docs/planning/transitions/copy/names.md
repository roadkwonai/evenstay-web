모듈 이름은 이미 확정됐다(`senior-lab/03-copywriting/ideas/pms-core-billing/names.md` v3, 2026-11-02): 직원 화면과 회원 화면 모두 **생활 지원 단계**(직원 화면 이름은 2026-11-03 사용자 결정으로 Evenstay Transitions에서 한글로 바꿈). 그래서 `product-name` 스킬은 쓰지 않았다. 이 파일은 화면 안 라벨(단계 이름, 평가 기록 항목, 상태, 선택지)만 정한다.
입력: 이 폴더 `product-marketing.md`, 코어 용어집, D `names.md`(건강 소식 종류 표시), B `names.md`(판단하지 않는 라벨 원칙).

## 라벨을 고른 기준
1. **단계 이름은 받는 서비스를 말한다.** "자립", "중증"처럼 입주자의 상태를 이름으로 삼으면 단계가 사람에게 붙는 꼬리표가 된다. 단계는 "어떤 서비스를 받는가"의 묶음이다(B 등급 라벨 "입주자의 상태를 말하지 않는다"와 같은 원칙).
2. **판정하는 말을 쓰지 않는다.** 시스템은 평가를 기록하고 사람이 결정한다. 상태 라벨은 "누가 무엇을 했는지"를 말한다("제안됨", "결정됨"). "판정", "적합/부적합"은 쓰지 않는다.
3. **번호를 매기지 않는다.** 1~4단계로 부르면 위아래가 있는 사다리로 읽히고, 직원이 함께 기록하는 장기요양 인정 등급(1~5등급, 인지지원등급)과 헷갈린다. 화면에는 이름만 쓰고 순서는 코드와 정렬에만 둔다.
4. **양쪽으로 바뀐다.** 라벨에 "올라감/내려감", "상향/하향"을 쓰지 않는다. 바뀐 것은 "○○에서 △△로"라고 쓴다.
5. 호칭과 말투는 코어를 따른다. 직원 화면 "입주자"와 합쇼체, 회원 화면 "회원님"과 해요체.

## 1. 단계 이름 (CareStage, 시드 사업장 기본값)
숏리스트 C의 작업 이름(자립 → 생활 지원 → 외부 돌봄 병행 → 전원 검토)을 위 기준으로 바꿨다. 단계 정의는 사업장 설정이다. 코드 4개는 고정이고, 라벨·설명·서비스·요금 묶음은 사업장이 새 판으로 바꿀 수 있다(P1, C 기획 2026-11-03 [가설]). 이 표는 데모 시드 사업장의 값이다.

| 코드 (순서) | 숏리스트 작업 이름 | 직원 화면 | 회원 화면 (라벨 / 한 줄 설명) | 고른 이유 | 버린 후보 |
|---|---|---|---|---|---|
| `BASIC` (1) | 자립 | **기본 서비스** | **기본 서비스** / 입주 계약에 있는 식사, 생활 도움, 프로그램을 받으시는 단계예요. | 받는 서비스를 말한다. 모든 입주자의 출발점이라 특별한 뜻이 붙지 않는다 | 자립(사람의 상태), 일반(그다음 단계가 "일반이 아님"이 된다) |
| `LIVING_SUPPORT` (2) | 생활 지원 | **생활 지원 추가** | **생활 지원 더하기** / 기본 서비스에 목욕, 약 챙기기 같은 도움을 더 받으시는 단계예요. | 모듈 이름 "생활 지원 단계"와 단계 이름 "생활 지원"이 같으면 "생활 지원 단계가 생활 지원이에요"처럼 겹친다. "더하기"로 무엇이 늘어나는지를 보인다 | 생활 지원(모듈 이름과 겹침), 생활보조(A15 사례 용어지만 "보조받는 사람"으로 읽힘), 케어 플러스(외래어) |
| `WITH_EXTERNAL_CARE` (3) | 외부 돌봄 병행 | **외부 돌봄 병행** | **다른 기관 돌봄 함께** / 방문요양처럼 다른 기관의 돌봄도 함께 받으시는 단계예요. 레지던스에서 받으시는 도움은 그대로예요. | 개정안의 "서비스를 받으며 계속 거주"에 해당하는 단계다(A3, E12) [추정: 대응 관계]. "외부"는 회원에게 낯설어 "다른 기관"으로 썼다 | 재가서비스 병행(법률 용어), 요양 단계("요양원"을 떠올림) |
| `PLACE_CONSULT` (4) | 전원 검토 | **거처 상담** | **지낼 곳 함께 의논** / 지금 받는 도움으로 이곳에서 지내시기 어려울 수 있어, 앞으로 지낼 곳을 회원님, 가족, 직원이 함께 의논해요. | "전원 검토"는 결론(옮김)을 먼저 말한다. 이 단계에서 하는 일은 상담이고, 결론은 상담 뒤에 사람이 정한다. 회원 설명에 "어려울 수 있어"를 숨기지 않고 쓴다 | 전원 검토(결론을 앞세움), 퇴거 검토(낙인·계약 해지로 읽힘), 요양 전환(결론), 이동 준비(결론) |

- **정렬**: 직원 목록과 회원 화면 모두 코드 순서로 놓는다. 순서는 "받는 도움의 양"이고 사람의 순위가 아니다.
- **`PLACE_CONSULT`는 다른 단계와 다르게 다룬다.** 결정 전에 회원 설명과 의견 기록이 반드시 있어야 하고, 대리인이나 회원이 고른 가족이 상담에 함께했는지 적는다(3절). 이 단계로 바뀌어도 입주 계약은 그대로다(코어 계약 상태는 바뀌지 않음).
- 단계 하나에 붙는 것: 한 줄 설명, 서비스 목록(바뀌는 것), 바뀌지 않는 것 목록, 단계가 바뀌는 때(조건), 요금 묶음(4절).

## 2. 평가 기록 (Assessment)
직원과 전문가가 본 일과 도와 드린 일을 적는다. **점수 칸, 진단명 칸, 다음 단계 추천 칸은 없다.** 진료 결과와 처방도 받지 않는다(D 건강 소식 경계와 같음).

**2-1. 머리 항목**
| 코드 | 직원 화면 라벨 | 입력 방식 |
|---|---|---|
| `assessedAt` | 살펴본 날 | 날짜 |
| `assessor` | 살펴본 사람 | 직원 이름 + 직무(간호 · 생활지원 · 외부 전문가). 외부 전문가는 이름과 소속을 적는다 |
| `trigger` | 살펴본 계기 | 선택(아래) |
| `residentPresent` | 입주자와 함께 | 함께 살펴봄 · 입주자가 함께하지 않음(사유) |

**살펴본 계기 선택지 (`trigger`)**
| 코드 | 라벨 |
|---|---|
| `SCHEDULED` | 정기 살펴보기 (MVP는 선택지만. 주기 알림은 Next, 6개월 [가설]) |
| `AFTER_DISCHARGE` | 퇴원 뒤 |
| `AFTER_INCIDENT` | 바닥에 앉아 계셨던 일 같은 일이 생긴 뒤 (B 기록 연결 가능) |
| `RESIDENT_REQUEST` | 입주자 요청 |
| `FAMILY_REQUEST` | 가족·대리인 요청 |
| `STAFF_OBSERVATION` | 직원이 본 일 |
| `EXTERNAL_CARE_CHANGE` | 외부 돌봄이 시작되거나 바뀜 |
| `REVIEW_REQUEST` | 다시 검토 요청(5절)으로 |

**2-2. 일상생활 항목** — 판단 대신 "실제로 도움을 드렸는지"를 고른다(B "직원이 한 일만 고른다"와 같은 원칙).
| 코드 | 항목 라벨 |
|---|---|
| `MEAL` | 식사 |
| `MOBILITY` | 걷기·움직이기 |
| `BATHING` | 씻기 |
| `DRESSING` | 옷 입기 |
| `TOILETING` | 화장실 |
| `MEDICATION` | 약 챙기기 |
| `GOING_OUT` | 외출 |

| 선택지 코드 | 라벨 | 버린 후보 |
|---|---|---|
| `INDEPENDENT` | 혼자 하심 | 자립(사람의 상태) |
| `SOMETIMES_HELPED` | 가끔 도움을 드림 | 부분 의존(판정) |
| `ALWAYS_HELPED` | 매번 도움을 드림 | 완전 의존(판정), 불가 |
| `NOT_OBSERVED` | 살펴보지 못함 | (빈칸으로 두면 "문제 없음"으로 읽힘) |

- 항목마다 "본 일" 한 줄을 적을 수 있다. 쓰는 법 안내: 직원이 본 일과 시각만 적습니다. 짐작이나 병명은 적지 않습니다.

**2-3. 기억·판단 관련** (P-031) — 진단명 칸 없음.
| 코드 | 라벨 | 입력 |
|---|---|---|
| `cognitiveObservation` | 기억·판단과 관련해 본 일 | 글(예: "11월 10일 점심, 식당 가는 길을 두 번 물으셨습니다.") |
| `screeningGuided` | 검사 안내 | 안내하지 않음 · 치매안심센터 검사를 안내함 · 입주자가 검사를 원하지 않으심 |

- 인지 관련 기록은 이것만으로 단계를 바꾸는 근거가 되지 않게 한다. 결정 화면에서 "기억·판단 관련 기록만 있는 제안"이면 다른 평가를 함께 보라는 안내를 띄운다(copy.md 2-4). 결정은 막지 않는다 [가설].

**2-4. 바깥에서 온 정보**
| 코드 | 라벨 | 입력 |
|---|---|---|
| `ltcGrade` | 장기요양 인정 결과 | 없음 · 신청 중 · 받음(등급과 유효기간, 증빙 받은 날). 공단 결과를 옮겨 적는 칸이다 |
| `dischargeNote` | 퇴원 때 받은 안내 | 받음(받은 날) · 받지 못함. 내용은 적지 않고 서류를 받았는지만 적는다 (P-020) |
| `externalAssessor` | 외부 전문가 의견 | 받은 날, 의견을 준 곳. 의견 원문은 저장하지 않는다(C 기획) |

**2-5. 회원님 뜻**
| 코드 | 라벨 | 입력 |
|---|---|---|
| `residentWish` | 입주자가 말씀하신 바람 | 들은 그대로 적는다(예: "목욕은 혼자 하고 싶다고 하셨습니다.") |

## 3. 단계 변경 제안·결정
**3-1. 제안 상태 (`ProposalStatus`)**
| 코드 | 직원 화면 | 회원 화면 | 고른 이유 | 버린 후보 |
|---|---|---|---|---|
| `DRAFT` | 작성 중 | (보이지 않음. 다시 살펴본 뒤 결정으로 돌아온 제안이면 "한 번 더 살펴본 뒤 정하기로 했어요") | 코어 계약 상태 "작성 중"과 같은 말 | — |
| `AWAITING_EXPLANATION` | 설명 전 | (보이지 않음) | 회원에게 설명하기 전에는 결정할 수 없다는 것을 이름이 보인다 | 승인 대기(설명 단계가 빠짐) |
| `AWAITING_DECISION` | 결정 대기 | 직원이 드린 제안을 살펴보고 있어요 | 회원 의견을 들은 뒤다 | 검토 중(누가 하는지 모호) |
| `DECIDED_CHANGE` | 변경 결정 | 정해진 내용 · ○○로 바뀌었어요 | 결정했다는 사실과 결과 | 승인(제안자에게 허락을 주는 말처럼 읽힘), 판정 |
| `DECIDED_KEEP` | 유지 결정 | 정해진 내용 · 지금 단계 그대로예요 | 바꾸지 않은 것도 결정이다. 기록에 남는다 | 반려(제안자를 탓함), 기각 |
| `WITHDRAWN` | 제안 취소 | (보이지 않음. 이미 설명한 뒤면 "제안을 거두었어요") | 제안한 사람이 거둠 | 삭제(기록이 사라지는 것처럼 읽힘) |

**3-2. 입주자 의견 (`ResidentOpinion`)** — 설명한 직원이 고르고, 들은 말을 함께 적는다.
| 코드 | 직원 화면 | 회원 화면 |
|---|---|---|
| `AGREES` | 동의하심 | 좋다고 하셨어요 |
| `WANTS_TIME` | 더 생각하고 싶어 하심 | 더 생각해 보기로 하셨어요 |
| `DISAGREES` | 동의하지 않으심 | 원하지 않는다고 하셨어요 |
| `COULD_NOT_HEAR` | 의견을 듣지 못함 (사유 필수) | (보이지 않음) |

- 함께한 사람: 대리인 · 입주자가 고른 가족 · 함께한 사람 없음. 가족이 함께해도 의견은 회원 본인의 말로 적는다.
- `PLACE_CONSULT`로 바꾸는 제안은 `COULD_NOT_HEAR`로 결정할 수 없다(**확정**, C 기획 2026-11-03).
- 마지막 의견이 `WANTS_TIME`이면 [제안대로 바꾸기]만 막고, `PLACE_CONSULT` + `DISAGREES`면 바꾸기만 막는다 [가설] (copy.md 5절).
- 설명 기록 체크 `memberAskedNotToTellFamily`: 가족에게 알리지 말아 달라고 하심 (들은 시각). 이번 차례 설명 중 한 번이라도 있으면 건강 소식에 올리지 않는다.

**3-3. 결정 선택지 (`StageDecision`)**
| 코드 | 버튼 라벨 |
|---|---|
| `CHANGE` | 제안대로 바꾸기 |
| `KEEP` | 지금 단계 유지 |
| `REASSESS` | 다시 살펴본 뒤 결정 |

- 결정하는 사람: 사업장 책임자(SITE_MANAGER) 또는 같은 범위의 본사 운영 매니저(HQ_MANAGER) [가설, C 기획]. **제안한 사람은 같은 제안을 결정할 수 없다**(코어 퇴거 정산 "작성자 ≠ 승인자"와 같은 원칙).
- 결정 사유는 필수다. 사유 칸 라벨: 결정한 까닭.

## 4. 요금 묶음과 요금 영향 표시
코어 요금표는 체결 때 고정되고 일할 계산이 없다. 계약 변경 API는 코어 Next다. 그래서 C는 요금을 바꾸지 않고 표시만 한다. 단계 정의에는 금액 없이 요금 묶음만 둔다(직원 화면만).

| 요금 묶음 코드 | 직원 화면 | 쓰는 단계 (시드) |
|---|---|---|
| `BASE` | 기본 묶음 | 기본 서비스 |
| `LIVING_SUPPORT` | 생활 지원 묶음 | 생활 지원 추가 |
| (이어받기) | 지금 서비스 그대로 이어받기 | 외부 돌봄 병행, 거처 상담 |

요금 영향은 직원이 고르지 않는다. 제안할 때 지금 단계와 제안 단계의 묶음을 비교해 화면이 보인다.

| 코드 | 직원 화면 | 회원 화면 |
|---|---|---|
| `NO_FEE_CHANGE` | 요금 변화 없음 (요금 묶음이 같음) | 내실 돈은 그대로예요 |
| `AMENDMENT_NEEDED` | 계약 변경 필요 (요금 묶음이 다름. 기본 서비스로 돌아갈 때도) | 내실 돈이 바뀔 수 있어요. 입주 계약을 바꿀지 직원이 따로 여쭤봐요 |
| `AMENDMENT_REQUESTED` | 계약 변경 요청함 (일시, 요청한 사람) | (위와 같음) |

- `AMENDMENT_REQUESTED`는 MVP에서 C가 계약 변경 요청을 기록하고 경리 "확인할 일"에 한 줄로 보이는 것까지다. 코어 `ContractCommand.requestAmendment`는 Next(C 기획).
- 계약 변경 요청 상태: `OPEN` 확인 전 · `ACKNOWLEDGED` 확인함 (확인한 사람, 처리 메모).

## 5. 다시 검토 요청 (`ReviewRequest`)
| 코드 | 직원 화면 | 회원 화면 |
|---|---|---|
| `ReviewRequest` | 다시 검토 요청 | 다시 봐 주세요 (버튼) |
| `OPEN` | 접수 | 직원에게 전했어요 |
| `REASSESSED` | 다시 살펴봄 (평가 기록 연결) | 직원이 다시 살펴봤어요 |

- 누가 요청할 수 있나: 회원 본인, 대신 처리하실 분. 가족(함께 보실 분)의 요청은 직원이 받아 "가족·대리인 요청" 계기로 평가를 연다 [가설].

## 6. 외부 돌봄 일정 (ExternalCareSchedule)
| 코드 | 직원 화면 | 회원 화면 |
|---|---|---|
| `provider` | 기관 이름 | 기관 |
| `serviceType` | 서비스 종류: 방문요양 · 방문간호 · 방문목욕 · 주야간보호 · 그 밖의 돌봄 | 같은 말 |
| `slot` | 요일·시간 | 오시는 때(주야간보호는 "다녀오시는 때") |
| `period` | 시작일 · 종료일(없으면 비움) | — |
| `source` | 정보를 준 곳: 입주자 · 가족·대리인 · 기관 | — |
| `providerContact` | 기관 연락처 | (보이지 않음) |
| `memberAskedNotToTellFamily` | 가족에게 알리지 말아 달라고 하심 (들은 시각) | (보이지 않음) |
| `ScheduleOverlap` | 시간 겹침 (노랑 + 겹친 두 칸 표시) | (보이지 않음) |
| 겹침 처리 선택지 | 레지던스 서비스 시간 옮김 · 기관에 시간 조정 요청 · 둘 다 그대로(사유) | — |

- 겹침 표시는 경고다. 직원이 처리할 때까지 일정 저장을 막지 않는다(외부 일정은 시설이 정할 수 없어서).
- 보호자 화면의 "일정"(D)에는 넣지 않는다. D는 일정에 코어 keyDates만 둔다. 외부 돌봄은 장기요양 이용을 드러내는 건강 관련 정보라서, 보호자에게는 건강 소식 범위로만 간다(7절) [추정: 법률 검토].

## 7. 보호자에게 가는 내용 (D 건강 소식 안)
D `names.md` 1-1의 종류 표시 표에 같은 라벨로 들어갔다(C 기획 확정, 2026-11-03).

| 제안 코드 (출처) | 라벨 (보호자 목록 한 줄 앞) | 안 쓰는 말 |
|---|---|---|
| `CARE_STAGE_CHANGE` (C 결정) | 생활 지원 단계가 바뀐 일 | 단계 변경, 등급 변경 |
| `EXTERNAL_CARE_START` (C 외부 일정 시작, P1) | 다른 기관 돌봄이 시작된 일 | 방문요양 일정(일정 항목과 헷갈림) |

- 다른 기관 돌봄이 끝난 일(`EXTERNAL_CARE_END`)은 Next라 라벨을 정하지 않는다.
- 대안이었던 D `CARE_NOTE`("그 밖의 건강 기록")는 쓰지 않는다. 보호자가 단계가 바뀐 일을 다른 기록과 구분하기 어렵다.
- 보호자에게 보이지 않는 것: 평가 기록 내용, 기억·판단 관련 본 일, 회원님 의견, 다시 검토 요청, 제안 단계(결정 전). 결정된 것만 간다.

## 9. 변경 이력 (StageHistory) 한 줄 틀
직원 화면: `날짜 시각 · 누가(직무) · 무엇을 · ○○ → △△`
- 예: 2026-12-10 16:20 · 최영미(사업장 책임자) · 단계 변경 결정 · 기본 서비스 → 생활 지원 추가

회원 화면(지난 단계 기록): `○월 ○일부터 ○○` 한 줄씩. 바뀐 까닭은 상세에서 본다.
