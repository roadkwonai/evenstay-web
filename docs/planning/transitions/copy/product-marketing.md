## Product Overview
**One-liner:** 건강이 바뀌어도 무엇이 바뀌고 무엇이 그대로인지 먼저 보여 주고, 단계를 바꾼 근거와 결정을 사람 이름과 함께 남기는 생활 지원 단계 관리. (숏리스트 C 가치 제안을 화면 용어로 바꿈)
**What it does:** 사업장마다 생활 지원 단계와 단계별 서비스를 정한다. 간호·생활지원 직원과 외부 전문가가 평가를 기록하면, 직원이 단계 변경을 제안하고 회원님께 설명한 뒤 다른 사람이 결정한다. 외부 방문요양 일정을 입주자 일정에 붙여 시설 서비스와 시간이 겹치면 직원에게 알린다. 요금이 달라지는 경우는 직원이 계약 변경을 요청하는 데서 멈춘다(요금 자동 반영 없음).
**Product category:** 시니어하우징 PMS의 케어 단계 모듈. 해외에서는 "level of care assessment", "service plan" 기능으로 불린다 [추정].
**Product type:** B2B2C. 직원이 쓰는 내부 화면("생활 지원 단계")과 회원 화면(Evenstay 홈 안의 "생활 지원 단계"). 보호자는 D의 "건강 소식"으로만 본다.
**Business model:** 포트폴리오에서는 해당 없음.

**시스템이 하지 않는 일** (모든 카피의 전제)
- 단계를 판정하지 않는다. 점수를 매기거나 다음 단계를 추천하지 않는다. 사람이 기록한 평가와 사람이 한 결정을 보여 준다.
- 진단명, 진료 결과, 처방을 받지 않는다(D 건강 소식과 같은 경계).
- 단계가 바뀌어도 입주 계약을 끝내거나 바꾸지 않는다. 계약 변경은 코어에서 따로, 서명으로 한다.
- 요금을 바꾸지 않는다. 코어 요금표는 체결 때 고정되고 일할 계산이 없다. 계약 변경 API(`ContractCommand.requestAmendment`)는 코어 Next 항목이다 [사실: 코어 기획].

## Target Audience
**Target companies:** 시니어하우징(노인복지주택)을 위탁 운영하는 회사. 개정안이 확정되면 입주자가 재가서비스를 받으며 계속 사는 경우가 늘어난다 [추정, A3·E12].
**Decision-makers:** 운영사 운영 책임자, 사업장 책임자. 기술 판단은 Tech Lead.
**Primary use case:** 입주자의 건강이 바뀌었을 때(퇴원, 바닥에 앉아 계셨던 일, 기억이 흐려지는 일) 평가 → 제안 → 설명 → 결정 → 서비스 변경을 기록으로 남긴다.
**Jobs to be done:**
- (회원) 몸이 조금씩 약해져도 지금 사는 곳에서 내 생활 방식대로 계속 살고 싶다(U1 핵심 과업).
- (직원) 퇴원하고 돌아온 입주자의 서비스를 바로 맞추고, 외부 돌봄 기관과 시간이 겹치지 않게 하고 싶다(U4 기대 3, P-019, P-020).
- (운영 매니저) 단계 변경을 누가 왜 결정했는지 설명할 수 있게 남기고 싶다(U5 기대 3).
**Use cases:**
- 퇴원 후 평가 기록 → "기본 서비스"에서 "생활 지원 더하기"로 변경 제안 → 회원님께 설명하고 의견 기록 → 사업장 책임자 결정
- 장기요양 인정 뒤 방문요양 시작 → 외부 일정 입력 → 시설 목욕 도움과 시간이 겹친다는 경고
- 회복 뒤 다시 평가 → 이전 단계로 돌아감(단계는 양쪽으로 바뀐다)
- 회원님이 결정에 동의하지 않음 → 다시 봐 달라는 요청 기록 → 재평가

## Problems & Pain Points
**Core problem:** 한 시설 사례에서 입주자는 평균 7.3년 머문다(A6, 노블카운티). 그동안 건강이 바뀌는 일은 정해진 경로에 가깝다(U1 통찰) [추정]. 그런데 건강이 나빠지면 계속 살 수 있는지, 어떤 서비스로 이어지는지가 시설마다 다르고 잘 보이지 않는다(P-003). 개정안은 서비스를 받아 독립생활을 유지할 수 있으면 계속 살 수 있게 하려 한다(A3, E12. 입법예고 2026-10-13~11-23, 확정 전).
**Why alternatives fall short:**
- 상담 때 말로 설명: 기록이 남지 않고 설명한 사람마다 다르다 [추정].
- 종이 평가표와 엑셀: 평가와 결정, 서비스 변경, 요금이 따로 논다 [추정].
- 외부 기관 일정은 회원·보호자 말이나 기관 전화로만 안다(P-019, 조정은 시설별 수기 [추정]).
- 문제가 생길 때까지 미룸: 퇴원 뒤 케어 계획이 맞지 않는다(P-020).
**What it costs them:** 퇴원 직후 서비스 공백, 외부 돌봄과 겹치거나 빠지는 시간, 단계 결정 분쟁 [추정. NEED: 직원·보호자 인터뷰].
**Emotional tension:** 회원은 단계가 "나가라는 신호"로 들릴까 두렵다 [가설, 숏리스트 가장 위험한 가정]. 보호자는 갑자기 전원 이야기를 들을까 불안하다 [가설]. 직원은 결정이 나중에 문제가 될까 부담스럽다 [추정].

## Competitive Landscape
**Direct:** 해외 시니어리빙 스위트의 케어 단계·서비스 계획 기능(B1 계열) — 한국 제도(장기요양, 개정안)와 계약 구조에 맞지 않는다 [추정].
**Secondary:** 장기요양기관용 기록 프로그램 — 급여 기록 중심이고, 민간 계약 기반 노인복지주택의 단계·계약 연결이 없다 [추정].
**Indirect:** 상담 직원의 설명, 종이 평가표, 보호자 단톡방 — 근거와 이력이 남지 않는다.

## Differentiation
**Key differentiators:**
- 판정 엔진이 없다. 평가는 사람이 기록하고, 제안한 사람과 결정한 사람이 다르다.
- 회원 화면은 "바뀌는 것과 바뀌지 않는 것"을 단계 이름보다 먼저 보인다.
- 단계는 양쪽으로 바뀐다. 회복하면 이전 단계로 돌아간다.
- 단계 변경과 계약 변경을 나눈다. 단계가 바뀌어도 계약은 서명 없이 바뀌지 않는다.
- 외부 돌봄 일정을 시설 서비스와 한 줄에 놓고 시간 겹침을 알린다.
**How we do it differently:** 단계를 입주자의 상태가 아니라 "받는 서비스의 묶음"으로 정의한다. 그래서 단계 이름도 사람이 아니라 서비스를 말한다(names.md 1절).
**Why that's better:** 단계가 낙인이 되지 않고, 분쟁이 생기면 누가 무엇을 보고 결정했는지 기록으로 설명할 수 있다 [가설: 인터뷰로 확인].
**Why customers choose us:** [NEED: 도입 근거 없음. 포트폴리오에서는 설계 근거로 대신한다]

## Objections
| Objection | Response |

| 단계 기록이 퇴거 근거로 쓰이지 않나 | 단계 변경은 계약을 끝내지 않는다. 계약 해지는 코어에서 따로, 본인이나 서명 권한이 있는 대리인의 요청으로만 접수된다(코어 2-7). 회원 의견과 다시 봐 달라는 요청이 결정 기록에 붙는다. 실제 입주 계약서의 해지 조항은 [NEED] |
| 시스템이 단계를 정하면 더 공정하지 않나 | 점수로 정하면 근거를 설명하기 어렵고 책임이 흐려진다. 사람이 평가하고 다른 사람이 결정하게 했다. 숏리스트 가정 표 윤리 항목의 대응("사람의 최종 결정")이다 |

| 건강정보를 너무 많이 모으지 않나 | 진단명·진료 결과·처방 칸이 없다. 평가는 직원이 본 일과 도움을 드린 일로 적는다. 보호자에게는 D 건강 소식(별도 동의)으로만 간다 |

## Switching Dynamics
**Push:** 말로만 하는 단계 설명, 퇴원 뒤 서비스 공백, 외부 기관과의 시간 겹침(P-003, P-019, P-020).
**Pull:** 바뀌는 것과 바뀌지 않는 것이 한 화면에, 결정 근거가 한 이력에.
**Habit:** 상담 직원의 설명, 종이 평가표.
**Anxiety:** 기록이 남는 것 자체에 대한 부담(직원), 단계 이름이 남는 것에 대한 부담(회원) [가설].

## Brand Voice
코어의 네 속성(차분하다, 존중한다, 근거를 보인다, 기록이 남는다)을 그대로 쓴다. C에서 특히 더 지키는 것:

| Attribute | Means | Doesn't mean | Example line |
|---|---|---|---|
| 바뀌지 않는 것부터 | 회원 화면은 바뀌지 않는 것을 먼저, 바뀌는 것을 다음에 | 바뀌는 것을 숨기기 | "방과 입주 계약은 그대로예요." |
| 사람이 정한다 | 누가 살펴보고 누가 정했는지 이름으로 | 시스템이 정한 것처럼 "단계가 변경되었습니다" | "간호 담당 박서준 직원이 살펴보고, 최영미 책임자가 정했어요." |
| 다시 바뀔 수 있다 | 단계는 회복하면 돌아간다 | 내리막 사다리처럼 번호 매기기 | "몸이 나아지시면 직원이 다시 살펴보고 단계를 다시 정해요." |
| 본 일을 쓴다 (직원용) | B처럼 관찰한 사실과 도와 드린 일 | 상태 판단, 진단 짐작 | "식당 가는 길을 두 번 물으셨습니다." |

**Tone by context:**
- 회원 화면: 해요체, "회원님", 한 문장에 하나의 사실, 단계 번호 없음.
- 직원 화면: 합쇼체·명사형 라벨, "입주자", 다음 행동을 함께.
- 보호자(D 건강 소식 안): D 4-4 틀. 있었던 일 → 정해진 내용 → 문의처. 평가 내용은 넣지 않는다.
- 오류: 코어 순서(무엇 → 왜 → 할 일).
- 면접관: 문제 → 설계 판단(판정하지 않음, 단계와 계약 분리) → 데모.
**Terms we own:** 생활 지원 단계(직원·회원 화면 같은 이름). `senior-lab/03-copywriting/ideas/pms-core-billing/names.md` v3 확정, 직원 화면 이름은 2026-11-03 한글로 바꿈.
**Never use (and why):**
- "AI가 단계를 추천" — C에는 AI가 없다. 판정 대행으로 읽힌다.
- "계속 거주 보장" — 개정안 확정 전이고, 계약 조항을 확인하지 않았다.
- "자동으로 요금 반영" — 코어에 일할·계약 변경 API가 없다(Next).
