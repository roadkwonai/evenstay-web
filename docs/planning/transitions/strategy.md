## 1. 비전
**한 문장**: 입주자의 건강이 바뀌어도 무엇이 그대로이고 무엇이 더해지는지 먼저 알고, 서비스를 바꾸는 결정은 사람이 근거를 남기며 함께 내리게 한다.

- 영감: 회원이 "아파지면 여기서 계속 살 수 있나"(P-003)를 혼자 짐작하지 않고, 바뀌는 도움과 그대로인 방·계약을 화면과 직원의 말로 미리 듣는다.
- 지향: 단계 변경 하나마다 누가 살펴보고, 누가 설명하고, 회원이 무엇이라 했고, 누가 왜 정했는지가 한 이력으로 남는다.
- 지키는 가치
  1. **사람이 정한다**: 시스템은 단계를 판정하거나 추천하지 않는다. 평가를 기록한 사람, 제안한 사람, 결정한 사람이 화면에 이름으로 보인다.
  2. **제안자와 결정자는 다르다**: 한 사람이 혼자 단계를 바꾸지 못한다.
  3. **단계는 양쪽으로 바뀐다**: 회복하면 이전 단계로 돌아간다. 번호를 매기지 않는다(장기요양 인정 등급과 헷갈림 방지, C `names.md` 기준 3).
  4. **단계와 계약은 따로다**: 단계가 바뀌어도 입주 계약과 청구는 서명 없이 바뀌지 않는다.
  5. **본 일만 적는다**: 점수·병명·진단·추천 칸이 없다(B "관찰한 사실만" 원칙과 같음).

- **왜 S1이 먼저인가**: 퇴원은 언제 생길지 정해진 사건이고, 평가 → 제안 → 결정 흐름을 한 번에 보여 줄 수 있다. 데모 주인공 이은숙의 이야기(사별 뒤 1인 거주 → 12월 입원·퇴원)에 자연스럽게 이어진다 [가설: 데모 설득력].
- 개정안 맥락: 2026-10-12에 보도된 노인복지법 시행규칙 개정안(입법예고 2026-10-13~11-23)은 건강이 나빠져도 장기요양급여 같은 서비스를 받아 독립생활을 유지할 수 있으면 노인복지주택에 계속 거주할 수 있게 한다 [사실, A3 https://www.mt.co.kr/policy/2026/10/12/2026101210070797563 · E12 https://www.imaeil.com/page/view/2026101215574176948, 2026-10-12. 입법예고 2026-10-13~11-23, 확정 전]. 확정되면 S2가 커진다 [추정].
- 한 시설 사례에서 건강 단계는 "일반 → 생활보조거실 → 노인요양원 연계"로 나뉜다 [사실, A15 https://www.heraldk.com/article/2026033018425341429, 2026-03-30]. 평균 거주 7.3년, 평균 연령 84세다 [사실, A6 https://www.heraldk.com/article/2026062013480077891, 2026-06-20]. 다른 시설의 단계 규칙은 [미확인].

## 5. 트레이드오프 — 하지 않을 것
| 하지 않을 것 | 이유 |
|---|---|
| **장기요양 등급 판정** | 공단 업무다. C는 공단 결과를 옮겨 적는 칸만 둔다(`ltcGrade`). 단계 이름에 번호를 붙이지 않는 것도 같은 이유다 |
| **요양 급여 청구** | 노인복지주택은 민간 계약 기반이다(target-companies) [사실, S6]. 급여 청구는 외부 기관 몫이다 |
| **의료 판단** | 진단명·진료 결과·처방 칸이 없다. 기억·판단 관련 칸은 관찰 글과 검사 안내(치매안심센터)만 받는다 |
| **퇴거 결정** | 단계 변경은 계약을 끝내지 않는다. "거처 상담"도 상담을 시작한다는 결정일 뿐이다. 퇴거 접수는 코어에서 본인 또는 SIGN_CONTRACT 대리인 요청으로만 한다(코어 3-1) |
| 단계 판정·추천(점수, 규칙 엔진, AI) | 근거를 설명하기 어렵고 책임이 흐려진다(숏리스트 C 가장 위험한 가정: 낙인·퇴거 근거 오용) |
| 요금 자동 반영 | 코어 요금표는 체결 때 고정되고 일할 계산이 없다. 계약 변경 API는 코어 Next다 [사실, 코어 `tech-design.md` 4절·8-2]. C는 "계약 변경 필요" 표시와 경리 확인할 일 한 줄까지만 한다(어느 방향으로 바꾸든 같다) |

| 효과 수치 주장("퇴원 후 공백이 사라짐" 등) | 측정한 적이 없다(value-prop "쓰지 않기로 한 문장") |

**좁혀서 얻는 것**: "시스템이 판정하지 않는다"가 설계 전체(데이터 모델에 점수 칸 없음, 결정자 분리, 계약 분리)로 증명된다. 면접관에게 개정안의 "서비스를 받으며 계속 거주"를 PMS로 어떻게 다루는지를 판단 엔진 없이 보여 준다.

## 6. 핵심 지표
- **North Star 후보** [미정]: "근거가 모두 붙은 단계 변경 결정의 비율" = (평가 기록 1건 이상 + 입주자 설명·의견 기록 + 제안자 ≠ 결정자 + 결정한 까닭이 있는 결정) ÷ 모든 단계 변경 결정. 시스템이 이 조건을 강제하므로 MVP에서는 늘 100%이고, 실서비스에서 의미 있는 지표인지는 [미정]이다. 대안 후보: 퇴원 뒤 첫 평가까지 걸린 날(P-020), 시간 겹침이 서비스 날 전에 처리된 비율(P-019). 효과 목표치는 정하지 않는다.
- **OMTM (MVP 동안)**: 데모 6단계가 한 번에 통과하고, 권한·전이 표 테스트가 모두 통과한다(`prd.md` 3절 KR).
- 확인 방법은 데모와 자동 테스트만 쓴다. 실서비스 효과는 [가설]이다.

## 7. 성장
- **영업 주도(Sales-Led)**: 운영사가 PMS 전체를 도입할 때 붙는 모듈이다 [추정]. 개인 회원이 따로 가입하는 제품이 아니다.
- 확산 순서 [가설]: 시니어 레지던스 사업장 1곳 → 같은 운영사의 다른 사업장(단계 정의만 사업장마다 설정) → 개정안 확정 뒤 "외부 돌봄 병행" 단계가 많아지는 사업장.
- 임대주택(사업장 2)은 C를 쓰지 않는다. 자산 유형마다 모듈을 켜고 끄는 방식은 코어 ADR-1·3의 사업장 설정 위에서 한다.
- 단위 경제: 포트폴리오에서는 해당 없음.

## 9. 모방이 어려운 이유
- 이 모듈의 값은 기능 목록이 아니라 **코어·D와의 경계 설계**에 있다: 단계 변경은 계약을 바꾸지 않고, 보호자 공유는 D 동의를 거치고, 권한은 코어 `authorize()` 하나다. 같은 PMS 위에 있지 않으면 이 연결을 그대로 가져가기 어렵다 [추정].
- 평가 → 제안 → 설명 → 결정이 쌓인 이력은 운영사가 바뀔 때 넘길 기록이 될 수 있다(개정안의 위탁운영자 신고, P-021) [추정].
- 판정하지 않는 설계는 베끼기 쉽지만, 점수·추천을 팔고 싶은 경쟁 제품에는 오히려 선택하기 어렵다 [가설].
