이름은 확정되어 있어 `product-name` 스킬은 쓰지 않았다. 회원·보호자 화면은 **Evenstay 패밀리**(이븐스테이 패밀리), 직원 화면은 **보호자 포털·동의**다(`senior-lab/03-copywriting/ideas/pms-core-billing/names.md` v3 조합 1, 2026-11-02 확정, 2026-11-03 직원 화면 이름을 한글로 바꿈). 여기서는 화면 안 라벨만 정한다.

**라벨 원칙**
- 회원 화면의 주어는 회원이다. "보여 주기"처럼 회원이 하는 동작으로 쓴다.
- 보호자 화면은 "볼 수 있어요 / 볼 수 없어요" 두 가지만 쓴다. 왜 볼 수 없는지(미허용인지, 거둔 것인지, 확인 대기인지)는 보호자에게 구분해 보이지 않는다. 회원이 거둔 사실이 드러나면 가족 사이에 부담이 생길 수 있다 [가설].
- 직원 화면은 업무 용어(허용, 철회, 열람)를 쓴다.
- 영문 이름은 앱 아이콘과 첫 화면에만 쓴다. 기능 이름은 우리말.

- 생활 소식에는 회원이 오래 자리를 비우신 날과 돌아오신 날도 들어간다(F18, 카피 4-7). 이유, 종류, 가신 곳은 들어가지 않는다.
- 생활 소식 글 제목은 "○월 ○주 생활 소식"(예: 11월 첫째 주 생활 소식).

  | 입주일 | 입주일 | 입주하신 날 |

### 1-1. B 결과 알림의 자리 (2026-11-03, 허브 요청)
B(안심 알림)는 직원이 조치를 기록한 뒤 보호자에게 결과를 알린다(예: 밤사이 침대를 떠났다 돌아오신 일, 119 신고와 병원 이송). 이 알림을 보낼지 회원이 어디서 정하는지를 정했다.

**결정: 다섯째 항목을 만들지 않고 "건강 소식" 안에 둔다.** 회원은 "소식 함께 보기"의 건강 소식 한 곳에서 정하고, B 화면에는 따로 정하는 곳을 두지 않는다.

| 선택지 | 판단 | 이유 |
|---|---|---|
| 건강 소식에 넣기 | **채택** | 결과 알림은 몸과 안전에 관한 기록이다. 119 신고, 병원 이송은 이미 건강 소식의 예("병원에 가신 일")와 같다. 민감정보로 다루고 별도 동의를 받는 쪽이 안전하다(G14) [추정. 법률 검토]. 회원이 정할 항목이 넷으로 유지된다 |
| 다섯째 항목 "안심 알림" 추가 | 제외 | 119 이송 같은 일은 두 항목에 동시에 걸려 어느 동의를 따를지 모호하다. 내용이 건강정보라 이 항목도 별도 동의가 필요해져 80대 회원에게 비슷한 동의가 두 번 나온다. "안심 알림"은 B 회원 화면(호출벨, 침대 센서)의 이름이라, 서비스를 쓸지에 동의하는 것처럼 읽힌다. "안부"를 B와 겹친다고 뺀 판단과도 어긋난다 |
| 생활 소식에 넣기 | 제외 | 생활 소식에는 건강 관련 문장을 넣지 않기로 했다(`copy.md` 4-2). 별도 동의 없이 건강 관련 기록이 나가게 된다 |
| 다른 방식: 비상 연락처로만 | 일부 채택 | 119 신고나 병원 이송 때 직원이 전화하는 것은 동의 항목과 따로 둔다. 입주 계약의 "급할 때 연락할 분"(코어)에게 거는 전화다 [가설: 코어 계약에서 확정, 법률 검토]. 앱에 남는 기록은 건강 소식을 허락받은 보호자에게만 보인다 |

**건강 소식 안의 종류 표시** (보호자 목록에서 한 줄 앞에 붙는 말)
| 코드 (출처) | 라벨 |
|---|---|
| `SAFETY_SIGNAL` (B 결과 알림) | 직원이 다녀간 일 |
| `HOSPITAL_TRANSFER` (B 또는 간호 기록) | 병원에 가신 일 |
| `CARE_NOTE` (간호·생활지원 기록) | 그 밖의 건강 기록 |
| `CARE_STAGE_CHANGE` (C 생활 지원 단계 결정) | 생활 지원 단계가 바뀐 일 |
| `EXTERNAL_CARE_START` (C 다른 기관 돌봄 시작) | 다른 기관 돌봄이 시작된 일 |

- C 종류는 결정된 것만 들어온다. 평가 내용, 회원 의견, 결정 전 제안은 보호자에게 가지 않는다(C 카피 4절). 라벨은 C `names.md` 7절과 같다. 다른 기관 돌봄이 끝난 일(`EXTERNAL_CARE_END`)은 Next라 넣지 않았다.

- 보호자에게 가는 알림 문자에는 "건강"이라는 말과 내용을 넣지 않는다. 잠금 화면에 보일 수 있고, 그만 보여 주기가 문자에는 미치지 못하기 때문이다(`copy.md` 4-3).
- 발신 머리말은 D와 같게 **[Evenstay 패밀리]**로 한다. 보호자가 같은 회원의 소식을 두 가지 이름으로 받지 않게 하기 위해서다.

## 3. 허락 상태 (ConsentStatus)
| 코드 | 직원 화면 | 회원 화면 | 보호자 화면 | 버튼 (회원 화면) |
|---|---|---|---|---|
| `NOT_GRANTED` (기본값) | 미허용 | 안 보여요 | 볼 수 없어요 | [보여 주기] |
| `PENDING_MEMBER_CONFIRMATION` | 입주자 확인 대기 | 회원님 확인을 기다려요 | 볼 수 없어요 | [확인하기] |
| `GRANTED` | 허용 | 보여요 | 볼 수 있어요 | [그만 보여 주기] |
| `REVOKED` | 철회 (일시) | 안 보여요 (○월 ○일부터 그만 보여 줌) | 볼 수 없어요 | [다시 보여 주기] |

- 켜고 끄는 스위치보다 글이 적힌 버튼을 쓴다. 스위치는 지금 켜진 상태인지 헷갈리기 쉽다 [추정. NEED: 회원 사용성 확인].
- 직원이 대신 설정하면 `PENDING_MEMBER_CONFIRMATION`이 되고 회원이 확인해야 `GRANTED`가 된다. 확인 전에는 보호자에게 보이지 않는다.
- 대리인이 설정한 경우 회원 화면에 "대신 처리하실 분 ○○○ 님이 정했어요"를 함께 쓴다.

**건강 소식 별도 동의 상태 (SensitiveConsent: HEALTH)**
| 코드 | 직원 화면 | 회원 화면 |
|---|---|---|
| `AGREED` | 건강정보 별도 동의 완료 (일시) | 건강 소식을 나누는 데 따로 동의하셨어요 |
| `NOT_AGREED` | 건강정보 별도 동의 없음 | 아직 따로 동의하지 않으셨어요 |
| `WITHDRAWN` | 건강정보 별도 동의 철회 (일시) | 동의를 거두셨어요 |

- 별도 동의는 보호자마다 받는다(누구에게 주는지가 동의 내용이기 때문) [추정. 법률 검토 필요].

| `WeeklyReport.status` DRAFT / IN_REVIEW / SENT | AI 초안 / 검토 중 / 발송 완료 | (발송된 것만 보임) | (발송된 것만 보임) |

- 회원에게는 열람 거부 기록을 보이지 않는다. 가족이 "보려다 막혔다"는 사실이 회원에게 부담이 될 수 있다 [가설]. 직원 화면에서만 보인다.

## 5. 메뉴 이름
| 화면 | 메뉴 |
