# 결과 중심 로드맵 — 생활 요청 (life-requests)

상태: 승인(2026-11-04, 사용자 "보류된것 승인해") · 작성: 2026-11-03 · 방법: `outcome-roadmap` 스킬(만들 것 → 이루려는 결과로 바꿔 쓰기, "[누가] [무엇을] 하게 해서 [무엇이 좋아진다]", 결과를 확인할 신호와 순서·의존). 파일 이름은 이 폴더 규칙대로 `roadmap.md` · 변경: 2026-11-04 전체 리뷰 보완(사용자 재승인 2026-11-04)
입력: `strategy.md`, `prd.md` 7·14절, `tech-design.md` 10절(모두 초안)

> 표기 규칙은 `strategy.md`와 같다. 효과 수치를 목표로 쓰지 않는다. 포트폴리오에는 실제 이용자가 없으므로 "결과를 확인할 신호"는 데모·테스트에서 보이는 사실이다.
> 기간은 상대 기간이다. 날짜를 약속하지 않는다.

## 전략 맥락
- 비전: 어떤 길로 말한 부탁이든 맡을 직원에게 닿고, 입주자의 확인까지 기록으로 남는다(`strategy.md` 1절).
- 북극성 [가설]: 입주자 확인으로 끝난 요청의 비율. MVP에서는 측정 대상이 없어 계산이 맞는지만 보인다.
- 순서 원칙: (1) 상태 기계 하나를 먼저 단단하게 → (2) 들어오는 길을 하나씩 더함 → (3) 나가는 길(청구, 대시보드)을 붙임. 다른 모듈 변경이 필요한 결과는 그 모듈이 준비된 순서로 붙인다.

| 만들 것 (output) | 결과 (outcome) | 결과를 확인할 신호 |
|---|---|---|
| 요청 모델·상태 기계·전이 기록(F11), 회원 올리기(F1), 대신 등록(F2) | 회원과 프런트가 앱이든 전화든 같은 요청으로 올리게 해서, 부탁이 메모에서 사라지지 않게 한다 | 두 길에서 들어온 요청이 같은 목록에 들어온 곳과 함께 보인다(통합 장면 L1·L2) |
| 직원 목록(F3), 배정(F4), 처리(F5), 기한(F9) | 담당 직원이 오늘 할 일과 기한 지난 일을 한 목록에서 알게 해서, 다시 묻는 일을 줄인다 | 통합 장면 L3·L5. 기한은 직원 응답에만 있다(KR3 테스트) |
| 입주자 확인·다시 열림·대신 기록(F6), 7일 닫힘(F7), 취소(F8) | 입주자가 확인해야 요청이 끝나게 해서, "끝났다"를 직원 혼자 정하지 않게 한다 | 통합 장면 L4, 전이표 테스트 통과(KR2) |
| (P1로 옮김, 2026-11-04) 안심 알림으로 옮기기(F10, B 목업 먼저) | 몸이 불편하다는 요청이 생활 요청 목록에 묻히지 않게 직원이 바로 안심 알림 당번에게 넘기게 한다 | 통합 장면 부록. 옮긴 뒤 생활 요청에는 옮긴 기록만 |
