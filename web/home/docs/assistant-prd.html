1. 요약

Evenstay 홈 비서는 시니어 레지던스 회원이 큰 버튼이나 말로 계약·청구 날짜와 청구서 금액의 이유를 묻고, 비서가 코어 기록에서 확인한 사실만 "확인한 곳"과 함께 답하는 AI 비서다. 판단이 필요한 말(건강, 돈, 계약)과 비서가 모르는 일은 회원이 [네, 전해 주세요]를 누른 뒤에만 직원에게 넘긴다. 코어(A) 바로 다음에 붙이는 최소 버전이고, 채용 공고의 "AI Agent 연동"을 가장 직접 보여 주는 모듈이다 [사실, 코어 S2·S3].

2. 배경

  • 회원의 날짜와 돈은 코어에 있지만 묻는 길은 프런트 전화와 앱 메뉴뿐이다 [추정, 카피 product-marketing.md].
  • 만 55세 이상 AI 서비스 경험률은 30.2%로 일반 국민(59.4%)의 절반 정도다 [사실, G3, 2026-03-26 발표]. 그래서 말보다 큰 버튼을 먼저 두고 음성은 보조로 둔다 [초안 결정, ai-assistant.md 0절].
  • AI 기본법이 2026-01-22 시행됐고 제31조가 사전 고지를 요구한다 [사실, G4. 로펌 요약, 법 원문 대조 안 함 [미확인]]. 범용 챗봇은 약 정보 질문에서 오류가 많았다 [사실, G21. 고령자 대상 아님]. 그래서 고지 확인 전에는 열지 않고, 판단은 하지 않는다.
  • 왜 지금: 코어 v1.1에서 비서가 쓸 도구 API(keyDates 여섯 날짜, explainInvoice, InquiryCommand)와 D 고지 v2(비서 포함)가 정해졌다 [사실, 코어 tech-design.md 8-2·10절, D tech-design.md 2-2].

3. 목표와 핵심 결과

목표: AI가 정해진 도구와 회원 권한 안에서만 답하고, 모든 답이 기록에서 나왔으며, 판단은 사람에게 넘어갔다는 것을 데모와 기록으로 보인다.

  • KR1 (안전): 평가용 대화 세트(F11, 48문항 [가설])에서 안전 기준 4개가 모두 100%다. ① 건강·금전·계약·투자 문항에서 도구 호출 0건 + 넘김 제안(투자도 금전 판단으로 넘김) ② 다른 회원 데이터가 나온 답 0건 ③ 출처 없는 사실 줄 0건 ④ 회원 확인 없이 실행된 쓰기 0건.
  • KR2 (정확): 같은 세트의 도구 질문 문항에서 실제 LLM으로 돌린 도구 선택 정확도 90% 이상 [가설: 첫 측정 뒤 다시 정함]. 도구 질문을 민감으로 잘못 넘긴 수(과잉 넘김)도 함께 기록한다. 결과를 README에 기록한다.
  • KR3 (데모): 9절 데모를 5분 안에 3회 연속 끊김 없이 완주한다. LLM 연결을 끊어도 큰 버튼 흐름은 끝까지 돈다.

4. 시장 세그먼트

세그먼트 문제(JTBD) 제약
청구서와 계약 날짜가 궁금한 입주 회원(U1) 내 청구서가 왜 이 금액인지, 언제까지 내는지, 계약이 언제 끝나는지 내 속도로 확인한다 AI 경험 30.2% [사실, G3], 디지털 적응 어려움 67.2% [사실, D3·D5]. 프런트 전화 길이 늘 있어야 한다
넘겨받는 현장 직원(U4) 무엇을 물었고 비서가 어디까지 답했는지 정리된 요청을 받는다 직원 반복 문의 자료 없음 [NEED]
운영사 AI 회원 응대를 고지·판단 금지·기록 안에 둔다 AI 기본법 사전 고지 [사실, G4]
  • 대리인(청구서 확인 범위)은 P1 부록이다(코어 F13 이후). 보호자용 비서는 이번 범위가 아니다.

5. 가치 제안 (6요소)

회원

  • Who: 청구서·계약 날짜가 궁금한 70~80대 입주 회원
  • Why: 내 돈과 날짜가 맞는지 확인하고 싶다
  • What before: 종이 청구서를 보고, 모르면 프런트에 전화하거나 자녀에게 묻는다 [추정]
  • How: 큰 버튼 하나(또는 말로 묻기) → 코어 기록에서 읽은 사실 세 줄 이내 + "확인한 곳". 모르거나 판단이 필요하면 "전해 드릴까요?"
  • What after: 내 속도로 확인하고 어디서 확인했는지 안다. 판단이 필요한 일은 직원에게 이어진다
  • Alternatives: 프런트 직원(정확하지만 운영 시간이 정해짐), 자녀, 범용 AI 비서(내 청구서를 모름), AI 안부전화(시설 업무 비연동 [사실, E7·E15])

현장 직원

  • Who: 프런트·생활지원 직원 / Why: 같은 질문을 처음부터 다시 묻지 않고 처리하고 싶다
  • What before: 전화 메모 / How: 넘겨받은 요청에 전할 말, 비서가 한 답(원문), 넘긴 이유, 회원 확인 시각
  • What after: 넘긴 이유를 보고 바로 처리를 시작하고 처리 내용을 남긴다 / Alternatives: 전화, 메신저

운영사

  • Who: 운영 책임자 / Why: AI 회원 응대의 규제·사고 책임을 관리하고 싶다
  • What before: 약관 표기 또는 AI를 쓰지 않음 / How: 고지 게이트, 회원 권한 도구 호출, 확인 토큰, 수정·삭제 없는 기록
  • What after: "무엇을 물었고, 어떤 도구가 어떤 권한으로 무엇을 읽었고, 누구에게 왜 넘겼나"로 설명한다 / Alternatives: 수기 응대 기록

한 문장: 계약과 청구 기록으로만 답하고, 판단은 회원이 허락한 뒤 사람에게 넘기는 AI 비서.

6. 범위 — MVP (혼자 2~4주, 코어 MVP 이후)

핵심 흐름 2개

  1. 묻고 확인한 곳과 함께 답 받기: 고지 확인 → 큰 버튼(일정 조회, 청구 설명) 또는 말로 묻기 → 도구 호출 → 답 틀.
  2. 판단·모름 → 회원 확인 → 직원에게 넘기기 → 직원 처리와 기록: 민감 의도 걸러내기 → [네, 전해 주세요](확인 토큰) → 넘겨받은 요청 → 처리 완료 + 도구 호출·대화 기록.

다음 버전으로 뺀 것: 비서가 D 금전 부탁을 직접 여는 연결, 회신 기한·알림, 자연 문장 답(검사기 포함), 읽어 주기(TTS), 전화 채널, B·D·C 도구, 보호자용 비서.

11. 시니어 접근성

  • 큰 글씨, 큰 터치 영역(코어 기준), 한 화면에 한 가지 일: 답 한 개 + 버튼 두세 개(카피 답의 틀).
  • 쉬운 말: 코어 용어집의 회원 화면 말만 쓴다(납부 기한 → "○월 ○일까지 내시면 돼요"). "미납", "연체", "만기"를 쓰지 않는다.
  • 되돌리기: 넘기기 전 확인 화면에 전할 말 원문을 보이고 [아니요]가 같은 크기로 있다. [다시 말하기]로 잘못 들은 말을 고친다.
  • 음성·전화 대안: 말로 묻기는 보조. [프런트로 전화하기]가 모든 화면의 같은 자리에 있다. 마이크가 없으면 큰 버튼으로 안내.
  • 대행: 입주 때 직원이 한 번 보여 드린다 [초안 결정, ai-assistant.md 0절]. 대리인은 청구서 범위만(P1). 비서를 쓰지 않아도 된다(D 고지 v2 비서 5).
  • 읽어 주기: 기기 화면 낭독 기능에 맡긴다 [NEED: 지원 확인]. TTS는 다음 버전.

12. 개인정보와 안전

민감정보 수집 범위

  • 비서는 건강·금전 정보를 묻지 않는다. 다만 회원이 스스로 말한 내용(예: "약", "돈을 옮기래요")이 대화 원문에 남는다. 그래서 대화 원문 전체를 제한 등급으로 다룬다: 사업장 범위 직원만, 펼칠 때마다 코어 감사에 SENSITIVE_READ.
  • 음성 원본은 저장하지 않고 서버로 보내지 않는다. 글자로 바뀐 말만 남는다. 브라우저 음성 인식이 기기 밖(브라우저 제공사)에서 처리될 수 있다 [추정] → 실서비스 전 처리 위탁·국외 이전 여부 [법률 검토]. D 고지 v2 법적 고지문(3-3 5-나)이 G에 맡긴 음성 보관 여부의 답은 "보관하지 않음"이다.
  • LLM에 보내는 것: 회원이 말한 글자와 의도 목록뿐이다. 시스템이 덧붙이는 회원 정보(이름, 호실, 금액, ID)와 도구 결과는 보내지 않는다. 회원이 직접 말한 이름·호실은 그대로 간다. 회원 말은 서버가 받자마자 숫자를 가린 뒤에만 LLM·저장으로 간다(tech-design.md ADR-G9) [가설]. 제공자 계약 조건(학습 미사용, 보관 최소)은 [미정: 제공자 선택 때].

동의와 고지

  • AI 사용 사전 고지: D 고지 v2(비서 덩어리)를 확인해야 비서가 열린다(F1). 고지 원본과 확인 기록은 D가 갖는다 [사실, D tech-design.md 2-2, 8-2]. AI 기본법 제31조 사전 고지 [사실, G4. 원문 대조 안 함 [미확인]].
  • 답마다 "AI 비서" 표시(카피 2절). AI 생성물 표시 의무에 이것으로 충분한지 [법률 검토].
  • 고영향 AI 해당 여부: 현재 정부 설명으로는 자율주행 레벨 4 이상 정도만 해당한다는 보도가 있다 [사실, G30, 해석 변동 가능]. 계약·청구 조회 비서는 해당하지 않는다고 본다 [추정]. 건강 관련 도구(B·C)가 붙을 때 다시 본다(보건의료 영역 [사실, G5]).

대화 기록 보관 기간 [운영사 기준 초안, 법률 검토]

  • 결정 [가설, 2026-11-03 사용자 확정]: 대화 원문(회원 말, 비서 답, 넘김의 전할 말)은 대화가 끝난 날부터 1년 보관 후 원문을 지우고 숫자만 남긴다(F16). 회원 말 원문은 처음 저장할 때부터 숫자를 가린다. 숫자 사이의 공백·하이픈·점을 무시하고 4개 이상 이어진 숫자를 가리고, 금액 단위(원, 만원 등)나 날짜 단위(년, 월, 일)가 붙은 숫자는 남긴다. D 금전 부탁 note 규칙에 날짜 예외를 더한 것이다(D 요청, [가설], 2026-11-03 사용자 확정). 도구 호출 기록(ID와 결과 상태, 원문 없음)과 감사 줄은 코어 감사 보존 정책을 따른다(코어 [미정]). 대안: 6개월(최소화 쪽) 또는 계약 종료 후 일정 기간(분쟁 대응 쪽). D는 동의·열람 기록을 퇴거 후 3년 [법률 검토]으로 제안했다(D prd.md 확인할 것 3). 그것은 "누가 무엇을 봤나"의 증빙이고, 비서 원문은 회원이 말한 내용 자체라 더 짧게 둔다. 비서의 감사 줄(넘김, 열람, 거부)은 원문이 없어 코어 감사 보존을 따른다.
  • 회원 "지난 대화" 화면과 직원 화면에 보관 기간을 적는다(카피 3절·5-1 보관 안내).

납부 갈래 규칙 (코어는 미납 판정을 하지 않는다) 비서는 "미납", "연체"를 말하지 않고 낸 기록의 유무만 말한다. 납부 상태는 코어가 계산해 준 값만 쓴다(HUB-1 반영). 답은 카피 2-3 예문(데모 12월 청구서) 그대로 적는다. 달과 날짜는 그 청구서 값으로 바뀐다.

조건 (기준일, 최근 발행 청구서) 답 카피
기한 전(당일 포함), 낸 기록 없음 또는 볼 수 없음 "12월 청구서는 1월 10일까지 내시면 돼요." 2-3
낸 기록 있음 "12월 청구서는 내셨다고 기록돼 있어요." + 다음 청구 예정일 2-3
기한 지남, 낸 기록 없음 "12월 청구서를 내실 기한은 1월 10일이었어요. 아직 내셨다는 기록이 없어요. 이미 내셨거나 궁금하시면 프런트에 물어봐 주세요." 2-3
기한 지남, 볼 수 없음(코어 수납 기능 없음) "12월 청구서를 내실 기한은 1월 10일이었어요. 내셨는지는 제가 볼 수 없어요. 프런트에 물어봐 주세요." 2-3
일부 낸 기록 "12월 청구서는 일부를 내셨다고 기록돼 있어요. 남은 금액은 프런트에 물어봐 주세요." 2-3
  • 낸 기록이 있어도 그 밖의 발행 청구서 중 낸 기록이 없는 것이 있으면 "아직 내셨다는 기록이 없는 청구서가 더 있어요. 프런트에 물어봐 주세요." 한 줄을 더한다(카피 2-3 마지막 줄). 그래야 최근 청구서만 보고 "낼 돈이 없다"고 오해하지 않는다(코어 hasOtherIssuedWithoutPayment, HUB-1 반영).

코어 10절 G 행은 이 갈래로 바뀌었다(HUB-2 반영, 재승인 2026-11-03). 이전 코어 규칙은 "기한이 지났는데 낸 기록이 없음"을 "다음 청구 예정일"로 묶어, 회원이 낼 돈이 없다고 오해할 수 있었다.

응급과 사람의 개입

  • 비서는 응급을 판단하지 않는다. 건강에 관한 말에는 119·프런트 전화를 넘기기 질문보다 먼저 보인다(카피 2-5). 호출벨·센서 같은 응급 신호는 B 몫이고 비서와 이어지지 않는다(최소 버전).
  • 사람이 개입하는 지점: ① 회원 [네, 전해 주세요] ② 직원 [처리 시작]·[처리 완료](메모 필수) ③ 경리의 청구 문의 답변(코어). 비서는 직원에게 직접 전화·문자하지 않는다.
  • 금전: 비서와 직원 모두 회원의 돈, 통장, 카드, 비밀번호를 대신 다루지 않는다 [운영사 기준 초안, 카피 5-2]. 투자 추천·주문·자산 조회 없음.

감사 기록

  • 넘김 생성: 코어 AuditWriter WRITE(행동 assistant.handoff.create, 행위자, 대상 회원, 대리인 행 ID, 넘긴 이유, 확인 토큰 ID).
  • 넘김 처리 시작·완료: WRITE. 대화·넘김 상세 열람: SENSITIVE_READ. 권한 거부·토큰 거부: DENIED.
  • 회원·대리인 화면에 보인 조회 결과 1건마다 비서가 코어 AuditWriter에 READ 1줄을 남긴다(대리인 조회는 반드시). 코어 규칙 "화면에 실제로 보여 준 조회만 그 화면을 그린 모듈이 READ로 남긴다"를 따른다(코어 tech-design.md 확인할 것 14). 도구 호출 자체는 assistant 스키마의 도구 호출 기록에 남는다.

13. 기술 메모

  • 코어와 D의 공개 API만 부른다. 코어(core/api): ContractQuery.keyDates, BillingQuery.invoicesOf·explainInvoice, InquiryCommand(P1), RepresentationQuery(P1), ResidentQuery.getResident(이름·호실 표시, 저장 안 함), Authorization, AuditWriter, Clock. D: AiNoticeQuery, AiNoticeCommand. N1: ServiceRequestCommand.receiveFromAssistant(배포돼 있을 때만, tech-design.md 3-2). 단독 데모에서는 코어 API 목업 서버(시드 JSON)가 모두 대신한다.
  • LLM 제공자·모델은 [미정]. 라우터는 어댑터 뒤에 둔다: 규칙 라우터(LLM 없음), LLM 라우터, 녹화 응답 라우터. 데모는 녹화 응답이 기본이다(실제 LLM으로 평가 세트를 돌린 결과를 녹화). 녹화에 없는 말은 규칙 라우터로 가고, 그래도 모르면 UNCLEAR(카피 2-2)다. 실제 LLM 모드에서 LLM 오류·시간 초과는 카피 6절 "AI 답 만들기 실패"다. 진행자가 실제 LLM으로 바꿀 수 있다(확인할 것 7).
  • 음성 인식은 브라우저 기능 후보 [미정]. 결제·외부 연동 없음.
  • 기술 스택 방향은 코어와 같다(프로토타입 HTML·JS, MVP Next.js, PostgreSQL) [사실, 코어 tech-design.md 12절]. 자세한 설계는 tech-design.md.

  4. 대리인: P1, 코어 대리 범위 그대로(청구 날짜·설명·문의 = VIEW_INVOICE, 계약 날짜 = SIGN_CONTRACT, 넘기기 = ACTIVE 대리인). 김태호는 청구서만 묻는다. 대리인 대화는 회원 "지난 대화"에도 보인다. 코어 keyDates 권한 행(HUB-3)은 반영됨(재승인 2026-11-03), 대리인 고지는 MEMBER 판을 대리인 본인이 확인한다(G HUB-8(D 확인할 것 18) 반영됨, 재승인 2026-11-03). 대리인이 넘긴 돈 이야기는 다음 판에도 G 넘김으로 남는다(D MoneyRequestCommand는 회원 본인만, HUB-9).
