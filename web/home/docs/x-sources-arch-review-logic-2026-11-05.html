이 문서에 나오는 용어

누르면 용어집의 풀이가 열립니다.

별도 에이전트가 설계안, 웹 문장, 도식 원본을 처음 읽고 지적한 내용이다. 웹 조사는 하지 않았다. 지적은 설계안 재검토에 반영했고, 줄 번호는 재검토 전 문서 기준이다.

요약

찾은 결함은 25건이고 높음 10, 중간 13, 낮음 2다. 단계 번호, 마일스톤 이름, 비용 합계는 대체로 맞는다. 큰 문제는 3·4단계 구성요소의 소유 모듈, 실행 주체, 트랜잭션 경계가 정해져 있지 않다는 점이다.

먼저 고칠 곳은 네 가지다.

  • 승인 재검증 위치
  • 시스템 작업의 RLS
  • 세 가지 비동기 기록의 역할
  • 안심 경로의 감시 방향

표기: 설계안은 senior-housing-architecture-design.md, 웹은 architecture.json이고, 숫자는 설계안 줄 번호다.

찾은 내용

높음

1. 승인 재검증이 실행과 분리되어 있다

  • 위치: 설계안 6.3 승인(237), 4.2 4단계(144), arch-agent의 m-recheck → m-exec, 웹 flows.items[arch-agent].rules[1]
  • 문제: 재검증은 승인 시점에 하고, 실행은 그 뒤 직원의 별도 업무 명령이다. 그런데 "승인 소비와 내부 상태 변경은 한 트랜잭션"이라고 적었다.
  • 왜 문제인가: 승인과 실행 사이에 계약 버전이나 권한이 바뀌어도 통과한다. 지금 흐름으로는 한 트랜잭션이 성립하지 않는다. 업무 명령이 승인에 묶이는 방법도 없어 승인 없이 같은 명령을 낼 수 있다.
  • 고칠 내용: 업무 명령이 승인 ID를 필수로 받게 한다. 재검증과 승인 소비는 그 명령의 트랜잭션 안에서 target_version 조건부 갱신으로 처리한다. 도식의 재검증도 m-cmd 뒤로 옮긴다.

2. 3·4단계 구성요소에 소유 모듈이 없다

  • 위치: 4.2 3단계(137), 5절 규칙 4(170), 6.4(249), 10.3(385), stack-a2의 pgvector 선(M819 460 H921), arch-agent의 m-recheck·m-log
  • 문제: 문서, 청크, 벡터, 실행 기록, 승인 표, 체크포인트가 어느 스키마와 모듈에 속하는지 없다. AI 서비스는 업무 DB에 접근하지 않는데, 도식의 pgvector는 업무 RDS의 확장이다. 누가 임베딩을 쓰고 누가 검색하는지 정의되지 않았다.
  • 왜 문제인가: arch-agent는 코어가 실행 기록을 직접 읽고 쓰는 그림이다. ADR-2("코어는 어떤 모듈도 모른다")와 ADR-G3("코어가 G의 토큰을 검사할 수는 없다")에 어긋난다. 2.2의 "확인 토큰을 직원 승인으로 넓힌다"도 같은 충돌을 물려받는다.
  • 고칠 내용: 문서 모듈과 에이전트 모듈의 자리를 정한다. 예를 들어 documents 스키마와 assistant 확장을 두고, Python은 청크와 벡터를 코어 API로 돌려주며 체크포인트 저장소를 명시한다. 코어는 승인 내용을 모르게 하고, 소유 모듈이 검사한 뒤 코어 명령을 부르는 모양으로 도식을 고친다.

3. 비동기 에이전트 실행의 권한 주체가 없다

  • 위치: 5절 규칙 4·7(170, 173), 4.2 3단계 ③(138), 6.3 실행 기록 표(228), arch-agent의 m-read
  • 문제: 규칙 7은 범위를 "서버가 세션과 대조"한다고 한다. 하지만 하루를 넘기는 실행에는 세션이 없다. 규칙 4는 코어가 허용 필드만 넘기는 방식인데, 3단계 ③과 m-read는 AI 쪽이 업무 API를 부르는 방식이다.
  • 왜 문제인가: 작업자가 어떤 주체로 authorize()를 통과하는지 정해지지 않았다. SYSTEM:<모듈키>로 부르면 요청자 권한을 넘어 조회하게 된다. 재검증도 승인 시점에만 있어 도중 조회는 비어 있다. 서비스 간 인증도 없다.
  • 고칠 내용: 사람 대신 조회할 때 쓰는 위임 주체를 정의한다. 요청자, 범위, 만료를 서버가 저장하고 호출마다 현재 권한을 다시 평가한다. 코어가 넘기는 방식과 AI가 부르는 방식 중 3단계 기준을 하나로 정한다.

4. 시스템 작업의 RLS가 M1의 결정 사항에 없다

  • 위치: 9절 8번(346), 10.1 M1 결정 사항(361), 코어 tech-design.md 확인할 것 35의 (나)(다)
  • 문제: 1단계 작업자의 일(월 청구, 타이머, 디스패처)은 전부 사람 없는 작업이다. 이 작업의 범위가 [미정]인데 M1의 결정 사항은 "작업 실행, ORM, 인증"뿐이다. 모듈별 DB 역할 방식도 9절에 없다.
  • 왜 문제인가: 작업자는 변수가 없어 0행을 보거나, BYPASSRLS 같은 넓은 권한으로 돌아 RLS의 뜻이 사라진다. 그래서 "다른 사업장 ID가 막힌다"는 완료 기준이 API 경로만 증명한다.
  • 고칠 내용: M1 결정 사항에 시스템 작업 범위와 모듈별 DB 역할을 넣는다. 조사 문서 5절의 runAs와 "아웃박스에 site_id·actor_id 저장"을 설계로 옮긴다. 완료 기준에 작업자 경로의 사업장 격리 시험을 더한다.

5. 아웃박스, Modulith 이벤트 기록, JobRunr의 역할 경계가 없다

  • 위치: 4.2 1단계(125), 2.1 비동기 행(31), 6.3 재시도 한도(241), 코어 tech-design.md의 OutboxEvent 행
  • 문제: 세 가지가 모두 "저장, 전달, 재시도"를 하는데 구분이 없다. 모듈 간 이벤트가 어느 쪽을 타는지, 아웃박스가 JobRunr를 부르는지 알 수 없다. 재시도 한도는 AI 경로만 다룬다.
  • 왜 문제인가: 코어 아웃박스의 attempts(C는 5회)에 JobRunr 재시도와 어댑터 재시도를 곱하면 설계안이 경고한 곱셈이 업무 경로에서 그대로 난다. 소비자 멱등을 저장할 인박스도 없다. JobRunr 등록이 업무 트랜잭션에 묶이는지도 확인되지 않았다.
  • 고칠 내용: 표 하나로 역할을 정한다. 예를 들어 모듈 이벤트는 아웃박스만, 지연·반복 작업은 JobRunr만 쓰고 Modulith 기록은 쓰지 않거나 대체한다. 재시도 권한을 쓰는 층을 지정하고 처리 완료 표를 넣는다.

6. "안을 바꿔도 다시 작성하는 부분은 여기에 그친다"가 과장이다

  • 위치: 1절 2번(17), 3절 안을 옮기는 방법(99), 웹 plans.p
  • 문제: "프레임워크"라고 적었지만 Java와 TypeScript 사이 이동은 코어와 모듈 코드 전부와 시험의 재작성이다.
    • C안에는 코어 API가 없을 수 있어 OpenAPI 계약이 "유지"되지 않는다.
    • Next.js 서버 코드에 업무 로직이 있으면 화면의 데이터 계층도 바뀐다.
    • JobRunr와 Modulith 표는 A안 전용이다.
    • RLS 정책 본문도 Supabase 인증과 세션 변수 방식에서 달라질 수 있다.
  • 왜 문제인가: C안에서 A안으로 가는 비용을 작게 보이게 해 안 선택을 왜곡한다. C안을 고르면 M1을 사실상 두 번 만드는데 그 이전 작업은 어느 마일스톤에도 없다. C안의 "Next.js 서버 코드"는 루트 CLAUDE.md의 "Next.js는 app/·ui/에만"과도 충돌할 수 있다.
  • 고칠 내용: 이동 경로별로 표를 나눈다(C→B, C→A, A↔B). 각 경로에 유지, 변환, 재작성을 적는다. C안 코어는 프레임워크 없는 TS 패키지로 둔다고 명시하고, M2 시작 조건에 "C안이면 이전 완료"를 넣는다.

7. 외부 상태 점검이 안심 경로의 실패를 잡지 못한다

  • 위치: 6.1(187), 4.2 2단계 완료 기준(133), arch-signal의 f-silent(어댑터 → 점검), stack-a2의 점검 선(M144 89 H340 V196)
  • 문제:
    • 도식은 멈춘 어댑터가 자기 멈춤을 알리는 방향이다.
    • 인프라 도식의 점검은 ALB로만 간다. URL 점검으로는 API가 살아 있는 상태의 작업자 정지를 못 본다.
    • 설계안에 하트비트가 없다.
    • L3 이상이 멈추면 "직원 화면"도 같이 멈출 수 있다.
  • 왜 문제인가: "작업자가 멈추면 앱 밖 경로로 알림이 간다"를 판정할 구성이 없다. 안심 확인할 것 27의 주기, 도구, 받는 사람이 [미정]인데 9절에도 없다. 조사 8절의 하트비트 메트릭, 누락 경보, 두 갈래 수신도 빠졌다.
  • 고칠 내용: 어댑터와 작업자의 하트비트를 서버 또는 외부 감시가 시간으로 세게 한다. 도식 화살표 방향을 뒤집는다. 점검의 위치, 받는 사람, 제공자를 정한다. 건물 인터넷 단절 시 현장에서 어떻게 아는지를 적는다.

8. 안심 넘김을 청구 부하에서 지키는 규칙이 없다

  • 위치: 4.2 2단계(132), 단계별 제안 7절 레드팀 3번
  • 문제: 설계안은 큐 분리 이유로 "결제 웹훅이 문서 작업 뒤에서 기다리지 않게"만 든다. 그런데 문서 작업은 3단계이고 단계별 제안은 AI 작업을 Taskiq로 뺀다. 안전 경로인 넘김 타이머는 언급이 없다. 레드팀의 "청구 생성 중 넘김 지연 측정"도 옮겨 오지 않았다.
  • 왜 문제인가: 같은 이미지, 같은 작업자, 같은 DB에서 월 청구가 넘김을 늦출 수 있고 이를 측정할 기준이 없다. 업무별 큐가 JobRunr 공개판에서 되는지 근거도 조사 자료에 없다. 내 기억으로는 유료 기능일 가능성이 있으나 웹 확인은 하지 않았다.
  • 고칠 내용: 2단계 이유를 안심 넘김 격리로 바꾼다. 넘김 타이머 전용 작업자 또는 연결 풀을 둔다. 완료 기준에 "월 청구 중 넘김 지연 N초 이하"를 넣고, JobRunr 판별 조건을 8절에 적는다.

9. 모듈 도입 순서가 마일스톤과 연결되지 않아 의존이 뒤집힌다

  • 위치: 10.1 M2 ⑤(362), 10.2 건물 층(378), 10.3(385~392), 6.3 도구 접근(207)
  • 문제: 10.3은 M1 뒤 모듈을 하나씩 도입한다고만 하고 어느 마일스톤인지 없다. M2 ⑤의 현장 어댑터는 safety가 있어야 받을 곳이 있다. 6.3은 내부 도구 등록부(ADR-G2)가 1단계라는데, 그것은 assistant의 일이고 10.3에서 마지막이다. M1 작업 순서에도 없다.
  • 왜 문제인가: safety가 언제 들어오는지 없어 M2가 시작될 수 없다. 실제 입주자 데이터를 받는 시점에 family 동의가 필요한지도 정해지지 않는다.
  • 고칠 내용: 모듈을 마일스톤에 배치한다. 예를 들어 M1 뒤의 별도 줄 또는 M2 시작 조건으로 둔다. 도구 등록부의 단계를 하나로 고친다.

10. "2단계 조건"이 정의되지 않고, M2·M3 병행의 실체가 불분명하다

  • 위치: 3절 표(76), 4.1(114), 4.2 2단계 완료 기준(133), 10.1 M3(363), 9절 9·10번
  • 문제: 실제 입주자 데이터의 문턱이 "2단계 조건"인데 완료 기준 3개에 암호화, 접속기록 점검, 계정 분리, 법률 검토, 처리 지역이 없다. RPO·RTO 값도 [미정]이라 "확인"을 측정할 수 없다. M0의 "복구 요구 합의"와 M2의 "복구 목표 결정"도 겹친다. M3는 계약서 추출을 다루는데, 실문서 없이 완료하는지가 없다.
  • 왜 문제인가: 이 문턱은 설계안에서 가장 무거운 약속인데 판정 기준이 없다. M3가 가상 문서로 끝난다면 "성공 1건당 비용"은 실제 값이 아니다.
  • 고칠 내용: 2단계 완료 기준에 위 항목을 넣고 RPO·RTO 값을 M0 또는 M1에서 정한다. M3 완료 기준에 가상 문서로 판정한다고 적거나, M3 완료를 M2 완료 뒤로 둔다.

중간

11. 어댑터 버퍼 재전송과 멱등 키 규칙이 없다

  • 위치: 6.1(186), 6.5 파티션(272), 조사 문서 6.4(148), 안심 확인할 것 27
  • 문제: 단절 뒤 쌓인 신호가 한꺼번에 오면 이미 끝난 호출로 넘김 타이머가 도는지 정하지 않았다. 접점 출구는 이벤트 번호가 없을 수 있다. 그런데 설계안은 (출처, 업체 이벤트 번호)만 쓰고 조사 문서의 대체 키를 옮기지 않았다.
  • 왜 문제인가: 복구 순간에 2차 알림이 몰려 직원의 경보 피로를 만든다. 어댑터가 재시작 뒤 다른 번호를 내면 멱등이 깨진다.
  • 고칠 내용: 늦은 신호는 기록만 하고 알림은 내지 않는 기준 시간을 설정값으로 둔다. 번호 발급 주체와 재시작 시 보존, 대체 키를 6.1에 적는다.

12. 기준안 근거와 평가표가 A안 쪽으로 기운다

  • 위치: 1절 1번(16), 3절 평가표(78~89), 3절 약점(75), 6.6(283), 7절
  • 문제:
    • GPT 14.5와 1.2는 "JVM 경험이 깊으면", "AWS 기반이 있으면"이라는 조건부인데 그 조건은 미확인이다. 12행은 회사 현황을 모른다고 적었고, decisions.md에는 사용자 주력 언어 기록이 없다고 적혀 있다.
    • "공고 직무 연결 A 강함"은 기술 스택 항목이 빈 공고와 맞지 않는다. 조사 문서도 Spring을 업계 표준이라 주장할 수 없다고 했다.
    • "업무 정확성·복구 A 강함, B 보통"은 세 안이 같은 스키마와 아웃박스를 쓴다는 1절 2번과 충돌한다. B안 약점인 "팀 규칙으로 경계를 지킨다"도 5절 규칙 3("안이 달라도 같다")과 코어 12절의 CI 도구와 맞지 않는다.
    • A안 약점 "언어가 둘이다"는 3단계부터 Python이 들어와 셋이 되는 것을 숨긴다.
    • "서울 안 처리 A 강함"은 Sonnet 5·Opus 5일 때만 맞고, B안(AWS)도 같다.
    • C안 약점인 고정 송신 IP는 A안 비용에서도 NAT가 빠져 있어 같은 문제다.
    • 78행은 "안전 경로와 데이터 위치를 더했다"고 쓰지만 "공고 직무 연결"도 더했고 GPT의 "실제 성능"은 뺐다.
  • 왜 문제인가: 결론을 지지하는 판정이 근거 없이 쌓인 모양이다.
  • 고칠 내용: "포트폴리오 적합"은 제품 기준에서 분리한다. 조건을 표에 붙이고, 같은 구조의 항목은 같음으로 고친다. A안 약점에 언어 수와 큐 수를 단계별로 적는다.

13. 선택 기준 순서상 C안에 도달할 수 없다

  • 위치: 3절 선택 기준(93~97), dd-choose STEPS
  • 문제: 위에서 처음 맞는 곳에서 멈추므로 JVM이나 TypeScript 담당자는 2·3번에서 끝난다. C안은 둘 다 아닐 때만 나오는데 C안 코어가 TypeScript다. 5번은 둘 다 아닌 사람에게 Java 코어를 준다.
  • 왜 문제인가: 판단 흐름이 적합한 경우 표와 어긋난다.
  • 고칠 내용: "실제 데이터 없이 화면 검증이 먼저인가"를 2번으로 올린다. 5번의 기본값에는 이유를 붙인다.

14. 구성요소의 도입 기준이 단계의 진행 기준처럼 적혀 있다

  • 위치: 1절 3번(18), 8절 머리(313), 웹 timing.p, 용어집 "도입 기준"
  • 문제: 설계안은 "신호가 확인되지 않으면 다음 단계로 진행하지 않는다"고 쓰고, 웹과 용어집은 "더하지 않는다"고 쓴다.
  • 왜 문제인가: 설계안대로 읽으면 SQS 신호가 없을 때 3단계로 못 간다. Multi-AZ 신호는 관찰이 아니라 필수 조건이다.
  • 고칠 내용: 8절을 "그 구성요소를 더하지 않는다"로 고친다. 필수 조건과 선택 신호를 나눈다.

15. 결제 상태 설명이 승인된 코어 상태기계와 다르다

  • 위치: 6.2(194), arch-payment, 코어 tech-design.md 3-5
  • 문제:
    • 코어에서 PENDING_BANK_RESULT는 ExpectedPayment의 상태이고 배치가 따로 있다. 설계안 사슬은 동의, 상태, 매칭을 한 줄로 이었고 배치가 빠졌다. 동의가 매달 흐름의 시작처럼 그려졌다.
    • "알 수 없음"은 코어 상태에 없다.
    • 도식의 lookup은 성공으로만 가는데, 코어는 조회 뒤 사람이 닫는다.
    • REVERSED, EXPIRED, CANCELLED, 배치 거절, 대사 불일치도 없다.
  • 왜 문제인가: 시간 초과 때 재전송 금지 같은 핵심 판단이 어느 객체에서 일어나는지 알 수 없다. 응답 없음에 대한 규칙이 있어도 이중 출금을 막는 경로가 도식에 없다.
  • 고칠 내용: 객체별로 사슬을 나누고 코어 3-5를 그대로 그린다. 배치 전송 시간 초과가 어떤 상태인지 코어에 추가한다.

16. M1 작업 순서와 영역표에서 뒤로 밀린 것이 있다

  • 위치: 10.1 M1(361), 10.2 업무 코어 M2 "없음"(375), 4.2 2단계(131)
  • 문제:
    • authorize()의 ENFORCE 감사 기록은 ①에 필요하고 ③ 청구·수납은 아웃박스를 쓰는데, 변경 이력과 아웃박스가 ④다.
    • ExpectedPayment, 3자 대사, LedgerExportBatch는 코어 일인데 M1 ③에 없고 M2 코어 칸은 "없음"이다.
    • 봉투 암호화와 블라인드 인덱스가 M2에 있어 칸 형태와 검색 쿼리를 바꾸는데, 5절 규칙에 없다.
  • 왜 문제인가: M1을 끝낸 뒤 코어 모델을 다시 쓰게 되어 5절의 재작성 방지 목표가 깨진다.
  • 고칠 내용: 변경 이력과 아웃박스를 ① 뒤로 올린다. M1 ③에 비동기 수납 모델을 넣는다. 5절에 "민감 칸은 처음부터 암복호 포트 뒤"를 더한다.

17. 4단계의 필요 근거가 약하고 범위 전제가 어긋난다

  • 위치: 4.2 4단계(143~145), 4.3(160), 8절(323, 324), 9절 4번, stack-a5, dd-timing, 코어 범위 밖(project.md 12절)
  • 문제:
    • 에이전트는 조회와 제안까지만 하므로 재개 뒤 할 외부 효과가 없다. 그런데 완료 기준은 "같은 효과가 두 번 나지 않는다"이다.
    • 대상 예인 계약 변경은 코어의 "다음 버전" 범위이고, "영향 계산"의 주체가 없다. 비서는 금액 계산을 하지 않는다.
    • 실행기는 [미정]인데 4.3, stack-a5, dd-timing은 LangGraph로 고정했다.
    • Spring AI는 조사 노트상 승인 UI와 영속화를 주지 않는다.
    • M4 ③은 실행기 도입을 필수로 쓰지만 8절은 코드가 복잡해질 때다.
  • 왜 문제인가: 조사 노트의 "DB 상태 머신으로 충분" 판단과 맞서면서 근거 없이 프레임워크를 넣게 된다.
  • 고칠 내용: 4단계 기본을 DB 상태기계로 두고 실행기는 조건부로 표시한다. 영향 계산은 코어 코드로 적고 계약 변경 명령의 전제를 M4 시작 조건에 넣는다. 표와 도식에서 "실행기 미정"으로 맞춘다.

18. 회원 비서와 1단계 Bedrock의 단계가 어긋난다

  • 위치: 4.2 1단계(123, 126), 3단계(138), 6.3 질문 경로(220), stack-a1(Bedrock 실선 "의도 분류만"), 웹 figs.stack-a1, project.md 7절, 단계별 제안 1절(13행)
  • 문제: 설계안은 1단계 외부 연동이 목업이고 AI가 녹화 응답이라는데, 도식은 Bedrock 실호출이다. 회원 의도 분류가 어느 단계에서 실호출되는지 없다. 단계별 제안은 주간 리포트 초안을 1단계 어댑터에서 가능하다고 봤는데 설계안은 3단계로 옮겼다. family는 10.3에서 첫 모듈이다.
  • 왜 문제인가: 회원 발화가 언제 모델로 가는지가 실제 데이터 문턱과 처리 지역 판단의 핵심이다.
  • 고칠 내용: 회원 의도 분류와 리포트 초안을 표에 단계로 적는다. stack-a1의 Bedrock은 점선과 "녹화 응답 기본"으로 고친다.

21. 금액을 임베딩하지 않는다는 규칙이 계약서 검색과 충돌한다

  • 왜 문제인가: 규칙을 지키면 계약서 검색이 깨지고, 어기면 규칙이 거짓이 된다. 입주자 이름 같은 개인정보 청크 처리도 비어 있다.
  • 고칠 내용: 규칙을 "원장 값과 수납 기록은 넣지 않는다"로 좁히고, 계약서 안의 금액과 개인정보 처리 방식을 적는다.

22. 복구 뒤 삭제와 허락 철회가 되살아난다

  • 문제: 복원 뒤 절차는 결제와 ERP 대사뿐이다.

  • 고칠 내용: 복원 절차에 철회·삭제 이벤트 재적용과 그 시험을 넣는다. 전파 대상에 비동기 기록을 더한다.

24. RLS 풀러 문구와 연결 한도 공식이 현재 구성과 맞지 않는다

  • 위치: 6.5(262)

  • Multi-AZ, pgvector, 읽기 복제본, OpenTelemetry, 외부 상태 점검의 도입 단계

근본 원인

  1. 단계가 구성요소 목록으로 쓰였다. 소유 모듈, 실행 주체, 트랜잭션 경계가 표에 없어 3·4단계에서 구멍이 된다.
  2. 코어, 안심, 비서 문서의 제약과 미결정(확인할 것 35, 27, ADR-G3, 3-5)이 설계안으로 옮겨지며 빠졌다.
  3. 설계안, 웹, 도식이 표마다 손으로 요약되어 단일 원본이 없다.

권장 순서

  1. 승인과 권한(1, 2, 3): 중간 작업량, 4단계의 안전 논리를 바로잡는다.
  2. M1 전제(4, 5, 16): 중간 작업량, 재작성 위험을 가장 줄인다.
  3. 안심 경로(7, 8, 11): 중간 작업량, 안전 약속의 판정 가능성을 만든다.
  4. 로드맵과 문턱(9, 10, 14, 19): 작은 작업량, 실행 순서를 맞춘다.
  5. 안 비교(6, 12, 13): 작은 작업량, 결론의 신뢰를 지킨다.
  6. 나머지와 웹·도식 재생성.
