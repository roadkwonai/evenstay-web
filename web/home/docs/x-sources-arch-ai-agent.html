1. 부동산·숙박 플랫폼은 에이전트에게 시스템을 어떻게 여는가

Takeaway

  • [사실] 운영 데이터용 공식 MCP 서버를 낸 것으로 확인되는 곳은 Apaleo(2025-09 발표, 알파)와 Yardi(2026-06 발표, 회사 주장)뿐이다. Cloudbeds의 공식 MCP는 개발자 문서·API 탐색용이다. Mews, Oracle OPERA, Entrata, RealPage는 공식 MCP를 찾지 못했다.
  • [추정] 나머지 대형 벤더는 "자사 앱 안에 내장된 에이전트"와 "파트너 프로그램을 통한 API"로 열고, 외부 에이전트에게 범용 도구 서버를 여는 쪽은 아직 소수다. 쓰기 권한과 승인 방식은 어느 벤더도 문서로 밝히지 않았다.

2. MCP 현황과 Spring AI, AWS 에이전트 런타임

Takeaway

  • [사실] 현행 MCP 스펙은 2026-07-28이고, 이전판(2025-11-25)과 구조가 다르다(세션과 초기화 핸드셰이크 제거, 무상태). 그런데 Spring AI 2.0.x가 쓰는 Java SDK는 2025-11-25판이다. 2026-07-28 지원은 SDK 2.2.0-M1에서 "서버만, 실험적"이다.
  • [사실] AgentCore는 서울에서 Runtime, Gateway, Identity, Memory, Policy, Observability, Evaluations가 모두 가능하다(직접 확인).

Cited Findings

MCP 스펙

  • [사실] 최신 스펙 개정은 2026-07-28이다. 큰 변경: 프로토콜 세션과 Mcp-Session-Id 제거, initialize 핸드셰이크 제거(요청마다 버전과 능력을 _meta에 실음), server/discover 추가, SSE 재개 기능 제거, 서버 주도 요청을 "다회전 요청(MRTR, input_required)"으로 대체, Tasks를 공식 확장으로 이동(tasks/get, tasks/update). — https://modelcontextprotocol.io/specification/2026-07-28/changelog (접근 2026-11-04, 직접)
  • [사실] 같은 개정에서 Roots, Sampling, Logging은 Deprecated, HTTP+SSE 전송은 Deprecated로 재분류, 동적 클라이언트 등록(RFC7591)은 Deprecated이고 Client ID Metadata Documents(CIMD)가 권장이다. 폐지 유예는 최소 12개월 정책. — 같은 페이지 (직접)
  • [사실] _meta에 OpenTelemetry 추적 문맥(traceparent, tracestate, baggage) 규약을 문서화했다. — 같은 페이지 (직접)
  • [사실] 스펙 개요: 호스트는 도구 호출 전에 사용자 동의를 받아야 하고, 도구 설명과 주석은 신뢰된 서버가 아니면 신뢰하지 않는다. 프로토콜 수준에서 강제하지는 못한다고 스스로 적는다. — https://modelcontextprotocol.io/specification/latest (접근 2026-11-04, 직접)

인가(OAuth)

  • [사실] 인가는 선택 사항이다. HTTP 전송에서 쓰면 OAuth 2.1 초안(draft-13)을 따르고, MCP 서버는 리소스 서버다. 서버는 Protected Resource Metadata(RFC9728)를 MUST로 제공해야 하고, 클라이언트는 resource 파라미터(RFC8707)를 인가·토큰 요청에 MUST로 넣는다. 서버는 자기 앞으로 발급된 토큰만 받아야 하며(audience 검증), 다른 토큰을 받거나 넘기는 것은 MUST NOT이다. — https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization (접근 2026-11-04, 직접)
  • [사실] 범위 부족은 403과 WWW-Authenticate: Bearer error="insufficient_scope", scope=...로 알리고, 클라이언트는 기존 범위와 합쳐 단계적 상향(step-up)으로 재인가한다. 인가 서버는 iss 파라미터(RFC9207)를 넣는 것이 SHOULD, 클라이언트는 있으면 검증이 MUST다. — 같은 페이지 (직접)
  • [사실] 보안 모범 사례 문서가 다루는 공격: 혼동된 대리인(confused deputy: 정적 client ID와 동적 등록과 동의 쿠키가 겹치는 MCP 프록시), 토큰 패스스루, SSRF(OAuth 메타데이터 URL), 상태 핸들 하이재킹(세션 대신 서버가 발급한 핸들), 로컬 서버 탈취, mix-up, 범위 과다. 범위는 최소로 시작해 오류 응답으로 올리고, *나 full-access 같은 범위는 피하라고 한다. — https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices.md (접근 2026-11-04, 직접)

Takeaway

  • [사실] 주요 프레임워크는 모두 "도구 호출 직전 중단 → 상태 저장 → 사람 결정 → 재개" 패턴이다. 공통 주의: 저장된 상태는 인증되지 않으므로 서버가 신원과 대기 건을 대조해야 한다.

Inferences

  • [판단] 마스킹은 앱 계층이 먼저 한다(주민번호, 계좌, 연락처, 입주민 이름과 호실). 허브 문서의 "Spring이 허용 칸만 넘긴다(ADR-G4)"가 이 한계(도구 인자·결과 미검사)를 이미 막는 구조다. Guardrails는 보조 그물로 둔다.
  • [판단] 입주민이 보낸 글은 전부 비신뢰 입력이다. ADR-G1(뜻 고르기만, 생성 답변 없음)은 주입 피해를 "잘못된 뜻 선택"으로 제한하고, 뜻 목록 밖의 값은 코드에서 거부한다. 직원용 초안 기능만 생성 텍스트 위험이 남는다.
  • [판단] 한국어 프롬프트 공격 필터가 필요하면 Standard 티어의 교차 리전 영향을 데이터 유형별로 정리하고 쓸지 정한다(예: 입주민 개인정보 제거 후 텍스트만 통과). 이 판단은 지리권 정보를 확인한 뒤에야 할 수 있다.

  • [판단] 비용·한도: 서울에서 모델이 2종이므로 서울 안 폴백은 Sonnet 5 ↔ Opus 5가 전부이고, 타 공급자나 교차 리전으로 폴백하면 리전 안 처리 약속이 깨진다. 기본은 "폴백 시 직원 수동 처리"로 둔다. 사용자·사업장별 호출 상한과 일일 예산은 앱 계층 카운터로 둔다 [판단, 근거 없음].
