1. 비전

한 문장: 입주자가 어떤 길로 말한 생활의 부탁이든 맡을 직원에게 닿고, 누가 맡아 언제 마쳤는지와 입주자의 확인이 기록으로 남게 한다.

  • 영감: "화장실 전등이 안 켜져요"라는 말이 프런트 메모에서 사라지지 않고, 회원님이 맡은 직원 이름을 보고 "다 됐어요"를 눌러야 끝난다.
  • 지향: 요청 하나의 수명(들어온 곳 → 배정 → 처리 → 확인)이 상태와 전이 기록으로 남는다. 누가 언제 무엇을 바꿨는지가 곧 변경 이력이다.
  • 지키는 가치
    1. 입주자가 확인해야 끝난다: 직원의 "완료"는 확인을 기다리는 상태다. [아직이에요]를 누르면 다시 열린다.
    2. 시간을 약속하지 않는다: 처리 기한은 사업장이 정하는 직원용 값이고 회원·보호자 화면에 보이지 않는다(카피 value-prop.md 원칙).
    3. 급한 일은 생활 요청이 아니다: 몸이 불편하다는 요청은 직원이 [안심 알림으로 옮기기]로 넘긴다. 시스템이 요청 내용을 읽고 가르지 않는다(카피 공통 규칙 1).
    4. 앱 밖의 길을 그대로 둔다: 프런트 전화, 지나가는 직원, 홈 비서로 말해도 같은 요청이 된다. 확인도 직원이 대신 기록한다.
    5. 건강 정보를 받지 않는다: 병원 동행은 날짜, 시각, 가실 곳, 돌아오실 때 동행 여부만 받는다. 입력 칸 단계에서 막는다(카피 names.md 2절).

2. 시장 세그먼트 (문제 기준)

세그먼트 문제(JTBD) 바라는 결과 제약 근거
S1. 입주자의 부탁을 받아 나눠 주는 프런트 직원 (첫 세그먼트) 전화나 말로 받은 부탁을 맞는 담당에게 넘기고, 끝났는지 다시 묻지 않고 알고 싶다 받은 자리에서 대신 등록하면 담당 팀 목록에 올라가고 상태가 보인다 프런트는 전화를 그대로 받는다. 앱을 쓰라고 할 수 없다 P-052 [추정: 국내에서 직원이 전화로 받아 적는다, 신뢰도 근거 G12·G16]
S2. 수리·청소·세탁·운전·생활 지원 담당 직원 오늘 내가 할 요청이 무엇이고 어느 호실에 언제 가는지 한 목록에서 보고 싶다 내 일, 배정 전, 기한 지남, 오늘 정기 작업이 한 화면 직원이 일을 하나 더 는다고 느낄 수 있다 [추정] 카피 product-marketing.md Personas [추정]
S3. 사업장 책임자 열린 요청이 쌓이지 않는지, 정기 청소·점검이 빠지지 않았는지 알고 싶다 열린 요청 수, 기한 지남, 정기 작업 마침·쉼·못 함이 숫자로 지금은 사람에게 물어서 안다 [추정] 같음
(정보 수혜) 회원 본인 부탁한 일이 잊히지 않고 누가 맡았는지 알고 싶다 맡은 직원 이름과 지금 상태 디지털이 어려운 회원이 있다 카피 product-marketing.md JTBD [추정]
(정보 수혜) 보호자 멀리서 부모님 방의 불편을 전하고 싶다 회원이 허락한 범위에서 올리고 본다 회원이 "생활 요청"을 허락해야 한다(기본 "안 보여요") decisions 70행 [사실]
  • 왜 S1이 먼저인가: 요청이 들어오는 길 넷(Evenstay 홈, Evenstay 패밀리, 프런트 대신 등록, 홈 비서) 중 셋이 프런트를 거친다(대신 등록, 분류 전 홈 비서 요청 분류, 보호자 요청 확인) [가설: 데모 흐름 기준]. 프런트가 쓰지 않으면 요청이 한 목록에 모이지 않는다.
  • 생활 서비스 맥락: 국내 시니어 레지던스 중 주 2회 청소와 세탁 대행(삼성노블카운티), 병원 동행(평창카운티)을 제공하는 곳이 있다 [사실: A6 https://www.heraldk.com/article/2026062013480077891 2026-06-20, A12 https://www.sidae.com/article/2025032413431314629 2025-03-25]. 해외 시니어 리빙 입주자 앱은 수리·서비스 요청을 직원에게 넘기는 기능을 기본으로 둔다 [사실: R10 Touchtown, R11 LifeLoop, R12 TELS, coverage review 4-1 N1 행]. 국내 현장에서 요청이 실제로 얼마나 빠지는지는 [미확인]이다.
  • Evenstay 안의 빈 화살표: G "직원에게 넘기기"가 받을 곳, D 생활 소식의 "요청" 재료, 운영 현황 대시보드의 "열린 생활 요청" 카드가 이미 N1을 가리킨다 [사실: coverage review 4-1 N1 행, 코어 tech-design.md 10절 카드 표].

3. 상대 비용 위치

  • 차별 가치 쪽이다. N1은 따로 팔지 않고 코어 PMS 위의 모듈이다. 비용 경쟁을 하지 않는다.
  • 비용을 줄이는 방법: 시설 관리 SW 전체(자산 대장, 법정 점검 서류, 협력 업체 계약)를 만들지 않는다 [사실: coverage review S56 "외부 시설관리 SW 영역"]. 요청 분류에 AI를 쓰지 않는다. 처리 기한·담당 팀·비용은 코드가 아니라 사업장 설정이다.
  • 비교: 해외 입주자 앱과 시설 관리 SW는 작업 지시가 있지만 한국어·국내 계약·청구 구조에 맞지 않는다 [추정, 카피 product-marketing.md Competitive Landscape]. 아파트 관리 앱의 민원 접수는 시니어 레지던스가 제공하는 생활 서비스와 청구 연결이 없다 [추정].

4. 가치 제안

세그먼트 이전 방법 이후 지금 쓰는 대안
S1 프런트 전화로 받은 부탁을 종이에 적어 전한다 [추정: P-052] [대신 등록] → 종류에 따라 담당 팀 목록, 들어온 곳과 받은 직원이 남음 누가 받았고 누가 맡았는지 다시 묻지 않는다 프런트 전화, 종이 메모, 단체 메신저 방
S2 담당 직원 오늘 할 일을 사람에게 듣는다 [추정] 내 일·배정 전·기한 지남·오늘 정기 작업 나누기, [맡기] [시작] [완료] 마친 일을 한 줄로 적으면 입주자 화면에 그대로 보인다 구두 전달
S3 책임자 처리 현황을 물어서 안다 [추정] 운영 현황 카드(열린 요청, 배정 전, 기한 지남, 오늘 정기 작업) 숫자와 기준 시각을 보고 기한 지남 목록으로 바로 간다 회의, 전화
회원 같은 부탁을 다시 해야 할 수 있다 [추정] 종류 타일을 누르면 시작하는 첫 화면, 맡은 직원 이름, [다 됐어요] [아직이에요] 부탁한 일의 상태를 앱·문자·프런트에서 본다 프런트 전화
보호자 시설에 전화해 말로 전한다 [추정] Evenstay 패밀리에서 회원님 대신 요청하기(허락 범위 안) 회원님 화면에 "딸 김지민 님이 요청했어요"로 보인다 전화

5. 트레이드오프 — 하지 않을 것

하지 않을 것 이유
요청 내용을 읽고 자동으로 종류·담당·급함을 가르기(AI·낱말 규칙) 종류와 담당은 직원이 정한다. 안심 알림으로 옮기는 판단도 직원이 한다(카피 공통 규칙 1, value-prop.md "쓰지 않기로 한 문장")
회원·보호자에게 처리 시간 약속, 처리 기한 표시 근거가 없다. 기한은 직원용 사업장 설정이다
병원 동행의 진료 과목·증상·진료 내용 받기, 진료 예약 진단·치료는 의료 행위라 기능으로 만들지 않는다 [사실: decisions 69행]
안전 신호 대신하기(급한 일, 몸이 불편한 일) 안심 알림(B)의 몫이다. 회원 화면마다 호출벨·프런트 전화를 고정한다
시설 관리 전체(자산 대장, 법정 점검 서류, 협력 업체 계약·정산) 외부 시설관리 SW 영역이다. 정기 작업은 청소와 점검 일정만 다룬다
요금 계산, 청구 항목 직접 쓰기 코어 청구 원장의 일이다(코어 ADR-4). N1은 "마친 유료 요청"을 코어 명령으로 넘기기만 한다
보호자에게 직접 문자 보내기 보호자에게 가는 길은 D다(evenstay CLAUDE.md 시니어 서비스 원칙)
금전 부탁(통장, 돈 옮기기) 처리 D 금전 부탁(I-31)의 몫이다. 비서의 금전 판단 넘김은 G 화면에 남는다
만족도 점수, 직원 평가, 처리 시간 순위 판단하지 않는 원칙. 사실(건수, 시각)만 보인다
효과 수치 주장 측정한 적이 없다

6. 핵심 지표

  • 북극성 지표 [가설]: 입주자 확인(입주자 확인 + 확인 없이 닫힘 중 입주자 확인)으로 끝난 요청의 비율. 요청이 "입주자 확인까지 남는다"는 약속을 재는 값이다. 포트폴리오에서는 측정 대상이 없어 데모 시드로 계산이 맞는지만 보인다.
  • OMTM(MVP) [가설]: 데모 시나리오에서 요청 하나를 들어온 곳부터 입주자 확인까지 끊김 없이 따라갈 수 있는가(KR1, prd.md 3절).
  • 보조 사실 값(목표선 없음): 열린 요청 수, 배정 전 수, 기한 지남 수, 다시 열림 수, 오늘 정기 작업 마침·쉼·못 함 수. 운영 현황 카드에 기준 시각과 함께 보인다(코어 tech-design.md 10절 원칙: 목표선과 좋음·나쁨 색 없음).

7. 성장

  • 포트폴리오에서는 판매가 없다. 성장은 "모듈이 늘 때 같은 모델로 받는 길이 늘어나는가"로 본다.
  • 들어오는 길: Evenstay 홈(P0), 프런트 대신 등록(P0), 홈 비서 넘김(P1, G), Evenstay 패밀리(P1, D), 정기 작업(P1). 길이 늘어도 요청 모델과 상태 기계는 하나다.
  • 나가는 길: 코어 청구 항목(P1), 안심 알림 옮기기(P1, B), 운영 현황 카드(P1), D 생활 소식 재료(Next).

9. 모방이 어려운 이유

  • 기능 자체는 흔하다 [추정]. 어려운 것은 다른 모듈과의 경계다: 비서의 넘김, 보호자 허락, 안심 알림, 코어 청구가 각자 규칙을 지키면서 한 요청 모델로 이어진다.
  • 시니어 레지던스 규칙이 모델에 들어 있다: 입주자 확인으로 닫힘, 직원 대신 확인, 병원 동행의 입력 칸 제한, 장기 부재 중 정기 작업 쉼.
  • 포트폴리오 관점: 면접관이 상태 기계, 배정, 기한, 정기 작업 생성, 청구 연결을 데모로 따라갈 수 있다 [가설: 카피 product-marketing.md Goals].

10. 전략 정합성 점검

점검 결과
비전(입주자 확인까지) ↔ 지표 북극성이 입주자 확인 비율이라 맞다
"시간 약속 없음" ↔ 기한 기능 기한은 직원 화면에만 있다. 회원·보호자 API 응답에 due_at을 넣지 않는다(tech-design.md 7절)
"급한 일은 아님" ↔ 자동 분류 없음 옮기는 판단은 직원. 회원 화면마다 호출벨·프런트 고정 문구
"건강 정보 없음" ↔ 병원 동행 입력 칸 넷만. "가실 곳"은 생활 지원·운전 팀만 보고 기간이 지나면 지운다 [가설]
모듈 경계 ↔ 연결 넷 코어·B·D·G 모두 api/ 호출 또는 이벤트로만. 사본 없음
1인 2~4주 ↔ 범위 P0은 회원·프런트·담당 직원의 한 흐름. 정기 작업·청구·보호자·비서는 P1

11. 반드시 참이어야 하는 것 (가설)과 가벼운 실험

가설 틀리면 가벼운 실험
H1. 프런트가 전화로 받은 부탁을 대신 등록하는 데 드는 수고를 받아들인다 요청이 한 목록에 모이지 않는다 현장 직원 1~2명에게 대신 등록 창(입력 칸 6개)을 보여 주고 전화 한 통 안에 끝나는지 묻는다 [NEED: 현장 직원 인터뷰]
H2. 입주자가 직원이 마친 뒤 확인을 누른다(또는 말로 해 준다) 대부분 확인 없이 닫혀 확인 기록이 의미를 잃는다 데모에서 [다 됐어요] 단계를 보여 주고 회원 화면 문구를 이해하는지 본다. 실서비스라면 확인 없이 닫힘 비율을 본다
H3. 종류별 담당 팀 기본값(카피 names.md 2절)이 현장 업무 나눔과 맞는다 프런트가 계속 담당을 바꾼다 담당 바꾸기 이유를 기록해 본다(데모 범위 밖)
H4. 정기 청소는 회차마다 확인 없이 끝내도 된다 빠진 청소를 늦게 안다 [다시 봐 주세요]가 새 요청으로 이어지는지 데모로 보인다 [사실: decisions 70행 ④]
H5. 유료 요청은 확인 때 청구 항목이 되는 것이 현장 관행과 맞다 청구 분쟁 [NEED: 사업장 요금표와 세탁 대행 청구 관행]

확인할 것

  1. [미정] 종류별 처리 기한 값: 사업장 설정이다. 데모 시드에는 자리값을 넣는다(prd.md 9절, [가설]).
  2. [가설] 데모 사업장이 세탁 대행·병원 동행·외출 차량을 제공한다: 카피 names.md 2절의 전제를 따른다.
  3. [NEED] 입주자·현장 직원 인터뷰: 실제 요청 표현, 놓친 사례. 지금 근거는 해외 앱 기능과 추정(P-052)뿐이다.
