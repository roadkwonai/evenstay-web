1. 멀티테넌시 모델: 테넌트는 운영사인가, 사업장인가, 소유주인가

Takeaway

  • [판단] 격리 경계(테넌트)는 운영사 1개로 두고, 사업장(site)은 모든 테이블에 붙는 스코프 축, 소유주(owner)는 스코프 축이자 리포트·반출 단위로 둔다. 소유주를 DB 분리 단위(silo)로 올리는 것은 계약이나 규제가 요구할 때만 한다.
  • [사실] 공급자 문서는 대체로 "공유 풀 + 선택적 분리(bridge)"를 권하고, Azure는 RLS 구현이 복잡해서 많은 곳이 안 쓴다고 경고한다. 즉 RLS를 쓰려면 테스트와 운영 비용을 같이 설계해야 한다.

Cited Findings

  • [사실] AWS SaaS Lens는 silo(테넌트별 전용 자원), pool(공유), bridge(일부 silo + 일부 pool) 세 가지로 나누고, 규제 프로필과 noisy neighbor 특성이 silo 쪽으로, 민첩성·접근 패턴·비용이 pool 쪽으로 기울인다고 설명한다. silo여도 온보딩·운영·ID는 공유한다. — 직접 SaaS Lens (2026-11-04 열람)
  • [사실] AWS 규범 가이드는 PostgreSQL pool 모델에서 RLS가 필수라고 하고, 테넌트별 DB 사용자를 만드는 방식보다 앱이 런타임 변수(app.current_tenant)를 세팅하는 방식을 권한다. 테넌트 데이터가 있는 모든 테이블에 RLS를 켜라고 한다. — 직접 AWS 규범 가이드 RLS (2026-11-04)

Inferences

  • [추정] 수탁 운영이라 "소유주"는 계약 당사자이지 SaaS의 "고객 테넌트"가 아니다. 데이터를 만드는 주체는 운영사 직원과 입주자이고, 소유주는 일부 사이트의 집계와 명세서를 읽는 이용자다. 그래서 소유주를 테넌트로 모델링하면 사이트 하나를 여러 소유주가 지분으로 나눌 때와 소유주가 바뀔 때 데이터 소유가 꼬인다.
  • [판단] 구조 제안: operator(1행, 또는 그룹 계열사를 넣으면 몇 행) → site → building/unit. 소유 관계는 site_ownership(site_id, owner_id, share, valid_at daterange)로 두고, 같은 사이트·소유주에 기간이 겹치지 않게 막는다. 소유주 읽기 전용 이용자는 이 테이블로 접근 가능한 site_id 집합이 풀린다(소유주 변경 시점의 명세서는 그 시점의 소유 관계로 계산).
  • [판단] 운영사 직원 스코프: 직원 역할 부여를 (role, scope_type, scope_id, valid_at)로 둔다. 본사=operator, 지역 매니저=site_group(또는 사이트 목록), 사업장 직원=site. 파트타임·순환 근무는 기간으로 풀고 겸직은 행을 늘린다.
  • [판단] 허브 문서 5절이 정한 "앱이 SiteOwnership 조회를 먼저 풀어 site_id 목록을 세션 변수로 넘기는" 방식은 이 구조와 맞는다. 여기에 직원·소유주·보호자 모두 허용 site_id 배열 하나(+ 보호자는 입주자 ID 배열)로 환원하는 규칙을 더하면 정책이 단순해진다. 이 환원 규칙은 내 설계안이다.
  • [추정] 소유주별 데이터 반출이 계약상 요구되는 수준이면 pool에서도 충분히 할 수 있다(사이트·기간 필터). DB 자체를 분리해야 하는 쪽은 소유주 고유 암호화 키나 지역 분리를 요구받을 때로 보이며, 이는 Azure가 든 조건과 같다.

2. RLS 운영 이슈: 풀러, 성능, 테스트, Spring 연동, 비동기 워커

Takeaway

  • [사실] RDS Proxy는 PostgreSQL에서 SET과 set_config 사용을 세션 고정(pinning) 사유로 문서화한다. 트랜잭션 로컬(set_config(..., true))이 예외인지는 이번에 확인하지 못했다. 이 점은 반드시 실측해야 한다.
  • [사실] PgBouncer 트랜잭션 풀링 모드는 SET/RESET을 "지원 안 함"으로 적었고 SET LOCAL은 언급하지 않는다.
  • [판단] Evenstay 시작 구성에서는 앱 수준 Hikari 풀만 쓰고, 외부 풀러(RDS Proxy 등)는 도입 시점에 pinning을 측정해 결정한다.

Cited Findings (풀러)

  • [사실] AWS 문서 요약: PostgreSQL에서 "SET 명령 사용"이 pinning을 일으키고, 세션 변수 기본값 지정에 쓰는 SET과 set_config가 거론된다. 저장 프로시저·함수 호출은 pinning을 일으키지 않는다. 세션 변수 설정에 대한 pinning을 끄는 필터가 있다. "SET LOCAL은 pinning 안 함"이라는 문구는 MySQL 쪽 설명에서만 보이고 PostgreSQL 쪽에는 없었다. — 검색요약 RDS Proxy pinning(Aurora 가이드) (RDS UserGuide 경로는 404였고 Aurora 가이드 경로는 검색 결과로만 확인)
  • [추정] 위 "pinning 끄는 필터"를 켜면 세션 값이 다른 클라이언트에 새는 위험이 생길 수 있다. 이 위험의 구체 문구는 확인하지 못했다. 테넌트 변수에는 쓰지 않는 쪽이 안전해 보인다.
  • [사실, 제3자] 한 pgsql-odbc 스레드 요약에 RDS Proxy의 InitQuery로 SET을 대신할 수 있다는 보고가 있다. 일본어 블로그는 2023-11 업데이트 이후 확장 쿼리 프로토콜이 pinning 사유가 아니라고 주장하지만 공식 문서로 확인하지 못했다. — 검색요약 Classmethod
  • [사실] PgBouncer 기능 표: 트랜잭션 풀링에서 SET/RESET, LISTEN, WITH HOLD 커서, SQL 수준 PREPARE/DEALLOCATE, 세션 수준 advisory lock은 "Never"로 표시된다. 프로토콜 수준 prepared statement는 max_prepared_statements가 0이 아니면 가능하다. — 직접 PgBouncer features
  • [사실] Bytebase(2025-09-05): PgBouncer 뒤에서는 current_user가 공유되므로 트랜잭션 단위 세션 변수를 쓰고, 클라이언트가 그 변수를 직접 못 바꾸게 막으라고 한다. — 직접 RLS footguns

Cited Findings (PG 동작과 성능)

  • [사실] PostgreSQL 문서: 슈퍼유저와 BYPASSRLS 역할은 항상 우회, 소유자는 FORCE ROW LEVEL SECURITY로만 정책을 받는다. 정책 안 서브쿼리는 READ COMMITTED에서 경쟁 조건을 만들 수 있다(완화: SELECT ... FOR SHARE, ACCESS EXCLUSIVE 락, 동시 트랜잭션 종료 대기). UNIQUE·PK·FK 검사는 항상 RLS를 우회하므로 공변 채널(covert channel)을 피하도록 설계해야 한다. 백업 시 row_security=off로 두면 필터링될 상황에서 조용히 빠지는 대신 오류가 난다. 연결 풀링과 current_setting은 이 페이지에서 다루지 않는다. — 직접 PG RLS 문서
  • [사실] Bytebase: LEAKPROOF가 아닌 함수가 정책에 있으면 인덱스 푸시다운이 막힐 수 있다. 정책 컬럼에 인덱스를 둔다. 뷰는 PG15+에서 security_invoker = true로 호출자 권한을 따르게 한다. FK 검사가 부모 테이블 SELECT 권한이 필요해 RLS가 오탐 위반을 낼 수 있다. 전역 UNIQUE 인덱스는 다른 테넌트에 값이 있는지 드러내므로 테넌트로 범위를 줄인다. 막힌 행은 오류 없이 0건 갱신이 된다. 구체화 뷰·COPY·백그라운드 작업은 정책 밖으로 행을 복사한다. 타이밍 채널이 있다. — 직접 RLS footguns

3. 멀티 자산 확장: 공통 코어 + 자산별 규칙, 재고, 시간 모델

Takeaway

  • [판단] 공통 코어(Party, Site, Unit, Contract, Charge/Invoice/Payment, ServiceOrder)에 계약 유형별 규칙을 설정 테이블 + 전략 코드로 두고, 자산 유형별 속성은 소수의 확장 테이블과 JSONB로 나눈다. 기능 켜기·끄기는 사이트 단위 entitlement 테이블로 둔다.
  • [사실] PostgreSQL 18은 PRIMARY KEY/UNIQUE ... WITHOUT OVERLAPS와 FOREIGN KEY ... PERIOD를 제공한다. 이중 예약 방지는 이 제약이나 EXCLUDE USING gist로 DB가 강제할 수 있다.

Cited Findings

  • [사실] PG 18 CREATE TABLE: UNIQUE/PRIMARY KEY (…, col WITHOUT OVERLAPS)는 마지막 컬럼만 해당하며 범위 또는 다중범위 타입이어야 하고 빈 범위는 안 된다. 다른 컬럼은 GiST에서 동등 비교가 가능해야 해서 보통 btree_gist 확장이 필요하다. GiST 인덱스를 쓰고 EXCLUDE USING GIST (id WITH =, valid_at WITH &&)와 같다고 문서가 말한다. FOREIGN KEY (…, PERIOD col) REFERENCES …는 참조 테이블이 WITHOUT OVERLAPS 키를 가져야 하며, 참조 동작은 NO ACTION만 가능하고 RESTRICT/CASCADE/SET NULL/SET DEFAULT는 "시간 외래키에서 지원 안 함"이다. — 직접 PG 18 CREATE TABLE
  • [사실] PG 18 EXCLUDE: 접근 방식은 amgettuple을 지원해야 해 GIN은 안 되고 GiST/SP-GiST를 쓴다. WHERE (predicate)로 부분 제약을 줄 수 있다(괄호 필수). 파티션 테이블이면 파티션 키 컬럼을 모두 =로 포함해야 한다. — 직접 (같은 URL) 및 PG 18 제약 조건 (이 페이지는 EXCLUDE만 다루고 WITHOUT OVERLAPS는 CREATE TABLE 페이지에 있다)
  • [사실] PG 19(개발판)는 UPDATE/DELETE ... FOR PORTION OF를 추가했다. 2026-04-01 커밋(depesz), PG 19 Beta 1은 2026-06-04. 공식 19 문서는 동시 세션 문제 때문에 같은 조건의 SELECT FOR UPDATE를 먼저 하라고 권한다. — 검색요약 PG 19 문서, 제3자 Neon 요약, depesz. 허브 문서는 19가 "아직 RC"라고 적었고 이번 조사는 그 시점 확인이 아니다.
  • [사실] Azure: 테넌트별 커스텀 컬럼 대신 커스텀 데이터를 전용 테이블에 두고, 기능 플래그와 테넌트 설정으로 변형을 처리하라고 한다. — 직접 Azure
  • [사실] Apaleo: 요금제는 정확히 한 unit group에 속하고 파생 요금제의 요율은 수정할 수 없으며 제약(restriction)은 상속되지 않는다. — 검색요약 Apaleo
  • [사실, 회사 주장] Mews의 Service/Product/Resource 모델은 pms-landscape.md(b)에 이미 있다. 이번에 새로 확인한 Yardi·Entrata·Oracle의 자산 간 공용 모델 구조는 없다.

Inferences

  • [판단] 코어 엔티티는 contract(contract_type, unit_id|service_id, party_id, period, status)로 통일하고, 유형은 RESIDENCY(시니어), LEASE(임대), STAY(단기숙박)로 시작한다. 유형별 차이는 (a) 청구 주기와 일할 규칙, (b) 상태 전이, (c) 필수 서류·동의, (d) 점유 단위(월/일/시간)다. 이 네 가지만 전략 코드로 두고 나머지(요금표, 보증금 비율, 퇴실 정산일)는 사이트별 설정 테이블로 둔다. [판단]
  • [판단] 점유(재고)는 occupancy(unit_id, period daterange|tstzrange, contract_id, state)에 EXCLUDE USING gist (unit_id WITH =, period WITH &&) WHERE (state IN ('held','active'))로 둔다. 취소건을 지울 필요 없이 부분 제약으로 제외하기 위해서다. 같은 목적으로 WITHOUT OVERLAPS PK를 쓰면 문서의 문법에 WHERE가 없어 취소 상태를 제약에서 뺄 수 없어 보인다 [추정]. 단기숙박은 시간 경계가 걸리므로 tstzrange, 월 단위 계약은 daterange(반개구간 [))가 자연스럽다.
  • [판단] 소유 관계·요금표·역할 부여처럼 "이 기간 동안 이 값"인 데이터는 PG 18의 WITHOUT OVERLAPS로 겹침을 막고, 과거 정정 이력이 중요한 계약 조건은 정정 이력 테이블을 별도로 둔다(이중시간 모델의 "시스템 시간"에 해당). PG가 시스템 시간 자체를 내장하는지는 이번에 확인하지 못했다 [미확인]. PG 19의 FOR PORTION OF는 도입 시 단순화되지만 18을 기준 버전으로 잡았으므로 포트폴리오에서는 "19에서 쉬워진다" 정도로만 언급하는 것이 안전하다.
  • [판단] JSONB는 자산 유형별 선택 속성(예: 시니어 주거의 돌봄 등급 메모)에, 조회·집계·정산에 쓰는 필드는 정규 컬럼에 둔다. EAV는 쓰지 않는다. 이 선택은 Azure의 "전용 테이블" 권고와 방향이 같다는 점 외에 별도 비교 자료를 찾지 못했다 [판단].
  • [판단] 사이트별 기능은 site_feature(site_id, feature_key, enabled, valid_at) 테이블로 시작하고 외부 플래그 서비스(OpenFeature/Unleash/Togglz)는 쓰지 않는다. 플래그가 "배포 제어"가 아니라 "사이트 계약 범위(entitlement)"이기 때문이다.

Gaps

  • OpenFeature/Unleash/Togglz는 이번에 조사하지 않았다. 위 판단은 문서 근거 없는 설계 판단이다.
  • Entrata, Oracle Hospitality의 멀티 버티컬 설계, Yardi Voyager와 Senior Living Suite의 공유 코어 여부는 공식 자료를 못 찾았다.
  • 국가별 청구 규칙(country-specific billing)은 한국 단일 국가라 이번 범위에서 제외했다.
  • JSONB vs EAV의 성능·유지보수 비교 자료는 이번에 조사하지 않았다.

  • [판단] 컬럼 암호화는 애플리케이션 계층 봉투 암호화(KMS + 데이터 키, 암호화 컨텍스트에 party_id·컬럼명 포함)를 쓰고 pgcrypto는 쓰지 않는다. 이유: SQL 문장에 평문이나 키가 실려 로그·pg_stat_statements에 남을 수 있다는 위험이 있기 때문이나, 이 위험을 직접 검증한 자료는 이번에 찾지 못했다. pgcrypto는 이번에 조사하지 않았다 [미확인].
  • [판단] 검색이 필요한 필드(전화번호, 이름 일부)는 블라인드 인덱스: 정규화한 값의 HMAC-SHA256을 별도 키로 계산해 별도 컬럼에 저장하고 동등 검색만 허용한다. AWS 비콘 문서가 설명하는 빈도 분석 위험(같은 값이 같은 태그)을 줄이려고 잘라서(truncation) 충돌을 허용하는 방식을 따르되, 검색 정확도와의 교환이다. 부분 일치·접두 검색은 포기한다. 이 키를 KMS의 MAC 생성 기능으로 만들 수 있는지는 이번에 확인하지 못했다 [미확인].
  • [판단] 주민등록번호는 수집하지 않는 것을 기본으로 하고, 법령상 필요한 경우만 별도 테이블(별도 역할, 별도 키, 열람 시 사유 필수)에 둔다. 시니어 주거에서 법적으로 요구되는 경우의 목록은 확인하지 못했다.
  • [판단] 파기와 분리 보관: 각 개인정보 컬럼에 "목적 종료일"을 연결한 보존 정책 테이블(retention_policy(data_class, basis, period))과 파기 배치를 두고, 법령상 보존 대상은 별도 스키마로 옮겨 일반 업무 역할의 접근을 끊는다. 암호화한 데이터는 데이터 키 폐기로 복원 불가 상태를 만들 수 있다는 점이 장점이나, 이것이 "복원 불가 파기" 요건을 충족하는지는 해석이 필요하다 [추정].
  • [판단] 감사 변조 방지 3단: (1) DB의 audit_log는 INSERT만 허용(UPDATE/DELETE 권한·트리거 차단), (2) 행마다 이전 해시를 포함한 해시 체인을 사이트별로 저장, (3) 정기 배치로 S3 Object Lock(compliance)에 내보낸다. 해시 체인에 대한 출처는 이번에 찾지 못한 설계안이다. Object Lock은 기간 단축이 불가하므로 보존기간을 법정 하한+여유로 정하고, 로그 본문에 평문 개인정보를 넣지 않아야 파기 의무와 충돌하지 않는다 [추정].
  • [판단] 화면·로그 마스킹: 기본 마스킹 + 열람 사유를 쓴 뒤 일정 시간 해제 + 해제 이벤트를 감사 로그에 기록. 로그에는 식별자(ID)만 남기고 값은 남기지 않는다.

Gaps

  • 안전성 확보조치 기준 제2026-9호 개정 내용, 부칙의 2027-01-01 시행 조항(제15조제5호, 제18조) 내용, 각 조의 현행 조문번호와 항은 국가법령정보센터 본문 또는 개인정보보호위원회 해설서로 확인해야 한다.
  • 제5조 권한 부여 기록 3년의 현행 조문 위치는 제3자 위키 하나로만 확인했다.
  • 민감정보 규정(법 제23조)과 시니어 주거 맥락의 적용, 정보주체 열람·정정 절차의 기한은 이번에 확인하지 못했다.
  • 다중인증(MFA)이 요구되는 정확한 대상은 확인하지 못했다. 해설은 "안전한 인증수단"이라고 표현한다.
  • 한국 맥락에서 AWS Encryption SDK/KMS를 쓰는 사례, 토스·우아한형제들의 암호화·마스킹 공개 글은 찾지 못했다.
