1. ERP: 운영 시스템에서 ERP로 전표를 어떻게 넘기나

Takeaway

국내 ERP(더존·영림원)의 공개 연동 문서는 못 찾았고, 제3자(비즈플레이) 문서가 보여주는 형태는 "중계 Agent가 ERP의 자동전표 테이블에 데이터를 넣는" 방식이다. 해외 호텔 PMS(Mews 등)는 불변 원장 항목을 계정 코드로 매핑해 파일·API로 내보내고, 정정은 과거를 고치지 않고 현재 기간의 새 항목으로 낸다. SAP의 Journal Entry Post API는 중복 검사를 해 주지 않아 호출하는 쪽이 멱등성을 책임져야 한다.

Cited Findings

국내 ERP 연동 형태

  • [사실] 더존 I-U는 엑셀 일괄 등록과 "자동전표 테이블" 연동을 지원한다. 비즈플레이는 중계 Agent가 결재 완료된 경비 데이터를 자사 표준 API로 조회해 자동전표 테이블에 전표 생성용 데이터를 넣는다. 거래처가 I-U에 없으면 Agent가 만든다. 권장 매핑은 용도→계정과목, 내용→적요, 사업예산부서→코스트센터, 사업자번호→거래처코드이다. 마감·취소·오류 처리는 페이지에 없다. — 비즈플레이 문서, 직접, 제3자(연동 사업자의 문서)
  • [사실] 영림원 K-System은 비즈플레이 카드내역을 K-System에서 조회해 전표처리하도록 양쪽 설정이 필요하다고만 나온다. 연동 방식(DB·API·파일)은 첨부된 "연동가이드"에만 있고 본문에는 없다. — 비즈플레이 문서, 직접, 제3자
  • [사실] 비즈플레이는 SAP A1·B1·ByDesign와 영림원 클라우드·구축형을 지원 대상으로 적었고 "300여 개 ERP·그룹웨어와 연계"라고 한다(회사 주장). 인터페이스 방식은 명시하지 않았다. — 비즈플레이 ERP 목록, 직접, 제3자
  • [사실] 아마란스10은 2021-05 출시, 구축형(온프레미스)과 SaaS(퍼블릭·프라이빗 클라우드) 모두 제공한다고 보도됐다. 외부 연동 API 명세는 기사에 없다. — 택스타임즈, 검색요약, 제3자(언론)
  • [사실] WEHAGO 도움말에는 전자세금계산서 인증서를 서버에 저장해 "API/Agent 실시간 연동"에 쓸 수 있다는 항목이 있다. 이는 전자세금계산서 쪽이고 전표 API가 아니다. — WEHAGO 도움말, 검색요약
  • [사실] Apideck의 연동 레이더에서 WEHAGO T는 "지원 예정 요청" 상태이다(기성 통합 커넥터 없음). — Apideck, 검색요약, 제3자
  • [사실] 신한은행 Bank-in Platform을 WEHAGO에 붙여 즉시 급여이체부터 적용했다(2026-04 보도). 더존이 은행 API 제휴를 하는 사례이지 오픈 개발자 포털은 아니다. — 아시아경제, 검색요약, 제3자(언론)

해외 SAP·NetSuite 쪽 멱등성

  • [사실] SAP S/4HANA의 Journal Entry Post API는 동기·비동기 호출 모두 중복 검사를 하지 않는다. S/4HANA Cloud Public Edition 지식베이스는 "대화형 사용자용 검사라 API·IDoc 전기에는 적용되지 않는 것이 정상"이라고 하고, 호출 전에 CDS 뷰·OData로 기존 전표를 조회하는 자체 중복 검사를 권한다. — SAP KB 3687026, SAP KB 2817042, 검색요약(로그인 필요 페이지일 수 있음)
  • [사실] NetSuite REST에서 journal entry를 외부 ID로 PUT upsert하는 경로가 있고 X-NetSuite-Idempotency-Key 헤더 예시가 있다. approved 플래그가 true면 즉시 전기, false면 승인 후 전기. 마감 기간에 대한 동작은 문서에 없었다. — withone.ai의 NetSuite 문서 사본, 검색요약, 제3자(Oracle 공식 아님, 2026-02 갱신)

해외 호텔·임대 PMS의 회계 내보내기

  • [사실] Mews는 LedgerEntry(베타)를 내보내기용으로 노출한다. 항목은 불변이고, 삭제된 Bill의 원래 BillId를 그대로 가진다. Value는 항상 양수이고 LedgerEntryType(Debit/Credit)으로 방향을 표시한다. LedgerType은 Revenue, Tax, Payment, Deposit, Guest, City, NonRevenue이다. PostingDate와 CreatedUtc를 따로 가진다. — Mews Connector API: Export types, 직접, 벤더 공식
  • [사실] Mews는 모든 거래를 복식으로 기록한다. 과거 항목은 편집할 수 없고 정정은 "현재 기간"에 새 항목으로 올라간다. 계상일은 소비일이 아니라 Bill이 닫힌 날이다. 순잔액(매출+비매출+결제−Guest−City+Deposit)이 0이 아니면 전기 문제로 본다. 세율 0%여도 값 0의 세금 항목을 만든다. — Mews 헬프센터 Ledger activity report, 직접, 벤더 공식
  • [사실] Mews는 회계 카테고리마다 원장 계정 코드(LedgerAccountCode)와 외부 코드(ExternalCode)를 둘 수 있고, ledgerBalances/getAll로 날짜별 원장 시작·마감 잔액을 받는다. — Mews open API 미러(비공식), 검색요약, 제3자
  • [사실] Mews의 회계 연동은 주로 제3자 중계(Omniboost 등)를 거친다. 중계 쪽 설명으로는 Mews가 "Consumed/Closed 흐름"에서 개별 Ledger Entry 방식으로 옮겼고, 연동은 포함할 항목을 고른다. BMD 연동은 파일 내보내기이고 "게스트 원장 코드·매출 대체 계정"을 요구한다. Acomba는 카테고리마다 원장 코드가 없으면 내보내기가 막힐 수 있어 대체 계정을 쓰라고 안내하고, 산출물은 ADX 파일이다. — Omniboost: Mews new accounting flow, Acomba 안내(Mews 헬프센터), 검색요약, 제3자
  • [사실] Apaleo 개발자 사이트에 "회계·재무 ERP 연동" 가이드가 있고 하위가 Overview / Map property and accounts / Get transactions / Get certified 네 쪽이다. 하위 쪽 본문은 열지 못했다. — apaleo.dev, 직접(목차만)
  • [사실] Apaleo Finance API는 송장·folio·회계 작업 전반에 접근한다고 설명하고(회사 주장), Omniboost→Exact Online 커넥터는 분개·매출 전표·고객 데이터를 옮긴다. 송장 무효화는 취소 송장을 만든다는 설명이 Make 연동 문서에 있다. — Apaleo APIs, Omniboost, 검색요약, 제3자·회사 주장
  • [사실] 호텔 PMS→ERP 사례로 (a) Protel은 PMS CSV를 모아 Business Central로 보내고 문서유형·부서·부가세율을 매핑하는 도구가 있고, (b) 일부 Business Central 호텔 애드온은 야간감사를 GL에 직접 전기한다고 소개한다(벤더 마케팅). Daylight PMS는 API와 정형 파일 내보내기를 병행한다고 한다. — ecosire BC Hotel PMS, Daylight/레퍼런스, 검색요약, 제3자·회사 주장

[지원 회사] 그룹 ERP

  • [미확인] [지원 회사]가 쓰는 ERP 제품(SAP·더존 등)은 공개 자료에서 찾지 못했다. 검색에 나온 ERP 구축 기사는 현대차그룹·현대건설기계·현대글로벌서비스 등 다른 그룹이다. [지원 회사]과 연결하면 안 된다. — 검색요약(여러 건, 해당 없음)

Inferences

  • [판단] 연동 형태는 "벤더마다 다르다"가 정직한 결론이다. 코어는 ERP 제품을 모르고, 확정된 원장 분개를 LedgerExportBatch(기간, 버전, 상태, 라인)로 묶어 내보내는 포트 하나만 알면 된다. 어댑터가 (1) 자동전표 테이블 적재, (2) 파일 생성, (3) REST 호출 중 하나를 맡는다. 근거는 위 사례들이 세 형태로 갈린다는 점이다.
  • [판단] Mews 패턴을 따르면 설계가 단순해진다. 계정 매핑(회계 카테고리→원장 계정 코드·외부 코드)을 설정 데이터로 두고, 매핑이 없는 항목은 대체 계정으로 보내되 내보내기를 막지 않는다. 정정은 과거 기간을 열지 않고 현재 기간 조정 항목으로 낸다. 이는 Evenstay의 "추가만 하는 원장 + 보정 항목"과 그대로 맞는다.
  • [가설] 요약 전표(일·시설·계정별 합계)와 건별 전표 중 무엇을 ERP에 넣는지는 회사 회계팀 방침이다. 공개 근거가 없다. 설계는 "요약 전표 + 건별 상세 파일"을 모두 만들 수 있게 두고, 어느 쪽이 정본인지는 [미정]으로 남기는 편이 안전하다.
  • [판단] SAP 예에서 보듯 ERP가 중복을 막아 주지 않을 수 있으므로, 배치 ID와 라인 번호로 만든 외부 참조를 모든 전표에 넣고 "ERP에 이미 있는지 먼저 조회"하는 단계를 어댑터에 둔다.
  • [판단] 기간 마감은 양쪽에 있다. PMS 원장 마감과 ERP 회계기간 마감이 따로 움직이므로, 내보내기 상태를 DRAFT→SENT→ACKED→REJECTED(기간 마감 등)로 두고 거절되면 다음 기간의 조정 전표로 다시 만드는 흐름이 필요하다. 거절 사유 코드는 ERP별로 다르다 [미확인].

Gaps

  • 더존 Amaranth 10·WEHAGO·iU의 공식 개발자 문서, 전표 인터페이스 테이블 명세, 인증 방식: 검색에서 나오지 않음. 영림원 K-System 연동 가이드는 첨부 파일이라 못 봄.
  • 산하 WINGS 등 국내 호텔 PMS의 ERP 연동 방식: 공개 자료 못 찾음.
  • SAP Business One Service Layer, 오라클 NetSuite 공식 문서의 마감 기간 처리: 못 찾음.
  • [지원 회사] 그룹 ERP 제품: 공개 자료 못 찾음.
  • Yardi GL, Oracle OPERA→ERP의 구체 방식: 이번 조사에서 열지 못함.

2. 결제·수납

2-1. CMS 자동이체

Takeaway

금융결제원 CMS의 이용기관 신청에는 월·건당 출금 한도와 보증보험이 걸려 있고, 월 수백만 원 규모 납부에서는 "건당 한도 ≤ 월 한도의 10%" 규칙이 먼저 부딪힌다. 효성FMS의 연동 명세와 수수료표는 못 찾았다(제3자 블로그에 건당 약 200~250원). 출금 동의는 법적으로 서면(전자문서), 녹취 등이며 이용기관이 직접 받아 전달할 수 있다.

Cited Findings

  • [사실] 금융결제원(KFTC) CMS 이용기관 심사 기준: 월 출금한도 최소 5백만 원 이상, 개인사업자 3천만 원·법인 5천만 원 한도 내에서 설정(초과는 사전 협의), 건당 출금한도는 월 한도의 10% 이내. 보증수단 가입금액은 신용도에 따라 월 한도의 면제~100%, 신규 신청기관은 1년간 100%. 서류는 보증수단 안내 출력본, 사업자등록증(법인은 등기부등본 추가), 이행(지급)보증보험청약서. — CMS 한도 결정, 직접, 기관 공식
  • [사실] 같은 페이지: 출금 동의는 금융기관 접수(기본)와 이용기관 직접 접수(선택, 보증수단 제출 필요, 면제 대상 제외)가 있고 방법은 서면(전자문서 포함), 전화 녹취, ARS이다. 파일(EDI) 송수신은 PC 방식(인터넷, CMS One 프로그램, 건수 적을 때)과 HOST 방식(전용선, 월 출금 1만 건 이상 예상 시 권장). 고객관리프로그램은 자체 개발, 상용 구입·임대, 결제원의 "빌링원플러스" 중 선택. 계약 절차와 수수료 금액은 이 페이지에 없다. — 위와 같음, 직접

2-2. 가상계좌, 웹훅, 청구서 매칭

Takeaway

2-3. 카드 빌링키, 오픈뱅킹, PCI

2-4. 은행 거래내역 수집, 정산 대사, 원장 설계 참고

Takeaway

쿠콘은 기업 계좌 거래내역을 배치로 조회해 ERP DB에 적재하는 API를 제공한다고 보도됐으나 사양서는 못 찾았다(스크래핑 API의 헥토는 미조사). 원장 설계 참고 자료는 Stripe Ledger와 Modern Treasury 글에서 "불변 + 정정은 새 항목 + 중간(clearing) 계정이 0이 아니면 이벤트 누락·지연"이라는 원칙이 확인된다.

Cited Findings

  • [사실] 쿠콘이 기업이 거래하는 은행의 계좌 거래내역·잔액을 일정 건수 단위로 나눠 조회하는 배치 API를 제공하고 조회 결과를 ERP DB에 자동 적재할 수 있으며 자금대사에 쓰인다는 보도 요약이 있다. 입금 건을 미수금에 자동 매칭하는 기능은 확인되지 않았다. — 스마트투데이, 검색요약, 제3자(언론, 어느 기사의 문장인지 단정 불가)
  • [사실] Stripe Ledger: 삭제·수정 불가한 이벤트 로그, 복식부기, 중간 정산("clearing") 계정의 잔액이 0이 아니면 누락·지연·오류 이벤트의 신호. 생성 이벤트와 해제 이벤트는 독립적이라 순서가 바뀌거나 출처가 달라도 키로 맞춘다. 정정은 되돌리고 재처리하는 방식이며 소스 데이터를 다시 발행할 수 있다. 완전성·적시성·클리어링 세 점검을 점수화한다. 하루 약 50억 이벤트, 금액 기준 99.99%가 4일 내 완전 수집·검증됐다고 밝힘(회사 주장). — Stripe 블로그, 직접, 벤더 공식
  • [사실] Modern Treasury: 회계 기록(불변 원장 거래)과 변경 가능한 업무 객체(주문)를 분리하고, 거래는 pending 동안은 수정 가능·posted 후 불변·실패하면 archived. 정정은 (1) 원 항목을 반대 금액으로 전부 되돌리고 새로 올리거나 (2) 차액만 올리는 두 방식. 한 주문에 여러 원장 거래를 연결해 이력을 추적한다. 멱등성·동시성 제어 수단을 제공한다고 소개했으나 방식은 못 찾았다. — Modern Treasury 글, 직접, 벤더 공식. 상태값과 expected payment 개념: Modern Treasury Ledgers, 검색요약, 회사 주장
  • [사실] 토스 기술 블로그에서 정산·원장·대사 설계 글은 찾지 못했다. 채용 공고에는 "사람이 대조하던 정산 검증을 시스템이 맞춰보고 예외를 잡도록 자동화"라는 문구가 있다. — Wanted 공고, 검색요약, 설계 근거로는 약함

Inferences

  • [판단] 3자 대사(three-way match)는 세 목록의 키 맞추기로 모델링한다. (a) 우리 원장의 ExpectedPayment, (b) PSP/CMS 결과·정산 파일, (c) 은행 입금 거래내역. 모든 수납은 "예상→PSP 통보→은행 입금→원장 확정"의 단계 계정을 거치게 하고, 중간 계정(clearing)이 0이 아닌 건이 곧 대사 예외 목록이 된다. Stripe의 clearing 점검 원리를 가져온 것이다.
  • [판단] 은행 거래내역 피드는 수집 어댑터로만 둔다(BankStatementFeed, 조회 주기·건수 한도 파라미터화). 입금자명·금액·일시로 매칭하는 규칙은 오탐이 나므로 "제안 매칭 + 직원 확정" 화면을 둔다. 스크래핑 API 계열의 안정성·규제 리스크는 [미확인].
  • [판단] 정정은 Modern Treasury의 두 방식 중 "되돌림 + 재기록"을 기본으로 한다. 감사 설명이 쉽다.

Gaps

  • 쿠콘·헥토 거래내역 조회 API 공식 사양, 가상계좌 입금 자동 매칭 여부: 못 찾음.
  • PSP 정산 파일 형식(토스·NICE·KG·KCP): 이번 조사에서 열지 못함.
  • Square Books는 허브 문서에서 이미 다룸. 이번엔 재확인하지 않음.

2-5. 현금영수증·전자세금계산서

Takeaway

팝빌 API는 taxType(과세·영세·면세)을 가진 전자세금계산서 발행, 관리번호(MgtKey) 기반 문서 식별, 국세청 전송, 수정발행(수정 사유 코드 + 원본 승인번호)을 제공한다. 면세 전자계산서를 별도로 다루는지는 확인하지 못했다.

Cited Findings

  • [사실] 팝빌 세금계산서 Java 참조: 즉시 발행(RegistIssue) 또는 임시저장→발행(Register→Issue), 역발행(RegistRequest), 위수탁. 발행 전 공급자 인증서를 팝빌 인증서 서버에 등록해야 한다. taxType은 과세·영세·면세. 관리번호는 최대 24자(영문·숫자·-·_)이고 정발행에 invoicerMgtKey 필수. 중복 키 처리는 페이지에 없고 키를 재사용하려면 발행 취소(CancelIssue) 후 삭제(Delete) 해야 한다. 국세청 승인번호(ntsConfirmNum, 24자)는 팝빌이 자동 부여. 수정세금계산서는 modifyCode와 orgNTSConfirmNum을 넣는다. 국세청 전송 SendToNTS는 30분 내 처리, 결과는 GetInfo 또는 웹훅. 대량 발행 BulkSubmit은 요청당 최대 100건(SubmitID). — 팝빌 개발자 문서, 직접, 벤더 공식
  • [사실] 팝빌 현금영수증 튜토리얼은 응답 code 1이 성공, 8자리 음수가 오류 코드임을 안내한다. — 팝빌 현금영수증, 검색요약, 벤더 공식
  • [사실] 바로빌은 개발지원센터와 함수 호출형 Open API를 제공한다는 2015년 기사만 확인했다. 현재 문서는 못 봄. — 이투데이 2015, 검색요약, 제3자·오래됨

Inferences

  • [판단] 청구 라인마다 과세구분(과세·면세 등) 필드를 두어야 팝빌류 API의 taxType에 매핑할 수 있다. 시니어 주거의 임대료·식비·돌봄 서비스가 각각 어떤 과세구분인지는 이번에 조사하지 않았고 세무 검토가 필요하다 [미확인].
  • [판단] 발행 어댑터는 우리 쪽 청구서 ID에서 만든 MgtKey를 쓰되 "중복 키 처리 문서 미기재"이므로, 발행 전에 GetInfo로 조회하는 단계를 둔다(SAP 사례와 같은 방어).
  • [판단] 발행 후 정정은 수정세금계산서(원본 승인번호 참조)라서, 원장의 보정 항목과 세금계산서의 수정 발행이 1:1로 연결되는 링크가 필요하다.

Gaps

  • 면세 전자계산서 발행 API의 별도 항목, 홈택스 API 직접 연동 가능 여부, 바로빌 현행 문서, 현금영수증 자진발급 규칙: 못 찾음.

3. CRM: 입주 영업

Takeaway

리드→투어→계약 흐름을 외부 CRM에 맡길지 직접 만들지에 대한 국내 시니어 하우징 사례는 공개 근거가 없다. 연동 기술 쪽 근거로는 Salesforce CDC의 72시간 보관, 카카오 알림톡의 정보성 한정(2026-04 심사 강화 보도), 세일즈맵 REST 개체 목록 정도만 확인됐다.

Cited Findings

  • [사실] Salesforce CDC·플랫폼 이벤트의 보관은 72시간이고 그 이후 보관은 보장하지 않는다. 구독자는 replay ID를 저장해 재연결 시 놓친 이벤트를 받고, 권장 경로는 gRPC 기반 Pub/Sub API이다. Confluent 커넥터는 갭 이벤트가 오면 해당 개체를 Bulk API 2.0 전체 재동기화로 전환하고, 큰 개체에서는 비용이 크다고 경고한다. Bulk API 2.0의 구체 한도는 못 찾았다. — Salesforce 메시지 내구성 문서, Confluent 커넥터, 검색요약. CDC 소개 페이지는 접근 403으로 못 엶.
  • [사실] 세일즈맵 개발자 문서 CRM 섹션에는 고객·회사·리드·딜·노트·웹폼·파일·커스텀 오브젝트 API가 있고 인증·Base URL·API 버전·Rate limiting은 별도 시작하기 쪽에 있다. 웹훅 지원 여부와 가격(공개 비교 글에서 "문의", 체험판 있음)은 확인 못 함. — 세일즈맵 개발자 센터, 검색요약, 벤더 공식
  • [사실] 카카오 알림톡은 정보통신망법상 광고성 정보의 예외인 정보성 메시지만 보낼 수 있다. 대행사 블로그는 2026-03 KISA 안내서 7차 개정 후 카카오가 2026-04-01부터 심사 가이드를 바꿨고 메시지의 전부·일부에 광고성 내용이 있으면 발송 불가이며, 친구톡은 2025-12-31 종료돼 광고성은 브랜드 메시지로 옮겨갔다고 설명한다. 승인 후라도 법령 위반 책임은 발송 기업에 있다고 한다. 카카오 원문과 대조하지 않았다. — 비즈고 블로그, 검색요약, 제3자(메시징 대행사). 관련 공지: 솔라피 2026-01-27 공지, 검색요약
  • [사실] HubSpot, Zoho, 채널톡, 상담 전화 CTI(센트릭스·클라우드 PBX)의 연동 사양은 이번 조사에서 근거를 찾지 못했다.

Inferences

  • [판단] 동기화 설계: 리드→투어→계약 확정에서 코어(계약·입주자)로 넘어가는 경계를 "계약 확정 이벤트 1개"로 좁힌다. 이전까지는 CRM이 정본, 이후는 코어가 정본으로 두고, 변경 이벤트 소비자는 replay 위치를 저장하며 72시간 갭이 나면 전체 재동기화(대사)로 복구한다(Salesforce 사례에서 도출).
  • [판단] 알림톡은 계약·청구·방문 안내 같은 정보성에만 쓰고, 입주 홍보는 별도 동의 이력(광고성 수신동의) 위에서 다른 채널로 보낸다. 동의는 목적별(정보성 / 광고성 / 보호자 정보 공유)로 분리 저장하고 철회를 이력으로 남긴다.
  • [가설] 소규모 초기에는 CRM을 사 오고(세일즈맵 등 한국형 SaaS), 코어는 CRM의 "리드·딜" 개체를 읽기 전용 참조로만 갖는 편이 제작량이 적다. 단 시니어 하우징은 방문 상담·보호자·대리 서명이 얽혀서 일반 영업 CRM 모델이 맞는지는 검증되지 않았다 [가설]. 해외 시니어리빙 CRM(WelcomeHome)은 축 7 노트에 있다.
  • [판단] 신원 매칭: 리드는 시니어 본인·보호자·직원 입력이 섞여 같은 사람이 중복되기 쉽다. 전화번호 정규화와 본인확인 CI로 승격 시 병합하되, 병합은 이력이 남는 사람 승인 단계로 둔다.

Gaps

  • 한국 시니어 하우징 운영사의 CRM 사용 실태(어떤 제품, 직접 개발 여부): 공개 자료 못 찾음.
  • HubSpot·Zoho·채널톡 API/웹훅 사양과 요금, 상담 전화 CTI 연동(센트릭스 등): 못 찾음.
  • Salesforce Bulk API 2.0 한도, CDC 개체 제한: 공식 문서 본문 못 엶.

4. 본인확인 · 전자계약 (짧게)

Takeaway

NICE 본인확인은 연계정보(CI/DI) 사용 신청과 체크리스트 제출이 필수이고 CI/DI 평문 노출 금지 등을 자체 점검하게 한다(재판매사 양식 기준). PASS 직접 이용 요건은 못 찾았다. 모두싸인은 웹훅(200 응답 10초, 5회 재시도)과 API 포함 요금제 제한이 확인됐고 대리 서명 사례는 못 찾았다.

Cited Findings

  • [사실] NICE아이디 CI/DI 제공 신청서(코드엠 고객용 2026-05 양식)는 CI·DI 사용 여부를 적게 하고, 체크리스트를 내지 않으면 서비스 등록이 불가능하며, 회원가입 단계에서 CI/DI가 평문 노출되지 않는지, 본인확인 결과값 변조 방지 조치를 했는지 자체 점검하게 한다. 일부 휴대폰 번호는 기술·정책상 본인확인이 안 될 수 있다고 명시한다. — 코드엠 양식, 검색요약, 제3자(재판매사 양식)
  • [사실] PASS는 방통위 지정 본인확인기관인 통신 3사 서비스로 소개되며 "휴대폰 본인인증"으로 2만여 사이트에서 쓰인다는 보도가 있다. 이용기관 신청 절차·계약 조건은 보도에 없다. 2026-09-29 기사 제목은 "통신3사 PASS 신분증 존폐 기로"로, 모바일 신분증 쪽 이야기이고 본문은 못 열었다. — SK텔레콤 보도자료 2021, MTN 2026-09-29, 검색요약, 제3자
  • [사실] 모두싸인 웹훅: 이벤트 document_started, document_signed, document_all_signed 등, API 기능이 포함된 요금제 고객에게만 제공, 200번대 응답이 아니거나 10초 안에 응답이 없으면 실패로 보고 총 5회 재시도(응답을 먼저 보내고 내부 작업은 나중에 처리하라고 권장). 완료 문서는 문서 상세 조회 API의 다운로드 링크(10분 유효)로 받는다. 서명 수단 보안 링크(SECURE_LINK)와 redirectUrl을 지정할 수 있다. — 모두싸인 고객센터, 검색요약, 벤더 공식(고객센터 문서)
  • [사실] 이폼사인·글로싸인 API, 전자서명법상 효력, 고령자 대리 서명(대리권 증빙, 위임장) 사례: 이번 조사에서 근거를 찾지 못했다.

Inferences

  • [판단] 전자계약은 ContractSigningPort(요청 발송, 상태 웹훅, 완료 문서 보관)로 어댑터화한다. 웹훅은 응답을 먼저 주고 큐로 넘긴 뒤, 문서 ID로 상세 조회 API를 다시 호출해 상태를 확정한다(모두싸인 가이드 방식). 서명 주체 필드를 "본인 / 대리인(관계, 위임 증빙)"으로 나눠 둔다. 대리 서명의 법적 유효성은 법률 검토 [미확인].
  • [판단] CI는 평문으로 저장하지 않고 암호화·분리 보관한다(위 점검 항목 근거). 본인확인이 안 되는 번호·시니어를 위한 직원 대면 확인 경로를 둔다.

Gaps

  • NICE·PASS 직접 이용 계약 조건, 심사 기간, 비용: 못 찾음.
  • 모두싸인 대리 서명·제3자 서명 정책, 이폼사인/글로싸인 API: 못 찾음.
