US-01 종류를 골라 요청하기 (P0, F1)

설명: 회원으로서 첫 화면의 종류 타일로 종류를 골라 고칠 것이나 필요한 일을 올리고 싶다. 프런트에 전화하지 않아도 맡을 직원에게 전해지게. 화면: REQ-01, REQ-03, REQ-05 · 문구 2-0~2-3, 2-5 인수 조건

  1. REQ-01에 종류 타일(제목 "어떤 일인가요?"), "내 요청" 구역, 화면 아래 고정 문구 "급한 일이나 몸이 불편하실 때는 호출벨을 누르시거나 방 전화로 내선 0번(프런트)을 눌러 주세요."가 있다.
  2. REQ-01에 종류 타일 6개(고장·수리, 청소, 세탁, 외출 차량, 불편한 점, 그 밖의 일)가 풀이 한 줄과 함께 보인다. 병원 동행 타일은 F14가 켜진 배포에서만 보인다. "점검"은 보이지 않는다.
  3. 종류별 입력은 한 화면에 한 칸씩이다. 고장·수리는 "회원님이 안 계실 때 직원이 방에 들어가도 될까요?"를 받아 요청에 저장한다.
  4. [네, 전해 주세요]를 누르면 요청이 RECEIVED(담당 없음)로 저장되고 "요청을 받았어요. 맡을 직원이 정해지면 이름을 알려 드려요."가 보인다. [다시 쓸게요]는 입력으로 돌아가고 아무것도 저장하지 않는다.
  5. 같은 Idempotency-Key로 두 번 보내면 요청은 하나다. 저장에 실패하면 copy 7절 회원 문구 "요청이 아직 전해지지 않았어요. 앱 연결이 잠시 끊겼어요. [다시 보내기]를 눌러 주세요. 안 되면 프런트로 전화해 주세요."를 보인다.
  6. 프런트 운영 시간 밖에 올리면 copy 2-5의 운영 시간 밖 줄을 더한다([NEED: 프런트 운영 시간] 값은 사업장 설정).

US-02 말로 하기 (P1, F21)

설명: 회원으로서 글을 쓰기 어려우면 말로 넣고 싶다. 화면: REQ-03 · 문구 2-3 머리 인수 조건

  1. 모든 글 칸 옆에 말로 하기 버튼이 있다.
  2. 음성은 글로 바뀌어 칸에 들어가고, 회원이 확인 화면에서 본 뒤 저장된다. 음성 파일은 저장하지 않는다.
  3. 음성 인식을 쓸 수 없는 기기에서는 버튼을 숨긴다.

US-03 프런트 대신 등록 (P0, F2)

설명: 프런트 직원으로서 전화나 말로 받은 부탁을 그 자리에서 올리고 싶다. 메모 없이 담당 팀으로 가게. 화면: REQ-14 · 문구 4-3, 2-10 인수 조건

  1. [대신 등록] 창의 칸은 호실 · 입주자 · 종류 · 들은 말 · 원하는 시각 · 들은 방법(전화, 직접)이다. 호실, 입주자, 종류가 비면 "호실, 입주자, 종류를 골라야 등록됩니다."로 막는다.
  2. 저장하면 source = STAFF_ENTRY, 받은 직원, 들은 방법이 요청에 남고 "등록했습니다. 청소·세탁 팀 목록에 올라갔습니다."(팀 이름은 종류 설정에 따라)가 보인다.
  3. 회원 상세에 "최민수 직원이 회원님 전화를 받고 대신 요청했어요. 맞지 않으면 프런트에 말씀해 주세요."가 보인다(들은 방법이 직접이면 문장 반영됨(copy 10-3)).
  4. 병원 동행을 고르면 "들은 말" 칸 대신 날짜, 시각, 가실 곳, 돌아올 때 동행 칸이 열리고 "날짜, 시각, 가실 곳, 돌아올 때 동행만 적습니다. 진료 과목이나 증상은 적지 않습니다."가 보인다(F14).
  5. 비용 있는 종류면 "비용이 드는 요청입니다(이불 1채 ○,○○○원). 입주자에게 금액을 말씀드렸습니까? [말씀드렸습니다]"를 눌러야 저장된다(F13, P1).
  6. 입주자 선택 목록은 코어 ResidentQuery로 매번 읽고, 직원의 사업장 밖 입주자는 나오지 않는다.

US-04 직원 요청 목록 (P0, F3)

설명: 담당 직원으로서 오늘 할 요청을 한 목록에서 보고 싶다. 화면: REQ-12 · 문구 4-1, 4-2, 6절 인수 조건

  1. 나누기 "내 일 · 배정 전 · 기한 지남 · 오늘 정기 작업 · 전체"가 있고, 첫 화면은 "내 일"이다. 맡은 요청이 없으면 "지금 맡은 요청이 없습니다. 배정 전 요청 2건이 있습니다. [배정 전 보기]"(숫자는 실제 값).
  2. 요약 "배정 전 · 처리 중 · 확인 기다림 · 기한 지남" 숫자가 같은 기준 시각의 조회에서 나온다.
  3. 카드 순서는 종류 → 호실·이름 → 요청 내용 → 원하는 시각 → 들어온 곳 → 상태·담당 → 딱지 → 버튼이다. 딱지는 먼저 처리, 기한 지남, 다시 열림, 비용 있음, 정기 다섯 가지다.
  4. 팀 필터 "프런트 · 시설 · 청소·세탁 · 운전 · 생활 지원", 종류 필터 "수리 · 청소 · 세탁 · 외출 차량 · 병원 동행 · 의견·불편 · 기타 · 점검"이 있다.
  5. 의견·불편 요청은 프런트 팀과 책임자에게만 나온다. 병원 동행 카드의 가실 곳은 생활 지원·운전 팀과 책임자에게만 "가실 곳"으로 열리고, 그 밖의 직원에게는 칸이 없다.
  6. 화면 아래 고정 문구 "몸이 불편하다는 요청은 생활 요청으로 처리하지 말고 [안심 알림으로 옮기기]를 눌러 주세요. 안심 알림 당번에게 바로 갑니다."가 있다.

US-05 맡기와 배정 (P0, F4)

설명: 프런트 직원으로서 배정 전 요청을 맞는 담당에게 넘기고 싶다. 담당 직원으로서 내 팀 요청은 내가 맡고 싶다. 화면: REQ-12, REQ-15 · 문구 4-4, 7절 인수 조건

  1. [맡기]는 요청 종류의 담당 팀에 속한 직원에게만 보인다. 누르면 "한도윤 님이 맡았습니다. 입주자 화면에 이름이 보입니다."
  2. [배정]은 프런트 팀과 책임자에게 보인다. 배정 창 "담당자를 고르세요."에 팀별 직원과 맡은 요청 수가 보인다(오늘 근무·휴무 표시는 Next).
  3. 다른 직원이 먼저 맡았으면 409와 "한도윤 님이 09:20에 먼저 맡았습니다. 함께 해야 하면 한도윤 님에게 연락하세요."
  4. 담당 바꾸기는 이유(근무 교대, 다른 팀 일, 그 밖의 이유)를 고를 수 있고 비워도 된다. 바꾼 기록이 전이 기록에 남는다.
  5. 종류 없는 요청(분류 전)은 [종류 정하기]로 종류를 정해야 [맡기]·[시작]이 열린다. 종류를 정하면 담당 팀과 처리 기한이 정해진다.
  6. 회원 화면이 "한도윤 직원이 맡았어요."로 바뀐다.

US-06 처리 (P0, F5)

설명: 담당 직원으로서 시작, 기다림, 완료, 하지 않음을 남기고 싶다. 입주자가 지금 상태를 알게. 화면: REQ-13 · 문구 4-5, 4-6, 2-7 인수 조건

  1. [시작]은 담당자 본인과 책임자가 누른다. 담당이 없으면 그 팀 직원이 눌러 맡으면서 시작한다. 누르면 IN_PROGRESS, 회원 화면 "한도윤 직원이 처리하고 있어요."
  2. [기다림]은 이유 4개(부품 · 바깥 업체 · 입주자가 고른 날 · 입주자와 시간 맞추기) 중 하나가 필수이고 메모(직원만 봄)는 선택이다. 회원 화면은 이유별 문장(copy 2-7)이고 메모는 회원·보호자 응답에 없다.
  3. [완료]는 "한 일 적기" 한 줄이 비면 저장되지 않는다(병원 동행은 글 대신 한 일 선택지 반영됨(copy 10-7), 기다림 메모도 받지 않는다). 저장하면 DONE, 회원 화면 "직원이 마쳤어요. 확인해 주세요."와 한 일 줄이 그대로 보인다.
  4. [하지 않음]은 이유 넷(관리 범위 밖 · 같은 요청이 이미 있음 · 입주자가 그만두겠다고 함 · 제공하지 않는 서비스) 중에서만 고른다. 회원 화면은 copy 2-7 하지 않음 문장인데, 그 문장은 "제공하지 않는 서비스" 이유만 있다. 나머지 셋(관리 범위 밖, 같은 요청이 이미 있음, 입주자가 그만두겠다고 함)의 회원 문장은 반영됨(copy 10-2)다.
  5. "같은 요청과 합치기"는 같은 입주자의 열린 요청 중 이 요청보다 먼저 들어온 것 하나를 골라 이 요청을 DECLINED(같은 요청이 이미 있음)로 닫고 고른 요청 ID를 남긴다.
  6. 허용되지 않는 전이(예: 접수에서 바로 완료, 닫힌 요청 시작)는 409다.

US-07 확인하기와 아직이에요 (P0, F6)

설명: 회원으로서 직원이 마친 일을 내가 확인해야 끝나게 하고 싶다. 아직이면 다시 봐 달라고 하고 싶다. 화면: REQ-08, REQ-01 내 요청 구역(REQ-06) · 문구 2-6, 2-8, 4-8 인수 조건

  1. DONE 요청이 있으면 목록 위에 "확인하실 요청이 1건 있어요."(수는 실제 값).
  2. [다 됐어요] → CONFIRMED, "확인하셨어요. 요청을 마쳤어요."
  3. [아직이에요] → "무엇이 아직 안 됐나요? (안 적으셔도 돼요)" → 저장하면 IN_PROGRESS, 다시 열린 횟수 + 1, "다시 봐 달라고 전했어요. 한도윤 직원이 다시 맡아요."
  4. 직원 카드에 "다시 열림" 딱지와 "입주자가 11:00에 [아직이에요]를 눌렀습니다. 입주자 의견: "거울 위 등이 아직 안 켜져요""(시각과 글은 실제 값). 담당은 그대로이고 처리 기한은 다시 연 시각부터 다시 계산한다 [가설].
  5. DONE 3일째부터 목록 위 "직원이 마친 요청이 있어요. 확인해 주세요."[가설: 3일].
  6. 두 기기에서 동시에 [다 됐어요]·[아직이에요]를 누르면 먼저 저장된 것만 남고 나중 것은 409.

US-08 입주자 확인 대신 기록 (P0, F6)

설명: 직원으로서 앱을 쓰지 않는 입주자의 말을 확인으로 남기고 싶다. 화면: REQ-16 · 문구 4-7 인수 조건

  1. DONE 요청에만 [입주자 확인 대신 기록]이 보인다. 창 안내 "입주자에게 직접 들은 말만 기록합니다. 들은 직원과 시각이 남습니다."
  2. "다 됐다고 하셨습니다" → CONFIRMED, "아직이라고 하셨습니다" → IN_PROGRESS(다시 열림). 들은 직원·들은 시각이 저장된다.
  3. 기록 뒤 "입주자 확인으로 바꿨습니다(14:00, 들은 직원 최민수)."
  4. 회원 화면 지나온 일에 직원이 대신 기록했다는 줄이 보인다 반영됨(copy 10-3).

US-09 확인 없이 닫힘 (P0, F7)

설명: 시스템으로서 완료 뒤 7일 동안 확인이 없는 요청을 닫고 싶다. 목록이 쌓이지 않게. 화면: REQ-07, REQ-12 · 문구 2-8, names 3절 인수 조건

  1. done_at + 7일이 지난 DONE 요청은 다음 작업 실행 때 AUTO_CLOSED가 되고 행위자는 SYSTEM이다.
  2. 데모 시계를 옮겨도 그 시각까지 따라잡아 닫는다(R-02: 11/9 완료 → 시계 11/17이면 닫힘).
  3. 회원 화면 "7일 동안 확인이 없어 마친 것으로 했어요. 아직 안 됐으면 프런트에 말씀해 주세요."
  4. 작업을 두 번 돌려도 같은 요청에 전이 기록은 하나다.
  5. 7일 안에 [아직이에요]로 다시 열리면 7일은 다음 완료 때부터 다시 센다.

US-10 취소 (P0, F8)

설명: 회원으로서 처리 전이면 내가 올린 요청을 거두고 싶다. 화면: REQ-07 · 문구 2-7, 7절 인수 조건

  1. RECEIVED와 회원 답 기다림(PENDING_MEMBER_OK)에서만 회원에게 [요청 취소하기]가 보인다. 확인 "이 요청을 취소할까요? [취소할게요] [그대로 둘게요]".
  2. 처리 시작 뒤에는 버튼 대신 "직원이 이미 처리하고 있어요. 그만하시려면 프런트에 말씀해 주세요."
  3. 보호자가 올린 요청도 회원이 취소할 수 있다(copy 2-10).
  4. 프런트 팀 직원과 담당은 닫히지 않은 요청을 취소할 수 있고, 이유 코드 없이 누가 취소했는지 남는다. 보호자는 취소하지 않는다(회원이 취소한다). 이미 취소된 요청을 다시 열면 "입주자가 09:30에 취소한 요청입니다."

US-11 처리 기한 (P0, F9)

설명: 책임자로서 종류별 기한을 정하고, 직원이 기한 지난 요청을 따로 보게 하고 싶다. 화면: REQ-12 · 문구 4-1, 5-2, 8-3 인수 조건

  1. 요청의 due_at은 종류(정하면) 설정의 기준(접수 시각, 원하는 시각, 수거 시각)과 시간으로 계산해 저장한다. 종류가 없으면 due_at도 없다.
  2. "기한 지남"은 due_at < 지금이고 RECEIVED·IN_PROGRESS·ON_HOLD인 요청이다. 저장하지 않고 조회 때 계산한다.
  3. 회원·보호자 API 응답에 due_at과 기한 지남 여부가 없다(KR3 테스트).
  4. 설정을 바꾸면 그 뒤에 만든 요청부터 새 값이 쓰인다.

US-12 안심 알림으로 옮기기 (P1, F10)

설명: 직원으로서 몸이 불편하다는 요청을 안심 알림 당번에게 넘기고 싶다. 화면: REQ-13 · 문구 4-9 인수 조건

  1. RECEIVED·IN_PROGRESS·ON_HOLD 요청 카드의 더보기 안에 [안심 알림으로 옮기기]가 있다(완료 뒤에는 없다). 확인 창은 copy 4-9 그대로다.
  2. [옮기기]를 누르면 B SafetyFrontCallCommand.registerFromRequest를 요청 ID 멱등 키로 부르고, 성공하면 요청은 MOVED_TO_SAFETY로 닫히며 "안심 알림으로 옮겼습니다(16:05, 최민수). 생활 요청에는 옮긴 기록만 남습니다."
  3. B 호출이 실패하면 요청 상태는 그대로이고 실패 안내를 보인다 반영됨(copy 10-5).
  4. 회원 화면 "이 요청은 안심 알림으로 옮겨 당번 직원에게 알렸어요."
  5. 시스템은 요청 글을 보고 버튼을 강조하거나 자동으로 옮기지 않는다.
  6. B에 넘기는 값은 사업장, 호실, 입주자, 출처(생활 요청), 요청 ID뿐이고 요청 글은 넘기지 않는다 [가설].

US-13 지나온 일과 감사 (P0, F11)

설명: 회원으로서 내 요청이 어떻게 지나왔는지 보고 싶다. 책임자로서 누가 언제 바꿨는지 보고 싶다. 화면: REQ-07, REQ-13 · 문구 2-7 인수 조건

  1. 모든 전이가 전이 기록(이전 상태, 다음 상태, 행위자, 시각, 이유 코드)에 한 줄씩 남고 코어 AuditWriter WRITE도 한 줄 남는다.
  2. 회원 상세의 지나온 일은 전이 기록에서 만든다: "11월 17일 오전 9시 5분 · 요청하셨어요", "오전 9시 20분 · 한도윤 직원이 맡았어요", "오전 10시 30분 · 직원이 마쳤어요: 천장 전구를 바꿨어요".
  3. 직원 메모, 기한, 담당 바꾼 이유는 회원 지나온 일에 나오지 않는다.
  4. 권한 거부는 코어가 DENIED로 남긴다. 다른 사업장 요청을 열면 "다른 사업장의 요청이라 볼 수 없습니다."

US-14 정기 작업 만들기 (P1, F12)

설명: 책임자로서 "A동 매주 화·금 청소"를 정하면 회차가 저절로 만들어지게 하고 싶다. 화면: REQ-17 · 문구 5-1, 6절 인수 조건

  1. 입력 칸 "이름 · 종류(청소, 점검) · 대상(동, 호실, 공용 시설) · 반복(매주 요일, 매월 날짜) · 담당 팀 · 시작일 · 끝나는 날(선택)".
  2. 만들기 뒤 "정기 작업을 만들었습니다. 첫 회차는 11월 20일(금)입니다. 회차는 그날 0시에 만들어집니다."(날짜는 실제 값).
  3. 바꾸면 "다음 회차부터 바뀝니다. 바꾼 사람과 시각이 변경 이력에 남습니다." 끝내기 확인 "이 정기 작업을 끝내시겠습니까? 이미 만들어진 회차는 그대로 남습니다."
  4. 사업장 책임자와 본사 운영 매니저만 만들고 바꾼다.

US-15 회차 생성과 장기 부재 (P1, F12)

설명: 시스템으로서 그날 0시에 회차를 만들고, 장기 부재 중인 입주자의 회차는 쉼으로 만들고 싶다. 화면: REQ-12(오늘 정기 작업), REQ-09 · 문구 4-2, names 4-3 인수 조건

  1. 대상 동의 호실마다, 그날 그 호실에 사는 입주자(코어 ResidentQuery.residentsInUnit)가 있으면 회차 하나를 만든다. 빈 호실은 만들지 않는다. 공용 시설 대상은 입주자 없이 회차 하나다.
  2. 그 호실에 사는 입주자 모두에게 코어 AbsenceQuery.absenceOf(residentId, 그날)이 부재를 돌려주면 회차는 SKIPPED(장기 부재)로 만든다(2인 호실은 둘 다 부재일 때만). 직원 라벨 반영됨(copy 10-4).
  3. 회원 쉬기 신청이 있으면 SKIPPED(입주자 요청)로 만든다.
  4. (정기 작업, 호실, 날짜)가 유일이라 작업을 다시 돌려도 회차가 늘지 않는다. 시계를 여러 날 옮기면 아직 만들지 않은 날을 모두 만든다.
  5. 데모: 시계 2026-11-17이면 A동 거주 4호실 회차가 생기고 301호 김정희는 쉼(장기 부재, 코어 시드 11/8~11/19)이다.
  6. N1은 코어 장기 부재 이벤트를 구독하지 않고 생성 때 읽는다. 부재를 저장하지 않는다.

US-16 회원 쉬기, 담당 처리, 다시 봐 주세요 (P1, F12)

설명: 회원으로서 이번 주 청소를 한 번 쉬고 싶다. 마친 청소가 덜 됐으면 다시 봐 달라고 하고 싶다. 화면: REQ-09, REQ-12 · 문구 2-9, 7절 인수 조건

  1. REQ-01·09의 "정기 청소: 매주 화요일, 금요일 [이번 주 쉬기]"에서 쉬기를 누르면 마감이 지나지 않은 가장 가까운 회차 날짜로 "11월 20일 금요일 청소를 쉴까요? [쉴게요] [그대로 할게요]".
  2. 쉬기 뒤 "11월 20일 금요일 청소는 쉬어요. 다음 청소는 11월 24일 화요일이에요." 마감(전날 18:00 [가설])이 지나면 "오늘 오후 6시가 지나서 내일 청소는 앱에서 쉴 수 없어요. 쉬시려면 프런트에 말씀해 주세요."
  3. 마감 전에는 쉬기를 되돌릴 수 있다 반영됨(copy 10-4). 직원은 회원 대신 쉬기를 기록할 수 있다 반영됨(copy 10-4).
  4. 담당 직원은 회차를 [시작] [완료] [못 함](이유 셋: 방에 안 계심, 입주자가 다음에 해 달라고 함, 담당자 사정)으로 바꾼다. 가운데 이유의 직원 라벨은 names 4-3 원문에 "회원"이 들어 있어 반영됨(copy 10-4)다. 회원 확인은 받지 않는다. 회원 화면 "오늘 청소를 마쳤어요. (오수진 직원)" 또는 "오늘 청소를 하지 못했어요. 이유: 방에 안 계셨어요. 다시 할 날은 프런트에서 알려 드려요."
  5. 마친 날 [다시 봐 주세요]를 누르면(직원이 대신 누를 수도 있다, source = STAFF_ENTRY) 새 요청(청소, 담당 = 그 회차 담당, 회차 연결)이 생기고 "청소 요청으로 다시 전했어요. 오수진 직원이 확인해요." 같은 회차에서 두 번 누르면 열린 요청이 있는 동안 새로 만들지 않는다.

US-17 비용 있는 요청의 청구 넘김 (P1, F13)

설명: 회원으로서 비용이 드는지 올리기 전에 알고 싶다. 책임자로서 비용 있는 요청은 확인 뒤 청구서에 근거로 붙게 하고 싶다. 화면: REQ-04, REQ-08, REQ-13, REQ-14 · 문구 2-4, 2-8, 4-6, 7절 인수 조건

  1. 종류 설정의 서비스 코드가 있고 코어 ServiceFeeQuery.priceOf가 금액을 주면 REQ-04 "이 요청은 비용이 들어요. 이불 세탁 1채 ○,○○○원이에요." / "직원이 마치고 회원님이 확인하시면 다음 청구서에 들어가요." [맡길게요] [그만둘게요]. 금액이 없으면 비용 없음으로 처리한다.
  2. 요청에 서비스 코드와 안내한 요금표 버전 ID만 남긴다. 금액은 화면을 그릴 때 코어에서 읽는다(사본 없음).
  3. CONFIRMED 또는 AUTO_CLOSED로 바뀌는 트랜잭션에 아웃박스 행이 생기고, 디스패처가 코어 ServiceChargeCommand.record(요청 ID 멱등)를 부른다. [아직이에요] 사이에는 넘기지 않는다.
  4. 확인 화면은 코어 ServiceChargeQuery.previewTargetPeriod로 달을 읽어 "확인하셨어요. 이불 세탁 ○,○○○원은 12월 청구서에 들어가요."를 보인다. 이 조회가 없으면 달 없이 "다음 청구서" 문장 반영됨(copy 10-6). 청구 단가는 회원에게 안내한 요금표 버전의 값이다.
  5. 5회 실패하면 [가설] 직원 상세에 "청구 항목을 만들지 못했습니다(세탁 대행, A동 202호). 요청은 입주자 확인으로 닫혔습니다. [다시 보내기]를 누르거나 경리 담당에게 알려 주세요." [다시 보내기]도 같은 멱등 키다.
  6. 회원·보호자에게 실패를 보이지 않는다.

US-18 병원 동행 (P1, F14)

설명: 회원으로서 병원 가는 날 직원이 함께 가 주기를 신청하고 싶다. 몸 상태는 말하지 않고. 화면: REQ-03, REQ-12, REQ-13 · 문구 2-3, 4-2, 8-1 인수 조건

  1. 입력은 날짜·시각, 가실 곳(유일한 자유 입력), 돌아올 때 동행 셋이다. 직원의 한 일, 기다림 메모, 회원의 [아직이에요] 의견도 글로 받지 않는다. 가실 곳 아래 "어디가 불편하신지는 적지 않으셔도 돼요. 날짜와 가실 곳만 있으면 돼요."
  2. 저장 모델에 진료 과목·증상·진료 내용 칸이 없다(스키마 테스트).
  3. 가실 곳은 생활 지원·운전 팀과 책임자만 열고, 열 때마다 SENSITIVE_READ 감사 줄이 생긴다. 목록·알림·문자·이벤트·감사 전후 값에는 없다.
  4. 전날 문자에는 병원 이름이 없다(copy 8-1 병원 동행 전날).
  5. 요청이 닫히고 30일 지나면 가실 곳을 지우고 지운 시각을 남긴다 [가설].
  6. B 첫 화면의 "병원에 가신 분"에 세지 않는다.

US-19 보호자가 보는 생활 요청 (P1, F15)

설명: 보호자로서 회원님이 허락한 생활 요청을 보고 싶다. 화면: REQ-10 · 문구 3-1, 3-2, 6절, 7절 인수 조건

  1. 코어 authorize(actor, requests.request.view_as_guardian, …)에서 D 정책이 "생활 요청" 허락을 확인해야 열린다. 허락이 없으면 "지금은 이은숙 회원님이 생활 요청을 보여 주지 않고 계세요. 궁금한 점은 프런트 02-000-0000 (가상 번호)으로 전화 주세요."
  2. 화면 위 "이은숙 회원님이 허락하신 생활 요청이에요."와 "고장·수리, 청소, 세탁, 외출 차량 요청이 보여요. 불편한 점과 그 밖의 일은 보이지 않아요."
  3. 의견·불편, 그 밖의 일, 분류 전 요청은 목록에 없다. 병원 동행은 건강 소식 허락과 건강정보 별도 동의가 모두 있는 보호자에게만 가실 곳 없이 보인다.
  4. 응답에 처리 기한, 담당 팀, 직원 메모, 기다림 메모가 없다. 맡은 직원 이름과 상태 문장(names 3절 보호자 열)은 있다.
  5. 허락이 바뀌면 "이은숙 회원님이 생활 요청을 보여 주지 않기로 하셨어요. 이제 이 화면을 볼 수 없어요."

US-20 보호자가 대신 올리기 (P1, F15, F19)

설명: 보호자로서 멀리서 회원님 방의 고장이나 필요한 일을 전하고 싶다. 화면: REQ-11, REQ-07 · 문구 3-3, 2-10, 8-1, 8-2 인수 조건

  1. 버튼 "이은숙 회원님 대신 요청하기", 종류는 고장·수리, 청소, 세탁, 외출 차량 넷만. requests.request.create_as_guardian을 D 정책이 허락해야 저장된다.
  2. 저장하면 source = GUARDIAN_PORTAL, 올린 사람(personId)이 남고 "요청을 전했어요. 이은숙 회원님 화면에도 보여요." 회원 화면 "딸 김지민 님이 요청했어요. 원하지 않으시면 [요청 취소하기]를 누르세요."
  3. 비용 있는 종류면 PENDING_MEMBER_OK로 저장하고 회원 화면에 "딸 김지민 님이 세탁을 요청했어요. 이 요청은 비용이 들어요. 이불 1채에 ○,○○○원이에요. 맡길까요? [맡길게요] [그만둘게요]". [맡길게요] → RECEIVED, [그만둘게요] → CANCELLED. 보호자 화면은 "이은숙 회원님께 여쭤봤어요. 맡기겠다고 하시면 접수돼요."
  4. 다음 날 오전 9시 [가설]까지 답이 없으면 프런트 목록에 보인다(목록 라벨 반영됨(copy 10-1)). 프런트가 회원에게 묻고 대신 기록한다(copy 2-10 [가설]). 7일 [가설] 동안 답이 없으면 SYSTEM이 취소한다(회원·보호자 문장 반영됨(copy 10-1)).
  5. 보호자 문자는 N1이 보내지 않는다. N1은 ServiceRequestStatusChanged를 내고 D가 그 보호자에게 맡았을 때·마쳤을 때만 "[Evenstay 패밀리] 이은숙 회원님 대신 요청하신 일에 새 소식이 있어요. …"를 보낸다.
  6. 병원 동행 버튼은 없고 도움말 "병원 동행은 이은숙 회원님이나 대신 처리하실 분이 프런트에 신청하실 수 있어요."

US-21 홈 비서에서 온 요청 (P1, F16)

설명: 프런트 직원으로서 회원이 비서에게 말하고 전해 달라고 한 일을 생활 요청 목록에서 받고 싶다. 화면: REQ-12, REQ-13, REQ-07 · 문구 4-2, 4-10, 2-10 인수 조건

  1. G가 넘김(이유 직접 요청 + 주제가 청구서·계약이 아님, 또는 도구 밖 질문)을 만든 뒤 ServiceRequestCommand.receiveFromAssistant를 부르면 종류 없는 RECEIVED 요청이 생긴다. source = ASSISTANT_HANDOFF, 넘김 ID와 확인 ID가 비면 거부하고 DENIED를 남긴다.
  2. 같은 넘김 ID로 다시 오면 처음 만든 요청을 돌려준다.
  3. 카드 "분류 전 · … · 넘긴 이유: 직접 요청 · [종류 정하기]"(넘긴 이유는 실제 값. 데모 문장은 G가 시설 요청으로 보고 "도구 밖 질문"으로 넘긴다, G names.md), 위 한 줄 "홈 비서가 입주자에게 묻고 넘긴 말입니다. 입주자가 한 말 그대로입니다."
  4. [비서 대화 보기]는 G 직원 화면의 그 넘김 상세로 간다. 권한은 G assistant.handoff.view다.
  5. 회원 화면 "비서가 직원에게 전한 말이에요: "목요일에 시장 가야 하는데 차 있어요?""(copy 2-10 예문의 장소를 "시장"으로 바꿈, R19, 반영됨(copy 10-8))
  6. 건강·금전·계약 판단 넘김은 이 목록에 오지 않는다.

US-22 운영 현황 칸 (P1, F17)

설명: 책임자로서 대시보드에서 생활 요청 숫자를 보고 기한 지남 목록으로 가고 싶다. 화면: REQ-19 · 문구 5-3 인수 조건

  1. ServiceRequestQuery.openCount(siteId, at, actor)가 requests.summary.read 권한을 CHECK로 검사하고 숫자만 돌려준다(이름 없음, 열람 기록 없음).
  2. 칸 "생활 요청", 숫자 "열린 요청 12 · 배정 전 2 · 기한 지남 1", 둘째 줄 "오늘 정기 작업 18 중 15 마침 · 쉼 2 · 못 함 1"(숫자는 실제 값), 기준 시각을 함께 보인다.
  3. 누르면 REQ-12 "기한 지남"으로 간다.
  4. N1이 배포에 없거나 권한이 없으면 칸이 나오지 않는다(코어 10절 규칙). 저장하거나 복사하지 않는다.

US-25 소유주 월 리포트의 생활 요청 숫자 (P1, F22)

설명: 소유주 담당자로서 우리 사업장의 생활 요청이 한 달 동안 얼마나 들어오고 닫혔는지 숫자로 알고 싶다. 화면: 코어 CORE-14 안의 생활 요청 칸 · 문구 반영됨(copy 10-9) 인수 조건

  1. 코어가 ServiceRequestQuery.monthlySummary(siteId, period, actor)를 부르고, N1은 requests.summary.owner_read를 CHECK로 검사한다. 온누리 담당자는 새봄 레지던스만, 다온 담당자는 다온하우스만 받는다(코어 1단계).
  2. 응답에 입주자 이름, 호실, 요청 글, 담당 직원 이름이 없다(테스트).
  3. 병원 동행은 종류별 숫자에 따로 나오지 않고 합계에만 들어간다 [가설].
  4. 정기 작업은 마침·쉼·못 함 수만 보인다.
  5. 소유주는 이 조회 말고 어떤 requests.* 행동도 할 수 없다.

US-23 알림 (P1, F18)

설명: 회원으로서 앱을 열지 않아도 중요한 변화는 문자로 알고 싶다. 직원으로서 나에게 온 일을 휴대폰으로 알고 싶다. 화면: 문자, 직원 알림 · 문구 8-1, 8-3 인수 조건

  1. 회원 문자는 맡았을 때, 마쳤을 때, 기다림, 하지 않음, 이동 전날, 보호자가 비용이 드는 요청을 올렸을 때만 보낸다(copy 8-1). 요청 글과 링크를 넣지 않는다.
  2. 이동 전날 문자는 외출 차량·병원 동행에만, 회원이 고른 시각만 다시 말한다. 병원 동행 문자에 병원 이름이 없다.
  3. 직원 알림은 배정됐을 때, 다시 열렸을 때, 기한이 지났을 때(담당, 팀장), 팀에 배정 전 요청이 있을 때다. 요청 글을 넣지 않는다.
  4. 발송은 platform Notifier이고 아웃박스로 보낸다. 같은 사건에 문자는 하나다.

US-24 요청 종류 설정 (P1, F20)

설명: 책임자로서 종류별 담당 팀, 처리 기한, 비용을 정하고 싶다. 화면: REQ-18 · 문구 5-2 인수 조건

  1. 표 머리 "종류 · 담당 팀 · 처리 기한 · 비용". 안내 "처리 기한은 직원 화면에만 보입니다. 입주자와 보호자에게는 보이지 않습니다."
  2. 비용 칸은 서비스 코드를 고르고 금액은 코어 요금표에서 읽어 보인다. "금액은 코어 요금표에서 가져옵니다. 요금표에 없는 서비스는 비용 없음으로 처리됩니다."
  3. 바꾸면 새 설정 버전이 생기고 옛 버전은 남는다. 이미 만든 요청은 만들 때의 값을 쓴다.
  4. 사업장 책임자와 본사 관리자만 바꾼다.
