1. ナースコール 벤더와 연동 방식 (아이폰 Vi-nurse, ケアコム 등)

Takeaway

  • 일본 시설의 ナースコール은 "단독 호출 장치"가 아니라 알람 허브다. 센서·카메라·스마트폰·PHS가 나스콜에 알람을 보내고, 나스콜이 직원 단말에 뿌리는 구조가 흔하다. [추정]
  • 벤더 간 연동은 의료용 국제 규격(IHE PCD ACM)을 일부 쓰는 경우와 벤더끼리 개별 협의하는 경우가 섞여 있다. 개호 쪽 공통 표준은 2022년 조사 시점에도 확립되지 않았다. [사실, 아래 근거]

Cited Findings

표준 규격 (가장 중요한 1차 자료)

  • [사실] NTTデータ経営研究所의 「介護業務支援システムに関連したデータ連携及び標準化可能性調査 報告書」(2022-03-25, 발주처는 문서에서 확인 못함 [미확인], AMED·経産省 사업 맥락)는, 見守りセンサー 등 IoT 기기와 介護業務支援システム 사이, 그리고 介護記録システム 사이의 데이터 연계가 "아직 방식이 확립되지 않았다"고 적는다. — 報告書 PDF, 발행 2022-03-25 [3년+], 검증: 직접(pdftotext)
  • [사실] 같은 보고서는 나스콜 쪽이 "성공 사례"라고 본다. 나스콜 시스템 영역에서는 IHE(PCD 도메인)의 규격에 따라 각 사가 제품을 내므로, 의료기관이 나스콜 제조사에 묶이지 않고 선정·교체할 수 있다고 한다. IoT 기기 제조사가 IHE PCD 준수 인터페이스를 구현하면 나스콜에 접속해 알람 데이터를 보낼 수 있다고 적는다. — 같은 PDF, 직접
  • [사실] 보고서에 따르면 나스콜 시스템은 IHE PCD의 ACM(Alarm Communication Management) 프로파일 기반으로 만들어져 있다. 데이터는 HL7 Version 2로 기술하고 기술 사양이 공개돼 있다. 그림에는 알람 보고(PCD-04), 통지(PCD-06), 응답(PCD-07) 트랜잭션이 나온다. — 같은 PDF, 직접
  • [사실] 보고서의 대조 사례: Continua Health Alliance 규격은 일본에서 대응 제품이 적고, 접속 대상 시스템(介護記録 등)이 대응하지 않으면 연결이 안 돼 "네트워크 외부성"이 생기지 않아 보급 기운이 안 오른다고 평가한다. — 같은 PDF, 직접
  • [사실] 보고서는 "센서·디바이스 데이터 연계 규격" 영역에서, 見守り 같은 알람 발생 기기에는 나스콜 쪽에서 채택이 진행된 IHE PCD의 ACM 틀을 쓰자고 제안한다(PCD-04 알람 → 介護業務支援システム/ナースコール → PHS 등). 확정된 표준이 아니라 2022년 시점의 검토 안이다. — 같은 PDF, 직접
  • [사실] 보고서 본문에서 "ECHONET"를 검색했을 때 0건이었다(grep). 이 보고서의 표준 조사 범위(Continua, IHE, HL7 V2/CDA/FHIR, JEITA 컨테이너 포맷, LIFE 외부 연계 인터페이스 등)에 ECHONET Lite는 없다. — 같은 PDF, 직접
  • [미확인] 2022년 이후 IHE PCD ACM이 개호용 見守り 기기에서 실제로 얼마나 확산됐는지는 못 찾았다.

벤더 사례: 인터뷰 속 ケアコム와 개별 협의형

  • [사실] 보고서의 인터뷰 사례 "I法人"은 ナースコール 제공사로 ケアコム를 들고, 見守りセンサー 등에서 얻은 알람을 스마트폰에 집약하며, 각종 센서와 나스콜이 IHE PCD로 연계한다고 적는다. 법인명은 익명 처리돼 있어 어느 회사가 인터뷰 대상인지는 확인 못함. — 같은 PDF p.70, 직접
  • [사실] 같은 보고서의 "J法人" 사례는 반대로, 타사 기기와의 접속을 특정 규격으로 모으지 않고 사업자별로 연계 방식을 협의한다고 한다. 그래서 개발비가 들기 쉽고, 介護記録システム 쪽 데이터 포맷이 회사마다 달라 같은 항목을 짝짓는 작업이 연계를 어렵게 한다고 한다. 구성: 착좌/초전/매트/도어 센서 → 센서 기기 게이트웨이/서버 → 介護記録システム, 이상 검지 전후 영상을 스마트폰에 전송, 인컴·타사 나스콜·네트워크 카메라도 외부 기기로 연결. — 같은 PDF p.69, 직접

아이폰(Aiphone) Vi-nurse

  • [사실] 아이폰은 2016-03-10 Vi-nurse와 パラマウントベッド 眠りSCAN의 연동 개시를 발표했다. 나스콜 親機(PC)에 재상/이상 상태를 표시하고, 상태가 바뀌면 親機·ハンディナース(PHS)·스마트폰에 알람을 보낸다. Vi-nurse는 간선을 IP화한 시스템으로 眠りSCAN과 나스콜 LAN 간선을 공유해 배선 비용을 줄인다고 한다. 연동에는 유상 전용 소프트가 필요하고 Vi-nurse Ver2.00 이상이 대상이며, 도입 완료 시스템은 유상 버전업이 필요하다. 회사 주장(보도자료). — 아이폰 보도자료 (共同通信PRワイヤー), 2016-03-10 [3년+], 검증: 직접(fetch 요약 경유)
  • [사실] BONX WORK(株式会社BONX)가 Vi-nurse의 호출 통지를 CDC(ケア・データ・コネクト, 株式会社ブライト・ヴィ 제공 개호·의료 데이터 연계 플랫폼) 경유로 받아, 그룹 채팅에 음성으로 실시간 전달하는 연계를 발표했다. 스마트폰+이어폰으로 받으므로 PHS 같은 전용 단말을 확인할 필요가 줄어든다고 한다. 회사 주장. 기사 본문에 발표일은 없고 페이지 최종 갱신은 2025-06-06. — itbusinesstoday, 2025-06-06 갱신, 검증: 직접(fetch 요약 경유)
  • [사실] NEC가 2014-09에 Vi-nurse 대응 스마트폰용 영상·환자 정보 통지를 발표했고, 영상·정보는 스마트폰에 저장되지 않는 사양이라고 한다. — NEC 보도자료 (검색 결과로만 확인), 2014-09-26 [3년+], 검증: 검색요약

2. 見守りセンサー 아키텍처 (眠りSCAN, HitomeQ, Neos+Care 등)

Takeaway

  • 일본 見守りセンサー는 시설 내 Wi-Fi/LAN → 시설 내 서버(또는 클라우드) → 직원 스마트폰/나스콜 알람 구조가 기본이다. 최근엔 센서 본체에서 AI 판정을 하는 방향(엣지)과, 시설 Wi-Fi가 없는 환경용 제품이 나오고 있다. [추정, 근거는 벤더 발표 검색요약]
  • 센서 벤더는 나스콜 벤더와 1:1로 연동 소프트를 만들거나, 음성 인컴 앱(Buddycom, BONX WORK)·介護記録와 개별 연계한다. [사실]

  1. 알람 허브를 PMS 본체와 분리 — [사실] 일본은 나스콜 계층이 센서 알람을 모아 직원 단말에 전달하고, 기록 SW는 그 이력을 받는다(Vi-nurse, ケアコム, 福祉の森 사례). [판단] PMS 안에 "알람 이벤트 수집·라우팅·이력" 모듈을 별도 경계로 두고, 센서 벤더별 어댑터를 얹는 설계가 현실적이다.
  2. 의료용 알람 규격 재사용 발상 — [사실] IHE PCD ACM(HL7 v2 기반)이 나스콜 영역에서 쓰이고, 개호 센서에도 채택하자는 안이 2022년에 나왔다. [판단] 한국 PMS가 자체 이벤트 스키마를 만들 때, 이벤트(알람 보고→통지→응답)의 3단 흐름과 상태 모델을 ACM에서 빌려오면 근거 있는 설계가 된다. 규격 전체 구현은 과하다.
  3. "파일 기반 표준 + 기기 개별 어댑터" 이원화 — [사실] 일본은 계획·청구·LIFE는 표준(CSV 등), 현장 기기는 개별 연계. [판단] MVP는 어댑터 1~2개(예: 가상 센서 시뮬레이터)로 충분하고, 표준화 주장은 피하는 편이 정직하다.
  4. 스마트폰 중심 직원 단말 — [사실] 호출 대응·기록·통화를 한 단말에 모으는 사례(SOMPO iPhone 2,500대 계획 2018, EGAO link, 富田ケアセンター). [판단] 직원용 모바일 우선 설계, 오프라인 입력 후 동기화(CAREKARTE 모바일의 서술)를 PMS 요구사항에 넣는다.
  5. 호출 시 영상 자동 팝업 + 기록 자동 적재 — [사실] 네트워크 카메라 자동 기동(회사 주장 효과), 호출 이력 자동 기록(福祉の森). [판단] 알람 이벤트에 "대응 로그(누가 언제 확인)"를 자동 적재하는 기능은 데모하기 쉽고 설명이 명확하다. 영상은 민감정보라 저장·열람 권한 설계가 먼저다.
  6. 안부 확인 의무의 방식 다양성 — [사실] 일본 サ高住는 방법이 자유(방문, 전화, 식사 확인, 동태 센서)이되 모든 입주자에게 제공해야 하고 거부해도 면제되지 않는다. [판단] PMS에 "입주자별 안부 확인 방법 + 실행 이력 + 미확인 에스컬레이션" 기능을 두면 책임 범위를 명시하기 쉽다. 한국 법령의 해당 의무 여부는 별도 확인 필요.
  7. 도입 부담을 점진화 — [사실] 일본 조사에서 전 침상·전 직원 단말 도입이 加算 상위 등급 장벽 1~2위. [판단] 객실·층 단위로 켤 수 있는 구조.

못 옮기는 것, 옮기면 위험한 것

  1. 개호보험 제도 연계층(LIFE, ケアプランデータ連携, 介護情報基盤, 加算) — [사실] 일본 고유 제도에 묶인 계층. [판단] 한국 장기요양 연계는 별개 제도라 이식 불가. 구조(보험 쪽 데이터는 파일/표준, 현장 데이터는 개별)만 참고한다.
  2. 生産性向上推進体制加算 같은 보수 유인 — [사실] 일본은 보수와 인원배치 특례로 기기 도입을 유도. [판단] 한국 레지던스(대개 민간 분양·임대형)에는 같은 유인이 없다. 도입 비용 구조가 다르므로 ROI 논리를 새로 써야 한다.
  3. 일본 센서·나스콜 벤더 제품 자체 — [사실] 이번 조사에서 한국 내 대응 여부는 미조사. [판단] 포트폴리오에서는 실제 제품 연동을 주장하지 말고 시뮬레이터/어댑터 인터페이스로 보여준다.
  4. 介護付き(간호 중심) 시설의 케어 기록 중심 모델을 독립생활형에 그대로 적용 — [사실] 확인된 구성 사례 대부분이 介護付き 또는 住宅型有料. [판단] 아파트형 독립생활 레지던스는 입주·계약·청구·커뮤니티·안부가 주축이라 케어 기록 모듈을 중심에 두면 과설계 위험이 있다.
  5. 경비회사 출동 모델 — [사실] 일본 지자체 개인가정 사업에서만 근거 확인, 시설 접속 모델은 미확인. [판단] 한국 경비/관제 업체 연동 구조는 이번 자료로 설계할 수 없다. 설계 시 "외부 수신센터 연동 인터페이스(웹훅/전화 연계)" 정도로만 열어 둔다.
  6. IHE ACM을 일본 표준처럼 소개하는 것 — [사실] 개호용으로는 2022년 시점 "제안", 보급 정도 미확인. [판단] "일본은 표준이 있다"고 쓰면 사실 왜곡이다. "의료용 규격을 참고한 설계 안"이라고 쓴다.
  7. 효과 수치(17시간/일, 야간 2명 체제 등) — [사실] 회사 주장이며 조건 불명. [판단] 포트폴리오에 근거 수치로 인용하지 않는다.
