1. 요약

생활 지원 단계 모듈은 입주자의 건강이 바뀌었을 때 직원이 살펴본 것을 기록하고, 그 기록을 근거로 생활 지원 단계 변경을 제안하고, 입주자에게 설명한 뒤, 제안하지 않은 사람이 결정하게 하는 코어 위의 모듈이다. 회원 화면은 바뀌지 않는 것부터 보여 주고, 보호자에게는 결정된 변경만 D 건강 소식으로 간다. 2026-10 입법예고된 시행규칙 개정안이 "서비스를 받으며 계속 거주"를 열려고 해서 [사실, A3, 확정 전], 단계 변경을 근거와 함께 남기는 일이 운영사의 기록 과제가 될 수 있다 [추정].

2. 배경

  • 건강이 나빠지면 계속 살 수 있는지, 어떤 서비스로 이어지는지가 시설마다 다르고 잘 보이지 않는다(P-003) [사실, A15: 한 시설은 일반 → 생활보조거실 → 노인요양원 연계].
  • 병원은 퇴원 예정 환자를 주소지 시군구로 연계한다. 입주 시설이 이 경로에 있는지는 자료가 없다(P-020) [사실, E2 https://www.korea.kr/news/policyNewsView.do?newsId=148960792, 2026-03-13].
  • 개정안: 65세 이상이 지정 재가서비스(방문요양, 방문간호 등)를 받으며 독립생활이 가능하면 노인복지주택에 계속 거주할 수 있다. 입법예고 2026-10-13~11-23, 시행은 공포 3개월 뒤로 보도됐다 [사실, E12 https://www.imaeil.com/page/view/2026101215574176948, 2026-10-12]. 확정되면 외부 돌봄과 시설 서비스를 함께 맞추는 일이 늘어난다(P-019) [추정].
  • 코어(A)는 요금표를 체결 때 고정하고 일할 계산을 하지 않는다. 계약 변경 API는 Next다 [사실, 코어 tech-design.md 4절·8-2]. 그래서 C는 단계와 계약을 나눈다.

S3 사업장 책임자·운영 매니저 단계 결정을 누가 왜 했는지 설명하고 싶다 사업장에 책임자가 1명인 경우가 있다 [추정]

5. 가치 제안 (6요소)

S1 간호·생활지원 직원

  • Who: 퇴원한 입주자를 처음 살펴보는 직원
  • Why: 퇴원 뒤 달라진 도움을 서비스로 바로 맞춰야 한다. 근거를 남길 틀이 없다
  • What before: 종이나 메모로 남기고 말로 전한다. 평가와 서비스 변경, 요금이 따로 논다 [추정]
  • How: 일상생활 7항목 × "혼자 하심 / 가끔 도움을 드림 / 매번 도움을 드림 / 살펴보지 못함" + 본 일 한 줄로 기록하고, 그 기록을 붙여 단계 변경을 제안한다. 결정되면 더해진 서비스 시간이 입주자 시간표에 들어간다
  • What after: 근거가 붙은 제안이 결정자에게 가고, 결정 뒤 해야 할 일(서비스 시간, 경리 확인할 일, 건강 소식)이 한 번에 생긴다
  • Alternatives: 종이 평가표, 엑셀, 구두 인계. 모두 결정과 근거를 잇지 못한다
  • 문장: 퇴원한 입주자를 살펴본 것을 정해진 틀로 남기고, 그 기록을 근거로 서비스 변경을 제안한다. 결정은 다른 사람이 한다.

S2 생활지원 직원 (외부 돌봄)

  • Who: 방문요양을 함께 받기 시작한 입주자를 맡은 직원
  • Why: 외부 기관 시간과 레지던스 서비스 시간이 겹치면 한쪽이 빠진다
  • What before: 회원 또는 가족의 말이나 기관 전화로 듣고 수기로 맞춘다 [추정]
  • How: 외부 돌봄 일정을 입력하면 같은 입주자의 레지던스 서비스 시간과 겹침을 바로 보이고, 어느 쪽을 옮겼는지 기록한다
  • What after: 서비스 날 전에 겹침을 알고 처리한다. 회원 화면에 바뀐 시간이 보인다
  • Alternatives: 전화와 수기 메모
  • 문장: 방문요양 일정을 레지던스 서비스와 같은 시간표에 놓고, 겹치면 서비스 날 전에 직원에게 알린다.

S3 사업장 책임자·운영 매니저

  • Who: 단계 변경을 결정하고 나중에 설명해야 하는 사람
  • Why: 결정이 분쟁이 되면 남은 근거가 없고, 결정 책임이 한 사람에게 쏠린다 [추정]
  • What before: 상담 일지와 기억
  • How: 제안자와 결정자를 나누고, 설명·의견 기록 전에는 결정을 막고, 결정한 까닭을 필수로 받고, 이력을 고칠 수 없게 한다
  • What after: 결정 하나에서 평가, 의견, 제안자, 결정자로 따라간다
  • Alternatives: 상담 일지, 내부 결재 메일
  • 문장: 단계 변경 하나마다 평가, 입주자 의견, 제안한 사람, 결정한 사람과 까닭이 한 이력으로 남는다.

6. 범위 — MVP (혼자 2~4주, 코어 위)

핵심 흐름 2개

  1. 단계 변경: 평가 기록 → 단계 변경 제안 → 입주자 설명·의견 → 다른 사람의 결정 → 회원 화면, 경리 확인할 일, 건강 소식(D)
  2. 외부 돌봄 병행: 외부 돌봄 일정 입력 → 레지던스 서비스 시간과 겹침 경고 → 처리 기록 → 회원 화면
  • 단계는 양쪽으로 바뀐다. 기본 서비스로 돌아가는 것도 같은 흐름이다.
  • 단계 정의는 MVP에서 시드(사업장 1, 버전 1)로 두고 읽기 화면만 둔다. 편집과 새 버전은 P1이다.
  • 요금은 바꾸지 않는다. 단계마다 "요금 묶음"을 두고, 결정 전후의 요금 묶음이 다르면 요금 영향이 "계약 변경 필요"가 되어 결정 때 경리 확인할 일에 계약 변경 요청 한 줄을 남기는 것까지 한다(양쪽 방향 모두). 청구는 계약을 바꾸기 전까지 그대로다.
  • 외부 돌봄 병행과 거처 상담은 레지던스 서비스와 요금 묶음을 지금 그대로 이어받는다(카피 names.md 1절 "레지던스에서 받으시는 도움은 그대로예요", copy 2-3 "입주 계약은 바뀌지 않습니다") [가설]. 그래서 이 두 단계로 바뀔 때는 계약 변경 요청이 생기지 않는다.
  • 하지 않는다: 장기요양 등급 판정, 요양 급여 청구, 의료 판단, 퇴거 결정(14절).

11. 시니어 접근성

  • 큰 글씨와 터치 영역: 회원 화면 본문 18px 이상, 버튼 44×44 CSS px 이상 [사실, WCAG 2.1 2.5.5 https://www.w3.org/TR/WCAG21/#target-size, 2018], 200% 확대에서 가로 스크롤 없음(코어와 같음).
  • 한 화면에 하나의 행동: 회원 첫 화면의 주된 행동은 읽기다. [다시 봐 주세요]는 확인 창에서 한 번 더 묻는다.
  • 쉬운 말: 단계 번호, "판정", "등급", "케어 플랜", "전원" 같은 말을 쓰지 않는다(C product-marketing Words to avoid).
  • 되돌리기: 단계는 양쪽으로 바뀐다. 회원은 [다시 봐 주세요]로 다시 살펴봐 달라고 한다(P1). 직원의 결정은 되돌리지 않고 새 제안·결정으로 바꾼다.
  • 음성·전화 대안: [프런트로 전화하기] 버튼, 다시 봐 주세요의 [말로 하기]. 설명과 의견은 대면이 기본이다.
  • 보호자·직원 대행: 프런트 직원이 회원 화면을 읽어 드린다. 설명 자리에 대리인(회원 화면에서는 "대신 처리하실 분")이나 회원이 고른 가족이 함께한다. 의견은 회원 본인의 말로 적는다.

12. 개인정보와 안전

  • 민감정보: 평가 기록(일상생활 도움, 기억·판단 관련 본 일), 장기요양 인정 결과, 외부 돌봄 일정은 건강 관련 정보로 다룬다 [추정, 법률 검토: 개인정보 보호법 제23조 민감정보 해당 여부]. 진단명, 진료 결과, 처방, 점수는 받지 않는다. 외부 전문가 의견 원문, 퇴원 서류 내용은 저장하지 않는다(받은 날·곳만).
  • 최소 수집: 장기요양은 상태(없음/신청 중/받음)와 등급, 유효기간, 증빙 받은 날만. 등급을 받는 근거와 보관 기간은 [법률 검토].
  • 열람: 평가, 설명, 이력은 간호·생활지원 직무와 책임자, 본사 운영 매니저만 보고, 볼 때마다 SENSITIVE_READ. 경리는 단계 이름과 계약 변경 요청만. 프런트는 회원 화면 범위(평가 내용 없음)만 보고, 프런트나 대리인이 회원 화면을 열 때도 SENSITIVE_READ로 남긴다(외부 돌봄·의견 요약이 들어 있어서). 소유주와 보호자는 C 화면이 없다.
  • 보호자 공유: 결정된 변경만 D 건강 소식으로. D가 건강 소식 별도 동의를 검사한다. 평가 내용, 기억·판단 기록, 입주자 의견, 다시 검토 요청, 결정 전 제안은 보내지 않는다. 회원이 알리지 말라고 하면 올리지 않는다(MEMBER_REQUEST). D가 받는 올리지 않는 이유는 MEMBER_REQUEST·NOT_A_HEALTH_EVENT 두 가지뿐이고(D 확정), C는 MEMBER_REQUEST만 쓴다.
  • 사람이 개입하는 지점: 평가(간호·생활지원), 제안(직원), 설명·의견(직원 + 회원), 결정(제안하지 않은 책임자), 계약 변경(경리 + 회원 서명, 코어 Next), 겹침 처리(생활지원). 시스템은 어느 지점도 대신하지 않는다.
  • 응급: C는 응급 대응을 하지 않는다. 입원과 이송은 B와 코어 비상 연락처의 일이다.
  • 법적 문구: 회원 화면 copy 3-3 두 줄과 4절 "지낼 곳 함께 의논" 상세는 [법률 검토 전 초안]이다. 입주 계약서의 변경·해지 조항을 확인하기 전에는 실서비스에 쓰지 않는다 [NEED].
