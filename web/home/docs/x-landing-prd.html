표기: 문장 끝 [사실] 원본 문서나 사용자 말로 확인됨, [추정] 근거로 미루어 봄, [가설] 이 문서가 새로 정한 것으로 사용자 확인 필요, [미정] 아직 정하지 않음. 표시가 없는 문장은 앞 문장과 같은 표기를 따른다.

이 사이트는 포트폴리오용 가상 서비스의 소개 사이트다. 실제 시설, 주소, 입주자, 직원, 후기, 효과 수치, 협력 병원, 인증, 수상은 없다. 사람과 공간 이미지는 모두 AI로 만든 가상 장면이다 [사실: 사용자 지시, CLAUDE.md 사실과 근거].

1. 요약

입주를 고민하는 시니어 본인과 보호자 자녀에게 Evenstay에서의 하루, 건물과 공간, 숙소, 직원, 오시는 길을 보여 주고, 회원님이 정하고 가족이 함께 보는 방식을 알리는 소개 사이트다 [사실: 사용자 요청]. 메인 랜딩 한 장(LND-00~15)이 입구이고, 소개·시설·숙소·생활·오시는 길·입주 상담 페이지가 뒤를 받친다 [가설]. 디자인 시스템(DESIGN.md v2.6, 사용자 재승인 2026-11-04)과 MVP 화면 프로토타입이 이미 있어서 앱 화면은 실제 모습으로 보여 준다 [사실]. 면접관에게는 메인 끝에서 설계와 데모로 가는 길을 준다 [가설].

3. 배경

  • 사용자 지시 순서: 랜딩 기획 → PRD·화면 정의서 → landing-page-design 프로토타입 → emil 스킬로 애니메이션·검수 [사실: 사용자 말, 2026-11-03]. 이 문서는 첫 단계다.
  • 메인 상단은 "뷰가 좋고 깨끗한 Evenstay 숙소에서 책을 보거나 여가를 보내며 쉬는 시니어" 영상 여러 편이 차례로 나온다 [사실: 사용자 말]. "뷰가 좋고"는 "가까운 신록과 안뜰이 보이는 방"으로 풀었다. 먼 산·강·호수를 넣지 않아 입지가 정해지지 않게 한다 [사실: KEY-TONE 확정, shared/decisions.md 2026-11-04]. 건물, 숙소, 시설 전경도 영상으로 보여 준다 [사실: 사용자 말 "직원응대 말고 매력적인 건물과 숙소, 시설 전경들도 소개되어야 될것 같은데"(허브 전달)].
  • 키 이미지, 인물 시트, 영상 원본처럼 고품질이 꼭 필요한 이미지만 gpt-image-api로 만들고, 그 이미지로 higgsfield MiniMax H3 영상을 만든다. 이미 만든 VID-BLDG, VID-ROOM은 Kling 4.0 파일을 쓴다 [사실: 사용자 "영상모델도 MiniMax H3 로 확정했어", 2026-11-04]. 일러스트, 평면도, 약도, 마스코트, 단순 이미지는 gpt-image로 만든다 [사실: 사용자 말, 허브 전달 2026-11-04]. gpt-image-api 모델은 gpt-image-2.5-sunburst다 [사실: 사용자 "확정하고 진행", 허브 전달 2026-11-04]. gpt-image-2.5-pro는 API에 없다 [사실: 허브 전달].
  • 건물, 시설, 숙소, 직원 유니폼이 사진마다 달라지지 않도록 키 이미지를 먼저 만들고 나머지는 그것을 참조해 만든다 [사실: 사용자 말]. 계획은 asset-plan.md 2~3절.
  • 어떤 UI 요소에도 이모지를 쓰지 않는다 [사실: 사용자 말].
  • 지금 MVP 화면은 모두 앱 안쪽 화면이라, 시설과 사람을 보여 주는 바깥 문이 없다 [추정].

4. 목표

목표: 처음 보는 사람이 3~5분 안에 "회원님이 편안히 지내고, 가족은 회원님이 허락한 소식만 보고, 중요한 일은 사람이 정한다"를 이해하고, 건물·숙소·직원이 한 곳의 모습으로 읽힌다 [가설].

성공 기준(정성, 지어낸 수치 없음): 프로토타입 검수에서 예/아니오로 확인한다 [가설].

  1. 시니어 본인 관점: 메인 히어로부터 첫 행동(상담 신청 또는 전화)까지 스크롤만으로 닿고, 모든 페이지 끝에 상담·전화 띠가 있다.
  2. 보호자 관점: "볼 수 있는 범위는 회원님이 정한다"는 뜻이 메인 패밀리 섹션과 생활·서비스 페이지에서 읽힌다. "지켜보세요" 같은 감시 표현이 없다.
  3. 접근성: 자동 재생 영상은 소리가 없고, 일시정지 버튼과 양쪽 화살표가 키보드와 터치로 동작하며, prefers-reduced-motion에서는 포스터만 보인다. 본문 대비 WCAG 2.2 AA.
  4. 사실 표기: 후기, 입주자 수, 정원 수, 면적, 가격, 수상, 인증, 협력 병원, 효과 수치를 지어 넣지 않았다. AI 생성 표기가 사람·공간 사진이 있는 모든 페이지에 있다.
  5. 판단 단어 0개: 낙상, 쓰러짐, 응급, 위험, 배회, 미납, 연체, 퇴소, 판정이 화면 글자와 대체 텍스트에 없다.
  6. 일관성: 같은 건물, 같은 실내 재질, 같은 유니폼, 같은 인물이 페이지를 넘어 같은 모습으로 보인다(키 이미지 대조 검수).
  7. 면접 시연: 메인 면접관 안내 섹션에서 MVP 프로토타입과 설계 문서로 한 번에 갈 수 있다.
  8. 안심·건강 지원: 호출이 오면 직원이 가고 아무도 맡지 않으면 다음 직원에게 넘어간다는 흐름이 메인과 /safety에서 읽힌다. Evenstay가 진단·치료한다는 문장, 도착 시간 약속, 지어낸 간호 인력·협력 병원·자격이 없다.
  9. 식사: 상차림 사진이 같은 식기·식탁·빛으로 보이고, 식단표에 "예시 식단" 표시가 있으며, 영양 수치·칼로리·원산지·영양사·식비 금액을 지어 넣지 않았다. "의료식", "치료식"이라는 말이 없다.

5. 대상

순위 대상 이들의 문제·일 제약
주 1 입주를 고민하는 시니어 본인(70~80대, U1) 내 생활과 결정권을 지키며 편히 지낼 곳을 고른다 [추정: 01-research/outputs/personas.md U1] 작은 글씨, 빠른 움직임, 앱 가입 요구가 부담 [추정]. 전화·방문이 익숙한 길
주 2 보호자 자녀(원거리, U3) 부모님 생활을 부모님 뜻을 지키며 알고 싶다 [추정: personas U3] 낮에 일하며 휴대폰으로 짧게 본다 [추정]
보조 포트폴리오 면접관(Tech Lead 채용) 이 사람이 시니어 하우징 PMS를 어떻게 설계하는지 빨리 본다 [사실: 지원 목적] 시간 3~5분 [사실: 04-planning/CLAUDE.md 데모 시나리오]

운영 직원, 소유주, 지자체는 이 사이트의 대상이 아니다 [가설]. 그들의 화면은 프로토타입에서 본다.

6. 가치 제안

6-1. 시니어 본인

  • Who: 입주를 고민하는 시니어 본인.
  • Why: 편히 쉬는 생활과, 내 일을 내가 정하는 것을 함께 지키고 싶다 [추정].
  • What before: 시설 소개는 공간 사진과 서비스 목록이 대부분이고, 내 기록을 가족에게 얼마나 보여 줄지 내가 정할 수 있는지는 잘 보이지 않는다 [추정: 01-research 문제 은행 P-008·P-047 계열, 소개 사이트 조사는 하지 않음].
  • How: 건물·숙소·공용 공간과 하루의 장면(영상), 직원 사진, 앱이 없어도 되는 길(호출벨, 프런트 전화, 직원이 함께), 회원님이 정하는 범위를 차례로 보여 준다.
  • What after: "편히 지내면서도 내가 정한다"를 확인하고, 전화나 방문으로 다음 걸음을 뗀다.
  • Alternatives: 다른 시설의 소개 책자, 직접 방문, 지인 소개. 차이는 정하는 사람이 회원님이라는 점을 앱 화면으로 보여 주는 것이다 [가설].
  • 문장: 편안한 하루는 그대로, 내 소식을 누구에게 얼마나 보여 줄지는 회원님이 정하는 레지던스 [가설, 화면 문구 아님 [NEED: 카피]].

6-2. 보호자 자녀

  • Who: 멀리 사는 보호자 자녀.
  • Why: 부모님 생활과 청구서를 부모님 설명에만 기대지 않고 알고 싶다 [사실: D value-prop.md 2].
  • What before: 전화로 묻거나 방문해야 안다 [추정].
  • How: Evenstay 패밀리에서 회원님이 보여 주기로 한 생활 소식, 일정, 청구서, 건강 소식, 생활 요청을 본다 [사실: D value-prop.md 2, D prd.md F20]. 사이트는 이 화면을 실제 프로토타입 캡처로 보여 주고, 시설·숙소·오시는 길로 방문 준비를 돕는다.
  • What after: 같은 기록을 같은 때에 근거와 함께 본다 [사실: 브랜드 3안 "함께 보는 기록", evenstay/design/brand/concepts.html 승인 2026-11-03].
  • Alternatives: 전화, 단체 대화방, 방문. 차이는 직원이 확인한 기록과 회원님이 정한 범위다 [사실: D value-prop 2].

6-3. 면접관(보조)

  • Who / Why: Tech Lead 채용 면접관. 도메인 모델, 권한, 외부 연동 경계를 빨리 본다 [사실].
  • How: 메인 끝 한 섹션에 모듈 일곱 개의 한 줄 소개, 소유주 월 리포트·위탁 계약 이력 한 줄, 프로토타입·설계 문서 링크를 둔다 [사실: 카피 정한 것 7, shared/decisions.md 2026-11-04].
  • What after: 회원·보호자 경험에서 운영 설계로 바로 넘어간다.

7. 해결책

7-1. 흐름

  • 메인(2026-11-04 순서): 히어로(영상 6편 차례 재생) → 공간과 하루 → 식사(LND-14) → 여가와 모임(LND-15) → 약속 세 가지 → 직원 → 회원님이 쓰시는 앱, Evenstay 홈(청구서, 생활 요청, 홈 비서) → 가족이 쓰는 앱, Evenstay 패밀리 → 도움이 더 필요해질 때 → 도움이 필요하실 때(안심·건강 지원, LND-13) → 앱이 어려우시면 → 앱이 혼자 정하지 않아요 → 상담·전화·방문 → 면접관 안내 → 푸터 [가설]. 히어로 다음 세 섹션을 생활로 두고 안심·건강 지원은 뒤로 뺐다 [사실: 레드팀 3 "메인 첫 세 섹션 중 둘 이상이 안전·건강이면 순서를 바꾼다"]. screen-spec.md 2절.
  • 메인의 각 섹션은 해당 페이지로 이어진다(공간과 하루 → 시설 소개, 식사 → 식사 소개, 직원 → Evenstay 소개, 안심·건강 지원 → 안심·건강 지원, 상담 → 입주 상담) [가설]. 페이지 정의는 screen-spec.md 8절.

7-2. 꼭 넣을 것(첫 버전)

  • 히어로 순차 영상: 건물 전경과 숙소 2편에 시니어 휴식 장면 4편을 이어 모두 6편, 소리 없음, 일시정지 버튼, 영상별 지속 시간 띠, 양쪽 화살표, 현재 영상 설명, 교차 전환, 움직임 줄이기에서 포스터 [사실: 사용자 말·허브 지시, U-02 사용자 변경 2026-11-04]. 공용 라운지 영상은 LND-03에 둔다 [가설].
  • 키 이미지 먼저: 톤, 건물, 실내(공용·숙소), 유니폼, 반복 인물의 기준 이미지를 먼저 만들고 사용자가 확인한 뒤에만 나머지를 만든다 [사실: 사용자 말].
  • 사람: 센터장 1명과 역할별 직원(프런트, 생활 지원, 식당)은 모두 가상 인물이다. 간호 직원 카드는 간호 인력 배치를 운영에서 확인한 뒤 더한다(U-12). 경력·자격·학력·수상은 쓰지 않는다 [사실: 허브 지시].
  • 식사: 식당 공간, 하루 세 끼, "예시 식단"이라고 밝힌 주간 식단표, 상차림 사진, 함께 드시는 장면, 드시지 않는 끼니와 청구서의 연결을 메인 LND-14와 /dining에 담는다 [사실: 허브 요청]. 범위는 13절.
  • 안심·건강 지원: 호출벨·신호가 오면 당번 → 2차 → 책임자 → 모두 호출로 넘어가는 흐름, 119 신고와 병원으로 모실 때 직원이 하는 일과 가족 연락, 회원님 동의 범위 안의 평소 살핌, 회원님이 정하는 공개 범위, 앱 없이 되는 길을 메인 LND-13과 /safety에 담는다 [사실: 허브 요청, 근거는 B 안심 알림 기획]. 범위는 12절.
  • 앱 화면: Evenstay 홈·패밀리 화면은 기존 프로토타입을 캡처해 쓴다. 새로 그리지 않는다 [가설].
