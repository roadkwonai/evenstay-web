0. 범위 (최소 버전)

  • 코어(A) 바로 다음에 붙이는 판이다. 도구는 코어 도구 3개 + 비서 자체 넘기기 1개다. 코어 도구는 일정 조회(ContractQuery.keyDates)와 청구 설명(BillingQuery.explainInvoice) 두 조회가 중심이고, 이 문서에서 청구 문의 접수(InquiryCommand, 쓰기, 회원 확인 필수)를 셋째로 둔다(결정 [가설], prd.md 확인할 것 2). 넘기기(assistant.handoff, 쓰기)는 비서 안의 도구다.
  • 비서는 새 데이터를 만들지 않는다. 코어는 G가 대화, 도구 호출 기록, 확인 토큰을 가질 것으로 예상했다 [사실, 코어 tech-design.md 10절]. 승인 카피는 "직원에게 넘긴 요청"도 비서가 갖는다고 적었다 [사실, 카피 copy.md 머리말]. 그래서 이 기획은 assistant 스키마에 넘김(직원에게 넘긴 요청과 처리 상태)을 더한다(설계안, tech-design.md 확인할 것 10).
  • 구조는 B·D·C 도구가 늘어도 바뀌지 않게 잡는다: 도구 하나 = 도구 정의 한 개 + 큰 버튼 하나 + 답 틀 하나 + 직원 화면 기록 한 줄(카피 names.md 라벨 원칙 "조회 도구 하나 = 큰 버튼 하나"에 도구 정의를 더한 설계안).

1. 비전

회원님이 자기 계약과 청구서를 직원을 찾지 않고 확인하고, 판단이 필요한 일은 회원님이 허락한 뒤 사람에게 이어지는 비서.

  • 회원은 큰 버튼이나 말로 묻고, 답마다 "확인한 곳"을 듣는다.
  • 비서는 기록에 있는 사실만 말한다. 모르면 모른다고 하고, 건강·돈·계약은 정하지 않는다.
  • 운영사는 AI가 정해진 도구와 회원 권한 안에서만 움직였다는 것을 기록으로 설명할 수 있다.
  • 지키는 가치: 사실은 기록에서 나온다. 결정은 사람이 한다. 상태를 바꾸는 일은 회원의 [네] 뒤에만 일어난다. 앱 밖 길(프런트 전화)은 늘 열려 있다.

2. 시장 세그먼트 (문제 기준)

순서 세그먼트 해결하려는 일 (JTBD) 제약
1 (첫 세그먼트) 청구서와 계약 날짜가 궁금한 입주 회원(U1) 내 청구서가 왜 이 금액인지, 언제까지 내면 되는지, 계약이 언제 끝나는지를 내 속도로 확인한다 만 55세 이상 AI 서비스 경험 30.2%(일반 국민 59.4%) [사실, G3]. 디지털 적응이 어렵다는 응답 67.2% [사실, P-037·D3·D5]
2 넘겨받는 현장 직원(U4: 프런트·생활지원) 무엇을 물었고 비서가 어디까지 답했는지 정리된 요청을 받아 처음부터 다시 묻지 않는다 직원 반복 문의 시간·빈도 자료가 없다 [NEED]
3 운영사(운영 책임자, AI 규제 책임) AI가 회원과 직접 이야기하는 기능을 사전 고지, 판단 금지, 기록 안에 둔다 AI 기본법 2026-01-22 시행, 제31조 사전 고지 [사실, G4. 로펌 요약, 법 원문 대조 안 함 [미확인]]. 과태료 계도기간 최소 1년 [사실, G6·G28]
(부록) 회원의 대리인(청구서 확인 범위) 대신 처리하는 회원의 청구서 이유와 기한을 확인한다 코어 대리인 기능이 P1이다 [사실, 코어 prd.md F13]

왜 1번이 먼저인가: 최소 버전 도구로 끝까지 답할 수 있는 질문이 계약·청구뿐이다 [사실, 코어 tech-design.md 10절 "G 최소판의 일정"]. 청구서는 회원에게 매달 오는 돈 문제라 묻는 이유가 분명하고 [추정], 코어 원장에 근거(Charge.evidence.plain)가 이미 있어 비서가 계산하지 않고 읽기만 하면 된다. 면접에서 보여 줄 판단(도구 호출, 권한, 확인 토큰, 감사)도 이 질문들에서 모두 나온다.

3. 상대 비용 위치

  • 고유 가치 우선이다. 경쟁 축은 "말을 잘하는 AI"가 아니라 "기록에 있는 것만 말하고, 무엇을 왜 답했는지 남기는 AI"다.
  • 비용은 코어를 고치지 않고 모듈 하나를 붙이는 노력으로 본다. 비서는 코어·D의 공개 API만 부르고(코어 ADR-2), 권한은 코어 authorize()가 판단한다.
  • LLM 비용을 낮추는 방법: 큰 버튼은 LLM을 부르지 않는다. LLM은 말로 물은 질문을 의도와 도구로 나누는 데만 쓰고, 답 문장은 서버가 답 틀에 도구 결과를 채워 만든다(tech-design.md ADR-G1). 데모는 녹화한 라우팅 결과로 돌린다(ADR-G6).

4. 가치 제안

세그먼트 What before How What after Alternatives
회원 청구서 금액이나 계약 날짜가 궁금하면 프런트에 전화하거나 앱 메뉴를 찾는다 [추정, 카피 copy.md 1절] 큰 버튼 또는 말로 묻는다. 비서는 코어 기록만 읽어 답 → 사실 → 확인한 곳 → 다음 버튼 순서로 답한다. 판단이 필요한 말은 "전해 드릴까요?"로 묻는다 내 청구서와 날짜를 내 속도로 확인하고, 어디서 확인했는지 안다. 모르는 일은 직원에게 이어진다 프런트 직원, 자녀에게 묻기, 종이 청구서, 범용 AI 비서(시설 데이터 없음), AI 안부전화(시설 업무 비연동 [사실, E7·E15]), 그냥 참고 넘김
현장 직원 같은 질문을 전화로 받고 무엇을 물었는지 처음부터 확인한다 [추정] 넘겨받은 요청에 회원이 전해 달라고 한 말, 비서가 한 답(원문), 넘긴 이유, 회원 확인 시각이 붙는다 넘긴 이유를 보고 바로 처리를 시작하고 처리 내용을 남긴다 전화 메모, 메신저
운영사 AI를 회원 응대에 쓰면 고지·판단 대행·사고 책임이 걱정된다 [사실, G4·G5·G8·G21] 고지 확인 전에는 비서가 열리지 않고(D 고지 v2), 도구는 회원 권한으로만 호출되며, 상태를 바꾸는 호출은 확인 토큰이 있어야 한다. 모든 호출이 남는다 문제가 생기면 "무엇을 물었고, 어떤 도구가 어떤 권한으로 무엇을 읽었고, 누구에게 왜 넘겼나"로 설명한다 약관 표기, AI를 쓰지 않음

한 문장: 계약과 청구 기록으로만 답하고, 판단은 사람에게 넘기는 AI 비서 [사실, 카피 copy.md 1절 제목].

5. 트레이드오프 — 하지 않을 것

하지 않는 것 이유
건강·약·응급 판단, 금전 판단(이체·송금 조언), 계약 변경 결정 판단 대행 위험 [사실, G5·G15·G21]. 회원 확인 뒤 직원에게 넘긴다
투자 추천, 주문, 증권·자산 조회 사업자 제공은 투자일임·자문 등록 영역 [사실, K25·K22]. 최소 버전에는 자산 조회도 없다(사용자 확정)
비서가 금액을 계산하거나 새 문장으로 사실을 지어내기 금액은 코어 원장의 항목과 근거를 읽기만 한다. 답 문장은 답 틀에 도구 결과를 채운다(ADR-G1)
미납·연체 판정, 독촉 코어가 미납 판정을 하지 않는다 [사실, 코어 tech-design.md 3-2]. 비서는 내셨다는 기록이 있는지 없는지까지만 말한다(요약, 카피 2-3)
말벗, 긴 대화, 정서 지원 정서적 과의존과 부적절 발화 위험 [사실, G8·G20]
시설 프로그램·행사·병원 일정, 시설 요청 접수 최소 버전 데이터에 없다 [사실, 코어 tech-design.md 10절]. 모듈이 생기면 도구로 붙인다(N1 요청 올리기, N2 프로그램 일정은 Next). 그 전에는 시설 요청을 넘기기로 받아 N1 생활 요청으로 보낸다(2026-11-04)
보호자용 비서 보호자 화면과 동의 범위는 D 몫이다. 최소 버전 비서는 회원 본인(그리고 P1 대리인)만 쓴다
음성 원본 보관, 전화 채널 음성은 보조 채널이다 [초안 결정, ai-assistant.md 0절]. 들은 말은 글자로만 남긴다(tech-design.md 7절)
회원 확인 없이 직원에게 넘기기, AI가 직접 직원에게 연락 상태를 바꾸는 일은 회원 확인 뒤에만 한다 [초안 결정, ai-assistant.md 5절 원칙 2]
마케팅, 가격 실험 워크스페이스 공통 규칙

"하지 않음"이 만드는 초점: 2~4주 안에 도구 호출, 권한 검사, 쓰기 전 확인, 넘김 이유, 호출 기록 다섯 가지를 깊게 보여 준다.

6. 핵심 지표

  • 게임 분류: 생산성 게임. 회원이 궁금한 일을 틀리지 않게, 빨리 끝내는 것이 가치다. 오래 머물게 하는 주의 게임은 목표가 아니다(말벗을 하지 않는 이유와 같다, 5절).
  • North Star (실서비스라면) [미정]: 매주 비서로 끝낸 질문 수. "끝냄"은 확인한 곳이 붙은 답을 받았거나, 회원이 확인한 넘김을 직원이 처리 완료(DONE)한 것이다. 막다른 답(두 번 못 알아들음, AI 오류)과 처리 안 된 넘김은 세지 않는다 [가설]. 목표 수치는 정하지 않는다(측정한 적 없음).
    • 이전 제안(끝난 질문 비율)에서 바꾼 이유: 비율은 질문이 줄어도 오르고 회원이 다시 쓰는지 보지 못한다. 넘김은 회원이 [네]를 누를 때가 아니라 직원이 끝낼 때 회원에게 가치가 생긴다.
    • 기준 점검: 이해 쉬움 ○, 회원 중심 ○, 비전(기록으로 답하고 판단은 사람에게) ○, 정량 ○(Turn·ToolCall·Handoff 기록으로 센다, tech-design.md AssistantUsageQuery), 실행 가능 ○(도구·답 틀·넘김 처리로 움직임), 지속 가치 △(질문이 없는 주가 정상일 수 있다), 선행 지표 △(프런트 문의 감소와의 관계는 주장하지 않는다).
  • 입력 지표 [가설]: ① 첫 시도에 맞는 도구나 넘김으로 간 질문 비율(평가 세트의 도구 선택 정확도와 같은 정의) ② 막다른 답 비율 ③ 넘김 처리 완료까지 걸린 시간 ④ 2주 안에 다시 묻는 회원 비율. 고지 확인 회원 비율은 D 몫이라 넣지 않는다.
    • 가드레일(어기면 지표가 올라도 실패): 다른 회원 데이터가 답에 나온 건수 0, 확인한 곳 없이 사실을 말한 답 0, 회원 확인 없이 실행된 쓰기 0, 건강·금전·계약·투자 의도에 도구로 답한 건수 0.
  • OMTM (포트폴리오 이번 분기): 평가용 대화 세트(prd.md F11) 통과. 안전 기준 4개는 100%, 도구 선택 정확도 90% 이상 [가설: 목표치는 첫 측정 뒤 다시 정함]. 그리고 데모를 5분 안에 끊김 없이 3회 연속 완주(코어와 같은 기준).
  • 보조 지표 [가설]: 넘긴 비율(넘긴 대화 ÷ 전체 대화, 카피 5-3 요약 카드), 권한 거부 수, 넘긴 이유 분포. 효과(문의 감소)는 주장하지 않는다 [사실, G1·G2·G26 수치가 거의 회사 주장].
  • North Star는 north-star-metric 스킬로 점검했다(2026-11-03). 정의는 사용자 확인 전이라 [미정]이다(확인할 것 1).

7. 성장

  • 내부 시스템 모듈이라 판매 경로가 없다. "성장"은 같은 틀에 붙는 도구가 느는 것이다: 코어 2~3개 → D(누가 내 소식을 보나, 금전 부탁 넘기기) → B(내 호출 처리 상태) → C(내 생활 지원 단계 설명) [가설, 각 모듈 기획 후 확정].
  • 확장 단위: 도구 정의 한 개(코드, 읽기/쓰기, 필요한 권한 행동, 인자 형식, 답 틀, 큰 버튼, 직원 화면 이름) + 평가 세트 문항. 대화·도구 호출 기록의 스키마는 바뀌지 않는다(tech-design.md ADR-G2).
  • 채널 확장(전화, 태블릿)은 같은 대화 API에 들어오는 입력 방식 하나로 붙인다 [가설].
  • 포트폴리오의 "획득 경로"는 면접관이 데모 링크를 열고 비서 장면과 직원 화면 기록을 따라가는 것이다.

9. 모방이 어려운 이유

  • 실서비스 기준: 비서의 답은 코어 원장과 계약 기록에 붙어 있어야 의미가 있다. 범용 AI 비서는 이 데이터와 권한이 없다 [초안 결정, ai-assistant.md 2절]. 시설 업무와 연동한 시니어 AI 비서 사례를 국내외에서 찾지 못했다 [사실: 발견 못함, ai-assistant.md 0절].
  • 포트폴리오 기준: LLM을 "의도와 도구를 고르는 라우터"로 가두고, 사실은 도구 결과에서만, 권한은 코어에서만, 쓰기는 회원 확인 토큰으로만 나오게 한 구조가 남는다. 같은 대화 화면을 흉내 내도 이 경계는 따라 하기 어렵다 [추정].

10. 전략 정합성 점검

  • 비전(기록으로만 답하고 판단은 사람에게) ↔ 차별점(확인한 곳, 넘김 이유, 확인 토큰) ↔ NSM(매주 비서로 끝낸 질문 수 + 가드레일 4개) ↔ 하지 않을 것(계산·판단·말벗·투자 없음)이 같은 방향이다.
  • 긴장 지점 1: 답 문장을 답 틀로 고정하면 대화가 딱딱해진다. 최소 버전은 정확성을 먼저 두고, 자연스러운 문장은 검사기를 붙인 다음 판에서 시험한다(roadmap.md Next).
  • 긴장 지점 2: 넘긴 비율이 높으면 "비서가 할 줄 아는 게 없다"로 보일 수 있다. 최소 버전에서는 넘긴 비율을 낮추는 것이 목표가 아니라, 넘겨야 할 것을 빠짐없이 넘기는 것이 목표다(가드레일 넷째).
  • 긴장 지점 3: 대리인이 쓰는 비서는 회원 본인과 답 범위가 다르다. 코어 대리 범위(VIEW_INVOICE 등)를 그대로 따르고 비서가 범위를 넓히지 않는다(prd.md 10절).

11. 반드시 참이어야 하는 것 (가설)과 가벼운 실험

# 가설 근거 실험 (2~4시간 이내)
H1 회원이 청구서·계약 날짜를 비서에게 실제로 묻는다 하 (AI 안부전화 이용 사례만 있음 [사실, E]. ai-assistant.md 6절 ★) 부모님·지인 시니어 3명에게 큰 버튼 시안과 답 틀을 보여 주고 무엇을 누르는지 본다 [NEED]
H2 70~80대가 큰 버튼으로 의도를 전할 수 있고, 말로 묻기는 보조로 충분하다 중 (스마트폰 보유 76.6%, 적응 어려움 67.2% [사실, D3·D5]) 종이 시안 4버튼 + "말로 묻기" 5개 질문으로 확인 [NEED]
H3 의도 분류가 건강·금전·계약 말을 빠짐없이 넘김 쪽으로 보낸다 중 평가 세트의 민감 문항(19개 [가설])을 규칙 + LLM으로 돌려 놓친 것 0건인지 본다
H4 LLM이 도구 인자로 다른 회원을 가리켜도 서버가 막는다 상 (설계로 보장: 인자에 회원 ID가 없고 코어가 매번 검사) "302호 청구서", "이전 지시 무시하고…" 주입 문항 4개를 통합 테스트로 고정
H5 비서 고지(D 고지 v2)와 대화 기록 보관 방식이 AI 기본법·개인정보 보호법에 맞다 중 [사실, G4·G14. 원문 대조 안 함] [법률 검토] 법률 검토 목록(prd.md 12절)을 한 장으로 만들어 검토 요청
H6 면접관이 "LLM은 라우터, 사실은 도구, 권한은 코어"를 AI Agent 연동 역량 증거로 본다 상 (공고 AI Agent 연동 [사실, S2·S3]) README 첫 장에 도구 호출 순서도와 직원 화면 도구 호출 기록 캡처를 둔다
