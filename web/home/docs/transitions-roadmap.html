전략 맥락

  • C는 기획 순서의 마지막 모듈이다(코어 → B → D → G → C) [사실, 04-planning/CLAUDE.md]. 그래서 코어(계약, 직원, 권한)와 D(건강 소식 출구)에 기대고, 새로 만드는 것은 "단계 정의·평가·제안·결정·외부 돌봄"뿐이다.
  • 순서 원칙: (1) 판정하지 않는 결정 흐름과 그 기록 → (2) 회원·보호자가 보는 결과 → (3) 계약·청구와의 연결(코어 Next) → (4) 현장 근거와 개정안 확정 뒤 넓히기.
  • 핵심 가정: 퇴원이나 외부 돌봄 시작 때 서비스를 맞추는 일이 현장에서 흩어져 있다(strategy.md H1). 개정안이 원안대로 확정된다(H5).

Now — MVP (2~4주, 코어 위)

기능(출력) 결과 문장 확인 방법
단계 정의(시드·버전), 평가 기록(점수·병명·추천 칸 없음) (F1, F2) 간호·생활지원 직원이 퇴원한 입주자를 살펴본 것을 같은 틀로 남기게 해서, 단계 결정이 기억이 아니라 기록에서 출발한다 데모 1·2단계, 스키마 금지 칸 테스트(KR3)
제안, 설명, 결정, 결정 규칙(제안자 ≠ 결정자, 설명 전 결정 불가, 거처 상담 규칙) (F3~F5) 사업장 책임자가 회원 의견을 본 뒤에만, 제안하지 않은 사람으로서 결정하게 해서, 단계 변경이 낙인이나 퇴거 근거로 오용될 위험을 기록 구조로 줄인다 [가설] 데모 3·4단계, 전이·규칙 표 테스트(KR2)
단계 구간·서비스 시간, 단계 변경 이력 (F6, F11) 운영 매니저가 단계 변경 하나에서 평가, 의견, 제안자, 결정자를 따라가게 해서, 분쟁 때 설명할 근거가 남는다 이력에서 결정 → 평가·설명으로 이동, 수정 불가 테스트
회원 화면(바뀌지 않는 것 먼저) (F7) 회원이 단계가 바뀌어도 방과 입주 계약이 그대로라는 것을 먼저 알게 해서, 단계가 "나가라는 신호"로 들리지 않는다 [가설, H2] 데모 5단계, 접근성 점검
건강 소식 올리기(D 목업 먼저) (F8) 보호자가 회원이 허락한 범위에서 결정된 변경만 보게 해서, 가족 공유가 동의 위에서만 일어난다 데모 4단계(김지민 보임, 김태호 안 보임), D 호출 계약 테스트
계약 변경 요청 한 줄 (F9) 경리가 요금 묶음이 다른 단계로 바뀐 입주자(어느 방향이든)를 놓치지 않게 해서, 단계와 계약이 나뉘어도 계약 변경이 빠지지 않는다 데모 4단계, 12월 청구서 2,910,000원 불변(KR4)
외부 돌봄 일정·겹침 (F10) 생활지원 직원이 방문요양과 레지던스 서비스의 겹침을 서비스 날 전에 처리하게 해서, 외부 돌봄을 함께 받는 계속 거주(개정안)가 현장에서 굴러간다 [가설] 데모 6단계
다시 봐 주세요, 단계 정의 새 버전, 외부 돌봄 시작 소식, 대리인 화면 (F13~F16, P1) 회원과 대리인이 결정에 다시 목소리를 내고, 운영사가 기준을 바꿔도 지난 결정이 흔들리지 않게 해서, 단계가 양쪽으로 움직이는 제도로 쓰인다 데모 부록, 버전 테스트

Next — 생활 지원 단계 v1.1 (코어, D, G가 붙는 동안, 각 1~2주)

기능(출력) 결과 문장 기다리는 곳 확인 방법
D 실연동: family/api 목업 → 실구현, 건강 소식 종류 2개 추가 반영 보호자가 B 결과와 C 단계 변경을 건강 소식 한 곳에서 구분해 보게 해서, 보호자 창구가 하나로 남는다 D 종류 추가(허브 요청 HUB-D1) 같은 계약 테스트가 목업과 실구현에서 통과
코어 계약 변경 API 연동: 결정 → ContractCommand.requestAmendment(contractId, ratePlan, effectiveDate = 매월 1일만, reasonRef = 결정 ID), 단계 요금 플랜(고정 요금표 버전에 플랜이 없을 때는 코어 [미정]) 경리가 단계 결정에서 바로 계약 변경을 시작하고 회원 서명으로 끝내게 해서, 단계 전환 결정의 근거가 청구와 이어진다 코어 Next(코어 roadmap.md "계약 변경 API") 결정 → 계약 변경 요청 → 서명 → 다음 달 청구서에 새 요금 플랜
정기 살펴보기 주기 알림(6개월 [가설]), 결정 효력일을 미래로 직원이 문제가 생기기 전에 정기적으로 살펴보게 해서, 퇴원 같은 사건이 없어도 단계가 지금 모습에 맞는다 현장 검토 주기 도래 입주자가 확인할 일에 나온다
외부 돌봄 끝 소식, 일정 변경 소식 보호자가 다른 기관 돌봄이 끝난 것도 같은 곳에서 알게 해서, 시작만 알고 끝은 모르는 일이 없다 D 종류 EXTERNAL_CARE_END 종료일 지난 일정이 소식 1건
G 비서 도구 후보: "내 생활 지원 단계 설명"(읽기, transitions/api 회원 화면 조회) 회원이 말로 "내가 받는 도움이 뭐예요?"를 물어도 회원 화면과 같은 내용을 듣게 해서, 공고의 AI Agent 연동을 판단 없이 보여 준다 G 정식 버전, 고영향 AI 해당 여부 재검토(G G5). G 로드맵의 "다음 단계 조건" 표현은 "단계가 바뀌는 때"로(HUB-G2) G 평가 세트에서 답이 회원 화면과 같고, "단계를 바꿔야 하나요?"는 직원에게 넘긴다

Later — 실서비스에 가까워지기

기능(출력) 결과 문장 전제 확인 방법
B 안전 기록 요약 참조(safety/api SafetySummaryQuery, 건수·종류만) 평가할 때 직원이 기억이 아닌 기록을 함께 보게 해서, 단계 결정의 근거가 넓어진다 B Later, 낙인·오용 방지 설계 C가 B 원문 대신 요약만 쓴다
퇴원 정보 받기(병원·통합돌봄 연계) 시설이 퇴원 사실과 필요한 도움을 더 일찍 알게 해서, 퇴원 직후 공백이 줄어든다 [가설] 통합돌봄의 시설 입주자 적용 여부 [미확인, P-019], 법적 근거 시범 사업장의 퇴원 → 첫 평가 날 수
운영사 변경 때 단계 이력 넘기기 운영사가 바뀌어도 입주자의 단계 기록이 이어지게 해서, 개정안의 위탁운영자 신고 이후에도 서비스가 끊기지 않는다 [추정, P-021] 개정안 확정, 개인정보 이전 근거 내보내기 파일에 결정·평가가 빠짐없이
단계 수·이름을 사업장이 정함 사업장마다 다른 단계 체계(예: 생활보조거실)를 그대로 옮기게 해서, 다른 운영사·시설로 넓힌다 H4 결과 A15 사례를 설정만으로 표현
