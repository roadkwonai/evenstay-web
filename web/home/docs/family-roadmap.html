표기 규칙은 strategy.md와 같다. 시기는 날짜가 아니라 단계다. 포트폴리오 기준의 "확인 방법"은 데모와 테스트로 확인할 수 있는 것만 쓴다. 실서비스 효과는 [가설]이고 목표 수치를 정하지 않는다.

전략 맥락

  • D는 B·C 결과가 보호자에게 닿는 공통 출구다 [사실, shortlist "D는 B·C 결과의 공통 출구"]. G 비서는 D의 AI 고지를 쓰고, 다음 버전에 금전 접수를 D로 넘긴다(직원 → 회원이 허락한 가족) [가설]. 그래서 첫 결과는 "회원이 정한 범위를 정확히 지키는 동의 체계"이고, 다음 결과는 "다른 모듈이 그 체계를 그대로 쓰는 것"이다.
  • 순서 원칙: (1) 데모 5단계에 필요한 것 → (2) B·C가 기다리는 동의·건강 소식 API와 G가 기다리는 AI 고지 API → (3) 실서비스에 가까워지는 것.
  • 핵심 가정: 보호자가 한곳에서 보기를 원한다(H1). 틀리면 Next의 보호자 기능을 멈추고 동의·권한 모델만 코어 쪽 공용 부품으로 남긴다(shortlist D 축소 기준).

Now — MVP (코어 MVP 이후 2~4주)

2026-11-04: 모든 화면을 클릭형 프로토타입으로 만든다. 통합 데모 흐름에 나오는 기능은 Now에 둔다(F18, F20을 Next에서 옮김). F19는 화면만 있고 흐름에 넣을지는 코어가 정한다.

기능(출력) 결과 문장 확인 방법
항목별 허락, 직원 대신 입력 + 회원 확인, 건강 소식 별도 동의 (F1~F4) 회원이 가족마다 보여 줄 것을 직접 정하고, 직원이 도와도 넓히는 것은 회원 확인으로만 적용되게 해서, 운영사가 "회원 의사에 반한 공유"를 설계로 막는다 데모 1~2단계, 확인 대기 중 보호자 요청 거부 테스트
권한 확장 정책, 보호자 화면, 열람 기록 (F5~F7) 보호자가 허락된 것만 한곳에서 보고, 거둔 것은 다음 요청부터 볼 수 없게 해서, 철회가 늦게 반영되는 분쟁을 없앤다 KR2 결정표 테스트, 데모 3·5단계
건강 소식 수신 API와 올리지 않기 규칙 (F8) B 결과가 회원이 동의한 보호자에게만, 운영사 재량 없이 올라가게 해서, 야간 사고 소식을 운영사가 거른다는 의심을 받지 않는다 [가설] 멱등·버전 번호 테스트, 이유 코드 외 거부 테스트
주간 생활 리포트, AI 사용 고지 (F9, F10) 직원이 AI 초안을 근거와 함께 고쳐 보내고, 회원·보호자가 그 사실을 미리 알게 해서, AI 기본법 사전 고지를 고령자 눈높이로 이행한다(G4) 데모 4단계, "직원 확인 없는 발송 0건" 서버 테스트
공개 API, 알림 문자 로그 (F11, F12) B·C가 코어와 D를 고치지 않고 동의를 묻고 G가 고지 확인을 묻게 하고, 문자로 내용이 새지 않게 해서, 모듈을 붙여도 동의 체계가 하나로 유지된다 경계 검사, KR3 문자 검사
금전 부탁, 대리인 경로, 초대, AI 고지 현황, 피드백 (F13~F17, P1) 직원이 돈 부탁을 정해진 곳으로 넘긴 기록을 남기고, 판단이 어려운 회원은 대리인이 정하게 해서, 경제적 착취 의혹과 대리 처리의 근거 문제를 기록으로 대비한다(P-048, I-31) 데모 부록 2개
사업장 동의 현황 숫자(F19, P1) 사업장 책임자가 확인 대기와 열린 문의를 숫자로 한눈에 보게 해서, 운영 현황 대시보드(app/ D1)가 다른 모듈 데이터를 복사하지 않고 모듈 API만으로 조립된다는 것을 보인다 숫자가 시드 계산값과 같고 이름·ID 없음(US-22)
장기 부재 소식(F18, P1, 코어 장기 부재와 함께, 통합 데모에 나옴) [가설] 회원님이 오래 자리를 비우시거나 돌아오셨을 때, 생활 소식을 허락받은 보호자가 이유 없이 사실만 알게 해서, 연락이 닿지 않는 동안 보호자가 프런트에 거는 확인 전화를 줄인다 [가설] 생활 소식 허락 보호자에게만 카드·문자, 건강 소식만 허락받은 보호자와 취소된 부재에는 없음(US-21). 통합 데모 12/2~12/7 장면
생활 요청 허락(F20, P1, N1과 함께, 통합 데모에 나옴) [가설] 회원님이 허락한 보호자가 멀리서도 고장이나 불편을 회원님 대신 전하게 하고, 병원 동행은 건강 소식까지 허락받은 보호자에게만 보이게 해서, 생활 요청이 늘어도 보호자에게 보이는 범위는 회원님이 정한 대로 유지된다 N1 데모 부록 2 대신 올리기가 허락 없으면 막히고, 병원 동행이 건강 소식 허락 없는 보호자에게 보이지 않음(US-23). 통합 데모 11/17 장면

Next — 모듈이 붙는 동안 (각 1~2주)

기능(출력) 결과 문장 함께하는 모듈 확인 방법
G 비서가 D 고지를 그대로 쓰기: 고지문 v2(비서 사용 추가), 대리인도 MEMBER 버전 확인 [가설] 회원과 대리인이 비서를 쓰기 전에 같은 고지를 읽게 해서, AI 창구가 늘어도 고지가 한곳에서 관리된다. 보호자용 비서는 두지 않는다(viewersOf는 G Next 도구 후보) G 고지 미확인 회원·대리인의 비서 사용 차단
G의 금전 의도 인계를 D 금전 부탁으로 받기 회원이 "은행이래, 돈 옮기래"라고 말하면 비서가 유형도 고르지 않고 회원 말 그대로 직원에게 넘기고, 직원이 회원이 고른 가족에게 잇게 해서, 사기 피해(P-039)를 사람이 먼저 막을 기회를 만든다 [가설] G 데모 시나리오 G-4가 금전 부탁 기록으로 이어짐
C 케어 단계 통지를 건강 소식으로 받기: 종류 CARE_STAGE_CHANGE, EXTERNAL_CARE_START(C P1). EXTERNAL_CARE_END는 그 뒤. 종류, 규칙, 테스트는 D MVP(F8)에 이미 있고, 여기서는 C가 실제로 붙는다 생활 지원 단계가 바뀌거나 다른 기관 돌봄이 시작될 때 회원이 허락한 보호자가 같은 체계로 알게 해서, 단계 전환 결정이 가족 분쟁으로 번지기 전에 공유된다 [가설] C C 데모 12/10 통지가 HealthFeedCommand로 들어와 김지민에게만 보임
면회 예약(일정 항목에 더함), 범위 변경 알림 세부 보호자가 회원이 허락한 범위에서 면회 예약을 시설 기록 그대로 보게 해서, 면회 일정 확인 전화가 줄어든다 [가설] 면회 예약의 주인(D family 또는 운영 화면) [미정] 예약 생성·변경이 SCHEDULE 허락 보호자에게만 보임. MVP 일정은 코어 keyDates 6개(2026-11-03 확정)
일정에 회원이 신청한 프로그램(N2-2), 보호자 첫 화면 레지던스 공지(N2-D2) (2026-11-04) 보호자가 회원이 허락한 일정 안에서 부모님이 신청한 프로그램 날짜를 보고, 레지던스가 보호자에게도 알리는 공지를 한곳에서 보게 해서, "어떤 모임에 가세요?", "면회 시간이 바뀌었나요?" 같은 확인 전화를 줄인다 [가설] N2 커뮤니티(community. ProgramQuery.enrolledSessionsOf, NoticeQuery.guardianNoticesFor) 확정 신청만 보이고 대기·시설 예약·출석 여부는 없음(US-20). 공지는 직원이 고른 것만(US-06 7번). 통합 데모 D-N2-1(11/18)
보호자 스스로 연결 끊기, 형제 보호자 여럿의 화면 정리 보호자도 원하지 않으면 스스로 빠질 수 있게 해서, 연결 관계가 실제 가족 상황과 맞게 유지된다 — 연결 해제 후 코어 관계·D 허락 동기화 테스트

Later — 실서비스에 가까워지기

기능(출력) 결과 문장 전제 확인 방법
실제 문자·알림톡, 휴대전화 본인 확인 연동 보호자가 실제 문자로 알림을 받고 본인 확인으로 들어오게 해서, 데모를 실제 시범 운영으로 옮긴다 발신 번호·사업자 등록, 본인 확인 업체 선정 발송 실패 재시도·대사 테스트
보관 기간과 파기 자동화 퇴거·연결 해제 후 정해진 기간이 지난 동의·열람 기록과 건강 소식 본문을 자동으로 파기하게 해서, 운영사가 개인정보 보관 원칙을 기록으로 증명한다 보관 기간 확정 [법률 검토] 파기 배치와 파기 기록 테스트
동의서 법률 검토 반영(별도 동의 방식, 재동의 기준, 대리인 동의) 법률 검토를 거친 문구와 절차로 동의를 받게 해서, 초안 표시를 걷어 낸다 변호사·개인정보 보호 담당자 검토 검토 의견 대응표
I-41 이례 거래 보호자 알림 회원 계좌에서 평소와 다른 큰 출금이 생기면 회원이 허락한 보호자가 알게 해서, 경제적 착취 피해를 일찍 막는다 금융기관 제휴(B2B2C)가 전제. 운영사가 회원 계좌를 볼 정식 경로가 없다 [사실, K25 맥락, shortlist 통합안]. D는 알림을 받는 동의 항목과 화면만 준다 면접에서 "다음 단계"로 설명. 만들지 않는다
보호자 인터뷰 기반 화면 개선 보호자가 실제로 찾는 정보를 먼저 보게 해서, NSM(허락한 소식이 닿은 비율)을 확인할 수 있게 한다 보호자 인터뷰 3~5명 [NEED] 인터뷰 결과 대응표

순서와 의존

코어 MVP ─► G 최소판 ─► B ─► D MVP ─► G 정식 ─► C
                         │      ▲  │        ▲      ▲
                         └ 건강 소식 ┘  └ 고지·금전 인계 ┘ 케어 통지
  • 모듈 순서 A → B → D → G → C [사실, 2026-11-02 확정]. B는 D보다 먼저 만들어지므로 B는 D가 없을 때 "보호자 알림을 보내지 않고 기록만"으로 동작하고, D가 붙으면 HealthFeedCommand로 올린다 [가설].
  • D가 코어에 기대는 것: authorize() 확장 정책 등록, GuardianQuery·GuardianCommand, RepresentationQuery, BillingQuery, ContractQuery.keyDates, StaffQuery(직무), MealQuery, AuditWriter, 코어 이벤트(residentIds 포함), 장기 부재 이벤트와 AbsenceQuery(2026-11-03 코어 확정, F18), MealQuery의 absent, platform의 Notifier·Clock. D가 요청한 보강(HUB-1~11)은 코어 v1.1로 들어갔다(재승인 2026-11-03, tech-design.md 확인할 것).
  • 코어 변경은 순서대로 한다. D 작업 중 코어를 바꿔야 하면 허브에 요청하고 코어 문서를 먼저 고친다 [사실, 04-planning/CLAUDE.md].
